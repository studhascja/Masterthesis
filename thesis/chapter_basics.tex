\section{Used Hardware} \label{sec:used_hardware}
First, the requirements for the hardware, particularly for the Wi-Fi cards, are discussed in order to provide the basis for the subsequent explanation of the hardware selection.  
The requirements apply especially to the Wi-Fi card.  
As mentioned in Chapter \ref{subsec:objective}, the Wi-Fi standards 4 through 6e and the frequency bands from 2.4 GHz to 6 GHz are relevant for the tests.  
Therefore, the Wi-Fi card must at least support Wi-Fi 6e.  
In addition, the drivers and firmware of the card should be open, as this ensures greater transparency for time analysis and allows for modifications to investigate their influence.  
Moreover, different Wi-Fi cards with different drivers and firmware are required.  
This makes it possible to compare the impact of components that cannot be replaced or are largely vendor-dependent.  
For the underlying computing unit, compatibility with the Wi-Fi card and affordability are the most relevant criteria.  
Specialized real-time hardware is deliberately avoided, since \ac{WLAN} is not a real-time standard and is more commonly used in mixed systems\footnote{In this context, mixed systems refer to systems that include both real-time and non-real-time requirements or processes. In other words, a system that is not purely designed for real-time but still needs to fulfill such properties, albeit to a lesser extent.}.

To include different drivers and firmware in the evaluation and to have access to fully open firmware, the AR5BXB92 from Qualcomm Atheros is used as additional card.  
This card was released in 2008 and only supports Wi-Fi 4 with 2.4 GHz and 5 GHz, as noted in \cite{ar5b}.

\section{Yocto Project} \label{subsec:yocto}
The Yocto Project was initiated by the Linux Foundation in 2010, as reported in \cite{The_Linux_Foundation_2011}.  
As Salvador notes in \cite[Chap. 1]{10251255}, the Yocto Project is open source and emerged as a collaboration among multiple companies with the common goal of developing Linux-based embedded systems.  
Its primary objective was to minimize duplicated work.  

As described by Gonzales in \cite[Chap. 1]{Gonzalez_2018}, the Yocto Project provides a framework for building embedded Linux distributions.  
These distributions are designed to be as minimal as possible, while remaining modular and extensible.  
The name of the project reflects its idea.
As noted in \cite[p. 29]{units}, “yocto” denotes the very small factor $10^{-24}$, symbolizing the creation of very small Linux distributions.  

\begin{figure}[ht]
    \centering
    \includegraphics[width=\linewidth]{figures/yocto.drawio.pdf}
    \caption{Overview of the Yocto workflow, based on \cite[p. 56]{layer} and \cite{yocto_pic}}
    \label{fig:yocto}
\end{figure}

According to Salvador \cite[Chap. 1]{10251255}, the Yocto Project evolved from the OpenEmbedded Project, which pursued similar goals of creating a flexible and reusable build system for different architectures.  
In this context, BitBake emerged as the build tool, comparable to \texttt{make} or \texttt{cmake}, but significantly more powerful.  

One of OpenEmbedded’s main challenges was that its codebase quickly became unstable due to a lack of structure.  
As a result, Poky was introduced.
Poky is a minimal Linux distribution that now serves as the default reference distribution within the Yocto Project.  
As Salvador explains, Poky consists of a collection of tools, configurations, and metadata provided through recipes.  

Figure \ref{fig:yocto} illustrates part of Yocto’s structure and workflow.  
To build a Linux distribution, several essential types of information are required:

\begin{itemize}
    \item \textbf{Metadata}: Provided through recipes, which are organized into layers.  
          As shown in Figure \ref{fig:yocto}, layers include OE-Core and meta-yocto, which are the OpenEmbedded core metadata and Yocto-specific layer, both included in Poky.  
          Additional layers such as \texttt{meta-raspberrypi} provide \ac{BSP} support, while other layers may cover tools or custom extensions.  
          Each layer contains a \texttt{/conf/layer.conf} file specifying metadata and structure.  

    \item \textbf{\ac{BSP} Configuration}: Hardware descriptions are provided through \ac{BSP} layers.  
          Poky includes a default \ac{BSP} for QEMU.  

    \item \textbf{User and Policy Configuration}: User configurations are typically defined in \texttt{local.conf}, e.g., selecting the target machine.  
          For instance, with the \texttt{meta-raspberrypi} layer, the specific Raspberry Pi model must be declared.  
          The file \texttt{bblayers.conf} specifies which layers are included in the build, with priorities determining the order in which recipes are searched.  
          Policy configuration defines choices such as the package manager or init system.  

    \item \textbf{Source Mirrors}: These provide the actual source code for the distribution, usually consisting of upstream project releases and local projects.  
\end{itemize}

In addition to build inputs, Figure \ref{fig:yocto} outlines the sequence of tasks executed during the build process, simplified into recipe phases.  
As described in \cite{yocto_style_guide}, the recipe usually starts with the \texttt{do\_fetch} task.  
This task retrieves all resources specified in the \texttt{SRC\_URI} variable, as outlined in \cite{yocto_Tasks}.  

Subsequently, the source code is unpacked into the working directory by the \texttt{do\_unpack} task.  
After that, the \texttt{do\_patch} task searches for patches applicable to the unpacked source code and applies them.  
These patches, however, must be provided in the recipe's \texttt{SRC\_URI} variable.  

Next, the \texttt{do\_prepare\_recipe\_sysroot} task installs the required files into the recipe-specific sysroot.  
In the \texttt{do\_configure} task, \texttt{oe\_runmake clean} is executed, which corresponds to a \texttt{make clean} when using \texttt{make}.  

In the following step, the source code is compiled by the \texttt{do\_compile} task.  
Then, the \texttt{do\_install} task copies all packaged files into the holding area, which contains all files which will be installed into the file system later.  
The \texttt{do\_populate\_sysroot} task subsequently copies some of the files installed by \texttt{do\_install} into the respective sysroot.  

Finally, the \texttt{do\_package} task splits the content of the holding area into available packages.  
Thus, the packages highlighted in yellow in Figure~\ref{fig:yocto} are generated.  
These packages are then integrated into an image during the image generation process\footnote{The image generation shown in Figure~\ref{fig:yocto} is strongly simplified.  
Additional intermediate steps exist but are not presented or further discussed, as they are not relevant for this work.}.

\section{Linux Network Stack} \label{subsec:linux_stack}

A simplified representation of the Linux network stack is shown in Figure \ref{fig:network_stack}.
In this illustration, the link-layer is depicted in greater detail.
The figure highlights both the path of an outgoing network packet from the application layer through the \ac{NIC} to the network, as well as the path of an incoming network packet.
The reception path is indicated in green, while the transmission path is highlighted in purple.

\begin{figure}[ht]
    \centering
    \includegraphics[width=\linewidth]{figures/network_stack.drawio.pdf}
    \caption{Presentation of a simplified Linux network stack}
    \label{fig:network_stack}
\end{figure}

During transmission, the path begins at the application layer.
In step \circnum{1}, the BSD socket API, as described in \cite{bsd}, interacts with the socket implementation in kernel space.
In the Linux kernel, sockets are represented by the \texttt{struct socket}, which manages the file descriptor.
Since sockets in Linux exist only as files, this abstraction is required.
Network packets are represented as \texttt{struct sk\_buff}, as described in \cite{arnout} and are incrementally filled across the different network layers.
The application provides the data, which constitutes the payload.
Kernel sockets represent the session layer and, as Gregg explains in \cite[Chap. 10.4.3]{Gregg_2020a}, are responsible for communication with the transport layer.
Furthermore, as outlined in \cite[p. 153]{FREITAS2022148}, sockets handle protocol binding.
Thus, a dedicated stack exists for each transport protocol.
In Figure \ref{fig:network_stack}, \ac{UDP} and \ac{TCP} are illustrated as representative examples, as both are used in this work.

In step \circnum{2}, sockets communicate with the transport layer.
This communication is handled via the \texttt{struct proto\_ops} contained within the socket.
The structure provides functions such as \texttt{connect} and \texttt{send} for executing protocol-specific operations.
For \ac{TCP}, as described in \cite{arnout}, the function \texttt{tcp\_transmit\_skb()} is called.
This function constructs the \ac{TCP} header and attaches it to the \texttt{sk\_buff}.
Control is then passed to the network layer.
This is shown in step \circnum{3}.
Here, the function \texttt{ip\_queue\_xmit()} performs routing and appends the IP header to the \texttt{sk\_buff}.
Subsequently, the function \texttt{dev\_queue\_xmit()} passes control to the link layer and enqueues the packet in the \ac{Qdisc}.
This step corresponds to \circnum{4}.
At this point, the packet enters the transmission API (Tx API).
As explained by Bolla et al. in \cite[p. 5]{tx_napi}, this API primarily consists of driver functions whose purpose is to notify network interfaces of the presence of packets.

The Tx API starts with enqueuing the packet into the \ac{Qdisc} and ends with its transfer to the driver queue, called \texttt{tx\_ring}.
The packet is assigned a priority within the virtual queue and, based on the scheduler policy, handed over via \texttt{dev\_start\_xmit()} to the \texttt{tx\_ring}.
The \ac{NIC} is then notified of the new packet.
According to \cite{arnout}, the most common scheduler policy is \texttt{pfifo\_fast}, which is a first-in-first-out policy with three priority levels.

In step \circnum{5}, the packet is retrieved from memory by the \ac{DMA} engine of the \ac{NIC} and in step \circnum{6} it is transmitted.
Once the packet has been successfully transmitted, the \ac{NIC} generates an interrupt, which triggers a soft \ac{ISR} with the \texttt{NET\_TX\_ACTION} flag.
As a result, the file descriptor of the transmitted packet is released.

Step \circnum{6} also represents the arrival of a packet at the \ac{NIC}.
This path, as previously mentioned, is highlighted in purple.
In step \circnum{7}, the \ac{NIC} writes the packet into the receive driver queue, represented in the figure as the Rx-ring.
As described in \cite[p. 4]{tx_napi}, this consists of available packet descriptors.

Step \circnum{8} takes place within the Linux receive API, known as NAPI.
Prior to NAPI, as explained in \cite[p. 4]{tx_napi}, packets were passed to the kernel via interrupts.
At high data rates, however, this caused significant overhead.
NAPI instead employs a polling mechanism.
The polling queue is notified of new packets by the soft \ac{IRQ} \texttt{net\_rx\_action}, which does not interrupt the \ac{OS}.
This queue contains all registered network devices.
A registered device is a physical or virtual network interface for which a NAPI poll function has been registered.

When \texttt{net\_rx\_action} is triggered, each device in the poll list invokes its poll function.
Each device then checks its respective Rx-ring for new packets\footnote{Each physical \ac{NIC} maintains at least one Tx- and one Rx-ring, as described in \cite[p. 4-6]{tx_napi}.
Since registered devices are usually physical interfaces, each device has its own Tx- and Rx-rings.
In Figure \ref{fig:network_stack}, only one \ac{NIC} is shown for simplicity.}.
When a packet is retrieved from an Rx-ring, the function \texttt{netif\_receive\_skb()} is invoked, which constructs the \texttt{sk\_buff} data structure and promotes the packet from the link layer to the network layer.

In step \circnum{9}, the packet is received by the function \texttt{ip\_rcv()}, which parses the headers and validates them, as described in \cite{arnout}.
If the receiving host is the intended destination specified in the IP header, the packet is delivered to the transport layer via \texttt{ip\_local\_deliver()}.

In step \circnum{10}, the packet is processed by the function \texttt{tcp\_v4\_rcv()} in the case of \ac{TCP}, as described in \cite{arnout}.
Here, the protocol-specific handling takes place.
For \ac{TCP}, for example, acknowledgements are verified.
Once protocol-specific processing is complete, the method \texttt{sk\_data\_ready} is triggered, handing the data over to the session layer, i.e., the kernel sockets.

In the final step, \circnum{11}, a system call transfers the data from the kernel sockets to user space.

\section{Wi-Fi standards} \label{subsec:stand}
Before discussing the specific standards and their characteristics, the frequency properties of Wi-Fi must first be explained.
These are illustrated in Figure \ref{fig:channel}.
It can be observed that Wi-Fi operates on the three frequency bands 2.4 GHz, 5 GHz and 6 GHz.
Each frequency band is divided into channels, which are spaced at intervals of 5 MHz.
For the 2.4 GHz band, as described in \cite[p. 2790]{9363693}, 13 channels exist, ranging from 2.412 GHz to 2.472 GHz.
Each channel has a minimum bandwidth of 20 MHz.
Since the channels are arranged in 5 MHz steps, they overlap, as shown in Figure \ref{fig:channel}.
Li et al. state in \cite[p.888]{li_pan} that the channel width is 22 MHz.
However, Nicolade et al. clarify in \cite[p. 1]{8088188} that this applies only to the legacy 802.11 standard.
This standard employs DSSS (Direct Sequence Spread Spectrum), which uses a channel width of 22 MHz.
With 802.11b, which is also considered in this work, \ac{OFDM} is used, which has a minimum channel width of 20 MHz.

The channel number always indicates only the center frequency.
For example, channel 1, located at 2.412 GHz, spans from 2.402 GHz to 2.422 GHz.
Thus, in the 2.4 GHz band, there are only the four non-overlapping channels 1, 5, 9 and 13, which are highlighted in green in Figure \ref{fig:channel}.
The availability of channels depends on the country.
In the United States, only channels 1 to 11 are permitted, while in Japan channel 14 also exists.
In this work and therefore also in Figure \ref{fig:channel}, the regulations of the European Union are followed.

\begin{figure}[ht]
    \centering
    \includegraphics[width=\linewidth]{figures/channel.drawio.pdf}
    \caption{Presentation of the channels of 2.4 GHz, 5 GHz and 6 GHz channel allocations, based on \cite{channel_palnning,data_alliance}}
    \label{fig:channel}
\end{figure}

The 5 GHz band is divided into three or four sections.
As described in \cite{5ghz}, these are referred to as U-NII-1, U-NII-2, U-NII-2-Extended and U-NII-3.
The last band is not available in the European Union and is therefore not fully represented in Figure \ref{fig:channel}.
In this frequency band, only non-overlapping channels are shown.
The 5 GHz band starts with channel 36 and ends with channel 144, or channel 165 in the United States.
A gap exists between channel 64 and channel 100, since no channels are allocated in this range.
Furthermore, the channels are shown with bandwidths of 20, 40, 80 and 160 MHz, always referencing the center channel.
For instance, in the 40 MHz band, the center between channel 36 and 40 is channel 38.

It can also be seen that the U-NII-2 band is marked as containing DFS channels.
\ac{DFS} is mandatory in the ranges 5.25-5.35 GHz and 5.47-5.725 GHz, since these frequencies are also used by aviation and military radar systems, as described in \cite{dfs}.
As a consequence, the connection must continuously scan for radar-specific pulse patterns and upon detection, switch to another frequency.
\ac{DFS} also includes weather radar, which, as explained in \cite[p. 4]{weather}, operates between 5.6 GHz and 5.65 GHz.

The 6 GHz band is divided into the radio bands U-NII-5 through U-NII-8, although in the European Union only U-NII-5 is permitted, as described in \cite{6ghz}.
The representation of this band is identical to that of the 5 GHz band.
In this band, channels start again at channel 1 and end at channel 93, or at channel 233 in the United States.
Thus, in the European Union, 500 MHz—corresponding to the frequencies 5.925-6.425 GHz—are available.
In contrast, in the United States, channels up to 7.125 GHz can be used.
Unlike the 5 GHz band, no \ac{DFS} channels exist in the 6 GHz band.

\subsection{IEEE 802.11n}
Before addressing the specific characteristics of Wi-Fi 4, also known as IEEE 802.11n, a fundamental technology must first be introduced.
As described in \cite[p. 20]{ofdm}, one of the essential components of IEEE 802.11 is the modulation and multiplexing scheme \ac{OFDM}.
This principle is illustrated in Figure \ref{fig:ofdm}.

\begin{figure}[ht]
    \centering
    \includegraphics[width=\linewidth]{figures/OFDM.drawio.pdf}
    \caption{Presentation of OFDM with 64 QAM modulation, adapted from \cite{ofdm_pic}}
    \label{fig:ofdm}
\end{figure}

As previously described, Wi-Fi connections use channels with a bandwidth of 20 MHz.
In Wi-Fi 4, these channels are divided into 64 so-called orthogonal subcarriers.
Each subcarrier consists of a sinusoidal wave with its own frequency and amplitude and thus represents a subset of the 20 MHz channel.
The subcarriers must be orthogonal to one another, which requires that equation \ref{eq:skalar} holds true.

\begin{equation} \label{eq:skalar}
\int_{0}^{T} s_1(t) \, s_2(t) \, dt = 0
\end{equation}

In other words, if the scalar product of the sinusoidal functions of two subcarriers $s_1$ and $s_2$ equals zero, they are perpendicular to each other and therefore do not interfere.
In \ac{OFDM}, this condition means that for the frequency spacing $\Delta f$ between two subcarriers, as indicated in Figure \ref{fig:ofdm}, the relation shown in equation \ref{eq:delta} must hold.

\begin{equation} \label{eq:delta}
\Delta f = \frac{1}{T_u}
\end{equation}

Here, $T_u$ denotes the useful symbol duration, i.e., the time interval during which a \ac{QAM} symbol is transmitted.

Figure \ref{fig:ofdm} shows that three types of subcarriers exist: guard subcarriers, pilot subcarriers and data subcarriers.
In Wi-Fi 4, the 20 MHz channel is divided into 64 subcarriers, which results from the use of a 64-point Fast Fourier Transform (FFT).
Each FFT point represents a discrete frequency bin in the spectrum and determines the resolution of the subcarrier allocation.
For simplicity, the subcarriers are depicted schematically in Figure \ref{fig:ofdm}.
In practice, the channel consists of four pilot subcarriers, 48 data subcarriers, and 12 unused subcarriers, which, as described in \cite[p. 20]{ofdm}, are referred to as guard subcarriers.

Guard subcarriers are located at the edges of the spectrum and serve to reduce interference between adjacent channels.
As can be seen in Figure \ref{fig:ofdm} there is also one guard subcarrier in the middle.
This one is called DC-subcarrier (direct conversion subcarrier) and isn't used because it is exactly on the center frequncy of the channel frequency.
Pilot subcarriers are inserted at predefined positions within the band and are used for channel estimation, synchronization and phase tracking.
Pilot subcarriers carry known signals, so the receiver can determine the error caused by the transmission.
Data subcarriers carry the actual data.

The spacing between two subcarriers in Wi-Fi 4 can be calculated as $\Delta f = \frac{20 MHz}{64} = 312.5 kHz$.
From this, an effective symbol duration $T_u$ of 3.2 $\mu s$ is obtained, as shown in Equation \ref{eq:tu}.

\begin{equation} \label{eq:tu}
T_u = \frac{1}{\Delta f} = \frac{1}{312.5 \, \text{kHz}} = 3.2 \, \mu s
\end{equation}

After each modulation symbol duration $T_u$, a guard interval is added, to avoid inter-symbol inteference caused by multipath propagation.
In Wi-Fi 4, this guard period has a length of 0.8 $\mu s$.
This results in a total symbol duration $T_s$ of 4 $\mu s$.

Figure \ref{fig:ofdm} distinguishes between the two types modulation and \ac{OFDM} symbol.
The \ac{OFDM} symbol is computed as shown in Equation \ref{eq:forier}.
Here, $N$ denotes the number of FFT points, and $k$ represents the respective subcarrier index.
$X[k]$ is the modulation symbol of the corresponding subcarrier.
Each modulation symbol is multiplied by the Fourier basis vector $e^{j2\pi kn/N}$ and summed across all subcarriers to construct the \ac{OFDM} symbol.
Finally, the result is normalized by $\frac{1}{N}$ to average across all subcarriers.

\begin{equation} \label{eq:forier}
x[n] = \frac{1}{N} \sum_{k=0}^{N-1} X[k] e^{j 2 \pi kn / N}, 
\quad N = 64, \quad X \in \mathbb{C}
\end{equation}

Figure \ref{fig:ofdm} also illustrates how a modulation symbol is determined.
The modulation symbol depends strongly on the chosen modulation scheme.
In the case of Wi-Fi 4, this scheme is \ac{QAM}-64.

The modulated signal, as described in \cite[p. 2,3]{CHEN20181}, is a sinusoidal wave with a distinct amplitude, phase, and frequency.
This waveform can be expressed as a combination of sine and cosine functions and is represented on a constellation diagram, as depicted in Figure \ref{fig:ofdm}.
The constellation diagram has a limited range, since the lengths of the X- and Y-axes depend on the signal power, which is constrained by the standard.
For \ac{QAM}-64, the diagram is subdivided into 64 discrete regions.
Consequently, the signal can be encoded with a precision of $\log_2(64) = 6$, meaning that each symbol represents 6 bits.
During reception, the received point is projected back onto the constellation diagram and its corresponding bit value is determined.
Since each of the 64 regions represents an area rather than a single point, the signal does not need to be transmitted perfectly.
As long as the received point lies within the correct decision region, the corresponding bits can be correctly decoded.
The transmitted point is a complex number.

Higher-order modulation schemes such as \ac{QAM}-1024 also exist.
In this case, the constellation diagram is divided into 1024 regions, which allows encoding of 10 bits per symbol.
While this increases the information density, it also makes the transmission more error-prone, since the decision regions become narrower.

For Wi-Fi 4, these techniques result in a data rate of 72 Mbit/s, as shown in Equation \ref{eq:through}.


\begin{equation} \label{eq:through}
\frac{48 Datasubacarries \times 6 Bits}{4 \mu s} = 72 Mbit/s
\end{equation}

\subsection{Real Time Systems} \label{subsec:rts}
As Mächtel and Quade describe in \cite[Chap. 1]{Quade_Maechtel_2012}, the result of a real-time system depends not only on correctness but also on a temporal component.  
A real-time task has a time window in which the result must be delivered.  
Otherwise, the result loses its value.  
This time window is defined in Figure \ref{fig:utility} by a minimum threshold $T_{Dmin}$ and a maximum threshold $T_{Dmax}$.  
A good example is a pacemaker.  
It is not sufficient that the pacemaker is able to deliver an electric pulse, it must do so at the correct time.  
If the pulse is delivered too early or too late, the patient will most likely suffer harm rather than being stabilized.  

As Quade and Mächtel explain in \cite[p. 24]{Quade_Maechtel_2012}, different types of real-time systems are distinguished.  
Figure \ref{fig:utility} illustrates the three types soft, firm, and hard real-time systems.  
In a soft real-time system, shown in Figure \ref{subfig:soft}, the value of the result decreases the further it deviates from the deadlines.  
In a firm real-time system, shown in Figure \ref{subfig:firm}, the value of the result drops immediately to zero if the boundaries are violated.  
In a hard real-time system, as shown in Figure \ref{subfig:hard}, the value of the result even becomes negative as soon as the boundaries are violated.  
Strictly speaking, there are no negative percentages, but the figure illustrates that in hard real-time systems, failing to meet the deadline does not merely render the result useless, but even it may cause harm.  
This is the case, for example, with a pacemaker.

To guarantee that a specific task delivers its result within these boundaries, both the task and the system must be fully predictable.  
This predictability is referred to as \textbf{determinism}.  
A task with real-time constraints usually occurs repeatedly, in other words, periodically.  
This does not necessarily mean in a fixed cycle.  
Thus, a minimum period $T_{Pmin}$ and a maximum period $T_{Pmax}$ exist, which separate two task executions.  

To ensure that a task always terminates within its real-time boundaries, this would ideally be proven mathematically.  
However, in systems with sporadic events this is difficult to achieve, which is why probabilistic approaches are often used.  
In other words, the \ac{WCET} of a task is determined, either mathematically or through repeated measurements.  
Using this, the maximum utilization $U_{max}$ can then be calculated.  
It is defined as $U_{max} = \frac{T_{WCET}}{T_{Pmin}}$, i.e. the longest execution time divided by the shortest distance between two events.  
If this value is below 1, the system should function correctly.  
According to Liu and Layland \cite[p. 9]{10.1145/321738.321743}, $U_{max}$ for many processes converges to $\ln(2)$, corresponding to $U_{max} = 0.69$.  
In practice, however, a more conservative threshold of $U_{max} < 0.5$ has proven effective, providing sufficient buffer.  
If a system is able to meet its real-time requirements, this property is referred to as \textbf{timeliness}.  

In addition to execution time and the number of deadline misses, jitter is frequently used as a quality metric for real-time systems, as described in \cite[p. 38]{real_time_systems}.  
Jitter refers to the temporal deviation from an expected event.  
For example, if the period $t$ is 3 ms and the start time is $t_0$, the following event is expected at $t_0 + 3$ ms.  
On a real system, however, it may occur at $t_0 + (3-x)$ ms, where $x \in [0, 3]$.  
This deviation $x$, i.e., the difference from the expected occurrence, is referred to as jitter and serves as a measure of the real-time capability of the system.  
The lower the jitter, the more deterministic the system is and thus the higher its real-time quality.  

The following section discusses how Linux can be made more real-time capable and which properties are most relevant in this regard.  

\subsection{Real Time Kernel} \label{subsec:real_time_kernel}
As described in Chapter \ref{subsec:yocto}, this work relies on Linux as the operating system.  
However, as noted in \cite{not_rt}, Linux does not inherently provide real-time capabilities.  
Additional functionalities not included in the standard Linux kernel can be introduced through extensions and modifications.
Theses are called patches.  
With the Preempt-RT patch, hereafter referred to as the RT-patch, Linux can be extended to meet the requirements of a real-time operating system\footnote{It is important to note that even with the RT-patch, Linux is not fully real-time capable, as demonstrated by a NASA study \cite{nasa}. Nevertheless, it is widely adopted in real-time applications, including by NASA and SpaceX, since it offers strong real-time capabilities while preserving the functionality of Linux.}.  

As discussed in Chapter \ref{subsec:rts}, a real-time system must be deterministic, i.e., predictable.  
It must be possible to determine the \ac{WCET} of a process and no spontaneous events may disrupt its execution.  

The RT-patch was initiated in 2005 by Steven Rostedt and others.  
As Rostedt explains in \cite{rt_patch}, one of the main causes of such unpredictable interruptions are hardware-generated interrupts.  
These signals, used by devices to communicate with the \ac{CPU}, are handled in \acp{ISR}.  
In conventional Linux systems, \acp{ISR} preempt processes, preventing the reliable determination of \ac{WCET}.  

In Linux, including with the RT-patch, processes are scheduled based on priority.  
Priorities range from $-100$ to $39$, whereas the lower number is the higher priority.  
For non-real-time processes, the priority $P$ is calculated as $P = 20 + NV$, where $NV$ is the nice value in the range $[-20, 19]$.
The default of the niche value is $0$.  
Thus, normal processes have priorities in the range $[0, 39]$.  
For real-time processes, $P = -1 - rt\_Prior$, where $rt\_Prior$ ranges from $[0, 99]$  yielding a priority range of $[-100, -1]$.  
As before $rt\_Prior$ has a default value of $0$.
Consequently, real-time processes are always preferred over non-real-time processes.  
Depending on the model of priorites they have different ranges.
In Linux the priorities often have a range of $[0, 139]$, where $139$ the highest priority is.
But for calculation of the priorities the model described before is used.

Interrupt handling is also adapted by the RT-patch.  
As described in \cite[p. 162]{rt_patch}, almost all\footnote{Exceptions exist, as noted in \cite[p. 163]{rt_patch}. Essential interrupts such as the timer interrupt are not threaded.} \acp{ISR} are moved into kernel threads.  
A distinction is made between hard \acp{IRQ} and soft \acp{IRQ}.  
Both are threaded, but while hard \acp{IRQ} remain non-preemptible, their execution becomes schedulable once threaded.  
Soft \acp{IRQ}, in contrast, are both schedulable and preemptible.  

Furthermore, the RT-patch introduces full kernel preemption.  
This means that user processes with sufficiently high priority can preempt kernel activities.  
Additionally, spinlocks and other blocking mechanisms have been replaced by mutexes to mitigate issues such as deadlocks and priority inversion.  
These modifications significantly improve the determinism of Linux under the RT-patch.
