\chapter{Test Environment}
In this chapter, the test environment is examined in more detail.
In the following, the terms test environment, test system and \ac{OS} are used. 
The test environment comprises both the test system and the \ac{OS}. 
The test system refers exclusively to the applications that are part of the test environment and run on top of the \ac{OS}. 
Accordingly, the test system does not include the underlying hardware or the \ac{OS} itself.

This chapter is divided into the three parts requirements, test system and the \ac{OS}. 
A detailed analysis of the requirements is provided at the outset, as they serve as the basis for both the development of the \ac{OS} and the test concept. 
Thus, the requirements constitute the foundation for the overall design of the test environment.
Afterwards the \ac{OS}, as it forms the foundation on which the test system will later be implemented, will be described.
Finally, the test system itself will be discussed in more detail.

\section{Requirements}
In this section, the requirements of the test environment are analyzed in greater detail. 
The discussion begins with a description of the system architecture, followed by an outline of general \ac{rt} requirements. 
These are then used to define the specific requirements applicable to the test system.

The test environment is illustrated in Figure \ref{fig:pi_wifi_general}. 
It consists of two Raspberry Pi 5 devices, whose exact composition is described in detail in Chapter \ref{sec:used_hardware}. 
One Raspberry Pi acts as the server, while the other functions as the client. 
Both devices run the same \ac{OS}.

    \caption{Outline of the overall test environment}

There are two communication links between the server and the client.
One link which transfers \ac{rt-data} and another one for transferring \ac{non-rt-data}.
These two links are illustrated in Figure \ref{fig:pi_wifi_general} in blue and red.
These connections are handled by separate processes but operate within the same network. 
The server provides an access point to which the client connects, thereby establishing a peer-to-peer connection.

In summary, the goal of the test environment is to transmit both \ac{rt-data} and \ac{non-rt-data} data over the same wireless network interface. 
While the bulk data throughput should be maximized, the primary focus is to ensure that no \ac{rt} violations occur on the \ac{rt} connection.

Since the test system is intended to transmit \ac{rt-data} among normal data, it must fulfill the requirements of a \ac{rt-system}. 
Therefore, the following section first outlines the general requirements of \acp{rt-system}. 
Subsequently, additional requirements that go beyond standard \ac{rt} criteria and are specifically relevant for this system within the given test environment are discussed in more detail.

\subsection{Requirements Real Time}
To enable a system to achieve \ac{rt} capability, numerous factors must be considered. 
Since this work aims to evaluate the \ac{rt} capabilities of Wi-Fi, an interface that is not inherently \ac{rt} capable—and given that hardware-based requirements would have little impact in this context while significantly broadening the scope of this thesis, only software-related requirements will be addressed.

As previously mentioned in Chapter \ref{sec:real_time}, the primary objective of a \ac{rt} system is predictability. 
According to Buttazzo \cite[p. 10]{Buttazzo_2024}, predictability can only be achieved if the system ensures timeliness, meaning that the value of a process depends not only on its correct output but also on its timely execution—specifically, meeting deadlines.

To fulfill these requirements, the software foundation, particularly the \ac{OS} kernel, must be tailored to \ac{rt} needs.
Key aspects include preemptiveness, scheduling, inter-task synchronization, inter-task communication, memory management, interrupt handling and timers.
The necessity for these mechanisms to be implemented differently in \ac{rt} capable kernels compared to non-\ac{rt} ones is discussed in detail in Chapter \ref{subsec:real_time_kernel} and will therefore not be reiterated here.

However, these mechanisms must not only be \ac{rt} capable at the kernel level—they also need to be considered during the development of applications intended to operate in a \ac{rt} context. 
As Buttazzo outlines in \cite[p. 13 - 20]{Buttazzo_2024}, particular attention must be paid to the choice of programming language, memory usage and synchronization and communication between processes.
It follows that, as shown in Figure \ref{fig:requirements} memory management, inter-task communication and inter-task-synchronsiation are not only requirements for the \ac{OS}, but must also be taken into account in the test system.

In \cite[p. 17, 18]{Buttazzo_2024} Buttazzo emphasizes that the choice of programming language for \ac{rt} systems should avoid the use of dynamic data structures and recursion. 
This is because dynamic memory allocation and deallocation introduce unpredictability in execution time, making it impossible to determine the program's timing behavior in advance. 
Therefore, memory must be allocated statically and prior to execution. 
Similarly, recursion poses a challenge, as it is difficult to predict the amount of memory required and the number of recursive calls during runtime.

Furthermore, Buttazzo argues that a programming language suitable for \ac{rt} applications should support bounded loops, meaning that the number of iterations is fixed and known at compile time. 
In general, programming languages for \ac{rt} systems should offer the capability to explicitly define timing constraints and ensure adherence to the aforementioned principles—ideally enforcing them.
As programming languages, Buttazzo suggests \texttt{Real-Time Concurrent C} and \texttt{Real-Time Euclid}, both of which fulfill all the stated requirements.

By contrast, Michael P. Rooney et al. describe in \cite[p. 1]{10321761} a study involving the development of a \ac{SCADA} \ac{rt} application implemented in the four different programming languages C, Rust, Numba Python and Cython.
All of these languages were successfully used to achieve \ac{rt} performance. 
Notably, Rust demonstrated a power consumption profile comparable to C, indicating similar efficiency.

While the characteristics outlined by Buttazzo are not mandatory in any of these languages, they can be implemented with appropriate discipline and design. 
Thus, these languages are also suitable for \ac{rt} application development, provided that the specific constraints related to memory management, recursion and timing predictability are consciously observed and enforced by the developer, as they are not inherently guaranteed by the language itself.

The chosen programming languages and specific implementation-level requirements for achieving \ac{rt} capability and how these are addressed are discussed in detail in Chapter \ref{subsec:impl}.

Furthermore, the test system must be capable of transmitting both \ac{rt} and non-\ac{rt} data concurrently over the same network, with the \ac{rt} traffic maintaining a maximum round-trip delay of 3 ms. 
This timing constraint stems from the fact that this work seeks to characterize Wi‑Fi’s \ac{rt} capabilities and the factors that influence them and to assess whether Wi‑Fi can be employed in an industrial \ac{rt} environment. 
As discussed in Chapter \ref{sec:real_time}, such environments commonly impose a 3 ms deadline.
So, beside the evaluation of the \ac{rt} capabilities of Wi-Fi and the minimization of the \ac{RTT}, timing constraint of 3 ms is the goal of this work, like stated in Chapter \ref{subsec:objective}.

Furthermore, a distinction is made between \ac{rt} and non-\ac{rt} requirements.

\subsection{Requirements of the Test Environment} \label{subsec:requirements}
The following section defines the requirements for the test environment which are shown in yellow in Figure \ref{fig:requirements}.
For both the test system and the \ac{OS}, the previously defined criteria for \ac{rt} capability are assumed to be fulfilled.

The requirements for the \ac{OS} include providing appropriate support for both the hardware and the software components of the test evnironment. 
As described in Chapter \ref{sec:used_hardware}, this work utilizes a Raspberry Pi 5, to which a MediaTek 7925B22M and an Atheros AR5BXB92 Wi-Fi module can be connected via PCIe.
Accordingly, the \ac{OS} have to support the Raspberry Pi 5 architecture and offer compatibility with the drivers mt76, mt7925e and ath9k.

Furthermore, the mt7925e driver is only available starting from Linux kernel version 6.8 and receives extended feature support with newer versions. 
These enhancements primarily concern functionality related to Wi-Fi 6E and Wi-Fi 7, which is described in \cite{mt76}. 
Since these standards are also within the scope of this work, the \ac{OS} should support the most recent possible version of the mt7925e driver to ensure full access to these capabilities.

In addition to hardware compatibility, the \ac{OS} must also ensure compatibility with the required software components. 
This includes the availability of essential programming languages and user-space networking and diagnostic tools which are necessary to run the test-system.

Moreover, the \ac{OS} should be as minimal as possible, containing only the components explicitly required for the test environment. 
This reduces background activity and minimizes potential sources of interference or error, thereby ensuring a more stable and predictable testing environment.

In addition to the \ac{OS}, the test system also has non‑real‑time requirements.
These are highlighted in yellow under “Test System” in Figure \ref{fig:requirements}. 
The application under test must be instrumented so that its \ac{rt} performance can be measured accurately, enabling meaningful conclusions to be drawn. 
This requires comprehensive monitoring and debugging facilities to precisely identify and isolate any sources of \ac{rt} violations.

For the non‑real‑time traffic, as much data as possible should be transmitted without degrading the \ac{rt} application’s performance. 
This means, only throughput and packet‑loss metrics need be considered for this traffic in the monitoring.

Moreover, this study will compare the \ac{rt} performance of the algorithms underpinning different Wi‑Fi standards. 
To that end, the server must support access points for Wi-Fi 4, 5 and 6 across all relevant frequency bands (2.4 GHz, 5 GHz and 6 GHz). 
The impact of QoS on \ac{rt} capability will also be evaluated, so the test system must be able to mark network packets with QoS parameters. 
Given the large number of combinations of Wi‑Fi standards, frequency bands and QoS settings, an automated test framework is required to generate a comprehensive dataset for all test cases, from which reliable insights can be derived.

In this chapter, the requirements for the test environment were defined. 
The following sections will discuss how these requirements are implemented. 
The focus will first be on the selection and configuration of the \ac{OS}, because it forms the foundation of the test environment after the choice of hardware.

\section{Operating System}
As discussed in the previous chapter, the selection of an appropriate \ac{OS} must primarily consider its \ac{rt} capabilities. 
Such \acp{OS} are referred to as \ac{RTOS}. 
There exists a wide variety of \ac{RTOS}, each differing in architecture, strengths and limitations.
The following section compares the advantages, disadvantages and performance characteristics of selected \acp{RTOS}. 
Furthermore, their suitability for the purpose of this work is evaluated.

\subsection{Selection of Operating System}
One \ac{RTOS} that imposes almost no restrictions in terms of performance and compatibility compared to a general-purpose \ac{OS} is RT-Linux. 
As described by Sampath et al. in \cite{Sampath_2007}, RT-Linux is a Linux-based system enhanced through the PREEMPT\_RT patch, which equips it with \ac{rt} capabilities. 
The authors examine the use of RT-Linux on an industrial controller with strict \ac{rt} requirements and additional \ac{rt} Ethernet demands. 
Their study demonstrates the suitability of RT-Linux for such applications, reporting a maximum jitter of 380 microseconds over a 24-hour endurance test.

Similarly, Arshiabanu \cite{ARSHIABANU_2014} presents a \ac{rt} system implemented using RT-Linux. 
The study evaluates the impact of various scheduling policies on \ac{rt} performance and is executed on a Raspberry Pi. 
Dewit et al. \cite{ae11aecebd4e4fd6896d0b8bb93fa73a} further investigate the influence of RT-Linux in combination with a Raspberry Pi 5 on scheduling latencies, reporting a maximum scheduling latency of 125 microseconds.
This study is especially relevant for this work, because it uses the same hardware platform.

Despite these studies, there also are more critical perspectives. 
Siro Arthur et al. \cite{Siro_2007} also evaluated \ac{rt} capabilities of RT-Linux. 
This study analyzes metrics such as context switch time, memory access latency and TCP latency. 
It compares not only various Linux preemption models but also contrasts RT-Linux against \ac{RTOS} specifically designed for \ac{rt} use, such as RTAI and LXRT. 
The study reveals that while the PREEMPT\_RT patch enhances \ac{rt} capabilities, it does not reach the same level of determinism as systems natively designed for \ac{rt} applications. 
Furthermore, this analysis was performed on single-core CPUs, where reduced shared resources can change the \ac{rt} behavior. 

There are also studies with multicore platforms which question the suitability of RT-Linux for hard \ac{rt} environments. 
Carvalho et al. \cite{9018464} investigated RT-Linux running on a Raspberry Pi, focusing on latency metrics such as polling, timed loops, hardware interrupts and software interrupts. 
Their results confirm that although RT-Linux offers certain \ac{rt}  properties, it should only be used in non-critical \ac{rt} environments. 
This conclusion is supported by Betz et al. \cite{5347056}, who state that RT-Linux is appropriate for soft \ac{rt} applications.

Yang et al. \cite{10870260} compare the \ac{rt} performance of NuttX, FreeRTOS, RT-Linux and Xenomai. 
A noteworthy aspect of their study is the inclusion of both \ac{rt} capabilities and general-purpose features. 
While RT-Linux can be used as a standalone system, to match these requirements, pure \ac{RTOS} like FreeRTOS and NuttX are executed alongside a general-purpose \ac{OS}. 
Also in this study a Raspberry Pi 4 was used as the hardware platform. 
The results are showin that pure \ac{RTOS}, especially FreeRTOS, netherless deliver better \ac{rt} performance.

Mariesk et al. \cite{6140739} distinguish between the two fundamental \ac{RTOS} types kernel-based \ac{RTOS} and embedded \ac{RTOS}. 
In their study, they evaluate systems based on interrupt latency, task switching time and preemption time. 
RT-Linux and Xenomai are considered kernel-based \ac{RTOS}, while eCos represents the embedded type. 
The results show that kernel-based \ac{RTOS} are more suitable for multi-task applications due to their lower task-switching overhead. 
Since this work requires the execution of multiple concurrent tasks, frequent scheduling switches are expected, making a kernel-based \ac{RTOS} the preferable choice.

In summary, the optimal \ac{RTOS} depends heavily on the specific application and \ac{rt} requirements. 
Based on the referenced studies, FreeRTOS appears to offer the best \ac{rt} capabilities. 
However, additional constraints beyond \ac{rt} performance must be considered when selecting the \ac{OS}, like stated in the previous section.
This means particularly hardware compatibility of the \ac{OS}. 
The MediaTek 7925B22M Wi-Fi card used in this work lacks drivers outside the Linux ecosystem, thereby excluding FreeRTOS as a viable option.

Considering the experience with RT-Linux on Raspberry Pi systems stated by the studies before and the demonstrated maximum scheduling latency of 125 microseconds along with a maximum jitter of 380 microseconds of the test-system, RT-Linux proves sufficient for the purposes of this work. 
Given a round-trip time (RTT) requirement of 3 milliseconds, this jitter is acceptable. 
Furthermore, since Wi-Fi is inherently not \ac{rt} capable
and as discussed in Chapter \ref{sec:used_hardware}, the employed hardware which has, among other shared resources, a split L3 cache, is not optimized for \ac{rt} processing.
So the minor limitations of RT-Linux do not significantly impact this test-environment.

There are various ways to implement an RT-Linux system. 
As described by Rostedt in \cite{rt_patch}, a  RT-Linux system can be created by extending the kernel with the $PREEMPT\_RT$ patch. 
This results in two primary approaches for building an RT-Linux system. 
One can either use an existing Linux distribution such as Ubuntu and apply the $PREEMPT\_RT$ patch, or build a complete Linux system from scratch using a build system.

As Vasquez outlines in \cite[Chap. 6]{10163343}, building an \ac{OS} using a build system offers the advantage of full customization tailored to specific needs. 
Every component of the \ac{OS} can be configured and assembled individually. 
However, this method is considerably more time-consuming compared to using a pre-built \ac{OS} that is already available for the Raspberry Pi 5, such as a customized Ubuntu version 24.02 or Raspberry Pi OS, which can then be extended with the $PREEMPT\_RT$ patch.

Due to the requirements defined in Chapter \ref{subsec:requirements}, the \ac{OS} must be capable of providing a foundation for both software and hardware. 
For the Wi-Fi card drivers, it is essential, as previously mentioned, that the kernel is as recent as possible. 
The kernel version can only be adapted with a reasonable effort, in the existing \acl{OS} for the Raspberry Pi 5.
A build system has a possibility, to do this more easily.
Moreover, certain kernel configurations must be set to support integration of these drivers. 
These configurations can be managed much more flexibly and conveniently using a build system. 
For this reason, the \ac{OS} used in this work is built using a build system.

Furthermore, an \ac{OS} built using a build system is the preferred choice for embedded systems, as noted by Navik in \cite{8008968}. 
This assertion is supported by Vasquez in \cite[Chap. 6]{10163343}, who argues that the main advantages lie in the minimal footprint and the ability to restrict applications and background processes as needed. 
Given that the requirements for the embedded system in this work also include reproducibility and minimal external interference, this further supports the decision to use a build system for the \ac{OS}.

As Salvador describes in \cite[Chap. 1]{10251255}, the Yocto Project is a widely used and powerful build system. 
It is open-source and comes with excellent documentation, making it a suitable choice for building the \ac{OS} in this work.

The technical details of how the Yocto Project functions were already covered in Chapter \ref{subsec:yocto}. 
Since all technologies used in the test system must be known for proper \ac{OS} configuration, the following chapter will provide a more detailed overview of the test setup.

\subsection{Structure of Test Environment}
Figure \ref{fig:technologies} illustrates the test environment along with all relevant components and technologies. 
As previously described, it consists of a server and a client. 
First, the structure of the test system is explained in more detail, followed by an analysis of how it satisfies the requirements defined in Section \ref{subsec:requirements}.

The test environment in Figure \ref{fig:technologies} is divided into several elements. 
The \ac{OS} is excluded from the discussion and the focus is placed solely on the components of the test system.

The server part of the test system is controlled via the \textbf{Server Test Suite}, which is responsible for executing test runs and automating the overall testing process. 
For each combination of access point configuration and QoS level, the test suite performs a complete test run. 
Therefore, the total number of test runs is defined as $N_T = N_{AP} \times N_{QoS}$, where $N_T$ is the total number of test runs, $N_{AP}$ is the number of different access point configurations and $N_{QoS}$ is the number of different considered QoS levels. 
The Server Test Suite is essential for the automated execution of these test runs, thereby fulfilling the previously specified requirement for test automation.

\begin{figure}[ht]
    \centering
     \includegraphics[width=\textwidth]{figures/Technologien_Testsystem.drawio.pdf}
    \caption{Illustration of the test environment including used technologies.}
    \label{fig:technologies}
\end{figure}

A \textbf{server-side test run} comprises the three components Hostapd, Iperf Bulk Server and Rust-RT Server. 
Each test run contributes to the overall test automation by ensuring that the required steps to establish both a \ac{rt} and a non-\ac{rt} network link within the same network are executed in the correct order.

The first step in a server-side test run is the creation of the \ac{AP}, which is achieved using the \textbf{Hostapd} software. 
Hostapd allows the configuration of various Wi-Fi standards, frequencies and bandwidths, thereby meeting the requirement to support multiple Wi-Fi standards.

Once the \ac{AP} is established, the server for non-\ac{rt} applications is launched using \textbf{Iperf3}. 
This Software supports differentiation between UDP and TCP traffic, various packet sizes and data rates. 
It also provides metrics such as packet loss and jitter, thus fulfilling all previously defined requirements for non-RT data transmission.

Finally, the \textbf{Rust-RT Server} is started. 
This component is implemented in Rust and makes use of \ac{BPF}. 
This enables both compliance with \ac{rt} requirements and integrated monitoring capabilities. 
The rationale behind the choice of programming languages is discussed after the explanation of the test system architecture in Section \ref{subsec:used_technologies}.

The \textbf{client-side test system} is structurally similar to the server-side system. 
As shown in Figure \ref{fig:technologies}, it also consists of a Client Test Suite and a test run. 
The functionality of the client-side test suite and test run mirrors that of the server-side system. 
However, the client-side test run differs slightly in structure.

The client-side test run comprises two phases. 
First, a connection to the server’s \ac{AP} must be established. This is handled using the \textbf{$wpa\_supplicant$} software, which utilizes a configuration file specifying details such as the network password and encryption algorithm. 
For this reason, client and server test runs must be synchronized.
Any mismatch in Wi-Fi standards will prevent the client from connecting to the server’s \ac{AP}.

Once a connection is established, the \textbf{Rust-RT Client} is launched. 
This client establishes a connection to the Rust-RT Server. 
Unlike the server-side test run, the Iperf client is not launched directly as part of the test run but is instead initiated from within the Rust-RT Client. 
The reason for this design choice is explained in more detail in Section \ref{subsec:impl}.

After describing the architecture and functionality of the test system and how it satisfies the specified requirements, the following section discusses the selection of technologies and their configuration within the Yocto environment.

\subsection{Used Technologies} \label{subsec:used_technologies}
To create an access point on the server, the software \texttt{hostapd} is used, as previously described.  
As Anderson states in \cite{hostapd}, this is one of the most widely used tools to create an AP that can be configured in detail.  
With this software, the Wi-Fi standard, frequency, bandwidth and encryption can be configured, as shown in \cite{hostapd2}.  
Thus, all previously specified requirements regarding the configurable properties of the Wi-Fi are met by this software.  

To allow the client to connect to the AP, the software \texttt{wpa\_supplicant} is used.  
As shown in \cite{hostapd2} and \cite{wpa}, it can be configured at the same level as \texttt{hostapd}.  
This allows for a fine-grained configuration of the connection to the AP.  
An alternative on Linux would be the NetworkManager.  
However, it includes more background processes and is therefore more heavyweight, which would impact the system more strongly.  
Moreover, it cannot be configured as precisely in coordination with \texttt{hostapd} as \texttt{wpa\_supplicant}.  

To generate network traffic, \texttt{iperf3} is used, as it fulfills the required specifications, as previously described.  
As shown in \cite{iperf}, this tool allows the generation of network traffic and precise configuration regarding TCP/UDP, packet size and throughput.  
Furthermore, no separate monitoring needs to be developed, as the tool already includes it.  
For example, latency and packet loss can be directly observed using \texttt{iperf3}.  

Both the server test suite and the client test suite are implemented in Python.  
This is possible because there are no real-time requirements for these components.  
Only the server responsible for the RT connection must fulfill real-time constraints.  
In this case, Python is a suitable choice because, as described in \cite{10209340}, it is very popular and widely used in embedded programming.  
Moreover, the language offers a high level of abstraction and is script-like in nature.  
Since the test suites only need to coordinate the testing processes, the script-based nature of Python is well-suited for this task.  

In contrast to the test suite, the RT server and client must fulfill real-time characteristics.  
As described by DLR in \cite[p. 86]{dlr212971}, most embedded real-time applications are written in C or C++.  
Nevertheless, Rust was chosen for the RT application in this work.  
This decision is based on the fact that DLR also states in \cite{dlr212971} that Rust is more suitable for RT applications due to its memory and thread safety.  
However, the language is still too young to be fully established for hard real-time systems.  
Rust does not use a garbage collector, as explained in \cite[p. 2]{10.5555/3563572.3563603}.  
Nevertheless, it prevents issues such as use-after-free, null pointer dereferencing and data races.  
This is achieved through Rust's ownership system.  
Ownership in Rust means that each value has exactly one owner, which becomes invalid once the owner goes out of scope.  
An owner can be a variable, function, or data structure that holds the exclusive right to access or modify a value.  
This mechanism also prevents undefined behavior.  
Furthermore, as described in \cite[p. 1]{10.5555/3563572.3563603}, Rust offers better development capabilities due to \texttt{rustc} and zero-cost abstractions.  
\texttt{rustc} allows better debugging and significantly eases troubleshooting.  
Rust provides better error messages than C and benefits from zero-cost abstractions.  
Additionally, as shown in \cite[p. 1]{10321761}, Rust performs similarly to C.  
Rust is also becoming increasingly popular, as noted in \cite[p. 2]{dlr212971}.  
This is also evident in its adoption into the Linux kernel due to its strong memory safety.  
As described by Panter in \cite{10.1145/3674805.3690756}, this integration has already shown promising results.  
Rust has also been integrated into Android for memory safety reasons.  
As described in \cite[p. 1]{seidel2024bringingrustsafetycriticalsystems}, the share of safety vulnerabilities was reduced from 76\% to 35\%.  
Moreover, increasing progress is being made in the field of real-time applications with Rust.  
As shown in \cite{Rust_Foundation}, the Safety-Critical Rust Consortium was founded in 2024 with the goal of using Rust in DO-178C-certified products.  
As described in \cite{do178} and \cite[p. 4]{seidel2024bringingrustsafetycriticalsystems}, this is one of the strictest certifications for airborne systems.  
In summary, Rust is well-suited for real-time applications and offers better development capabilities than C and C++.  
It is also becoming increasingly popular and has almost no performance disadvantages compared to C.  
Accordingly, the RT application in this work is written in Rust.  

To implement monitoring of the real-time application, \ac{BPF} is used.  
It can be seamlessly integrated into Rust code using \texttt{libbpf-rs}.  
\ac{BPF}, is a technology for efficient in-kernel data processing and monitoring, originally designed for packet filtering.  
As described by Gregg in \cite[Chap. 2.10]{Gregg_2020}, it was originally build to observ network packages.
And it offers nearly the same functionality as the widely used profiling tool \texttt{perf}.  
Furthermore, it is also employed in practice for network monitoring.
This is evident in \cite{network_obser} and \cite{9359159}.
However, it integrates better with Rust and is more flexible due to its scriptability and access to a broader range of event sources than \texttt{perf}.  
BPF supports more event sources such as tracepoints, kprobes, uprobes and performance counters, enabling more detailed and application-specific monitoring.  

In summary, the programming languages Python, Rust and BPF, as well as the tools \texttt{hostapd}, \texttt{iperf3} and \texttt{wpa\_supplicant}, must be provided by the operating system for the test system.  
The following section describes how this can be realized using the Yocto Project.

\subsection{Implementation}
The background and functionality of the Yocto Project have already been described in Section \ref{subsec:yocto}.  
Therefore, this section does not elaborate on them further and proceeds directly with the specific implementation within the context of this thesis.  

Figure \ref{fig:yocto_own} illustrates the structure of the Yocto Project as used in this work.  
The figure displays the various layers of the Yocto Project that were utilized.  
Layers that required no modifications are marked in green.  
Layers that were integrated but still required certain adjustments are highlighted in yellow.  
The red-colored \texttt{meta-masterthesis} layer was entirely developed as part of this thesis and contains all necessary customizations to the base image in order to meet the project-specific requirements.  

The Yocto Project used in this thesis incorporates the layers \texttt{poky}, \\
\texttt{meta-openembedded}, \texttt{meta-raspberrypi} and \texttt{meta-rust}.  
The \texttt{poky} and \\
\texttt{meta-openembedded} layers serve as the foundational layers, as is common in most Yocto-based projects, as discussed in Chapter~\ref{subsec:yocto}.  

From the \texttt{meta-openembedded} layer, the sublayers \texttt{meta-oe}, \texttt{meta-python} and \\
\texttt{meta-networking} are utilized.  
The \texttt{meta-python} layer provides support for the Python programming language, which is required by some of the tools used in the testing environment.  
The \texttt{meta-networking} layer supplies essential networking tools that are also necessary for the test setup.  

The \texttt{meta-raspberrypi} layer is essential for hardware-specific support for the Raspberry Pi platform.  
This layer enables the generation of a customized operating system image that is compatible with the Raspberry Pi 5, by providing the required kernel configurations, bootloader integration and board-specific device trees.  

The \texttt{meta-rust} layer is included to integrate the Rust programming language into the Yocto build system.  
This integration is necessary to develop the \ac{rt} application in Rust, as required by the objectives of this thesis.

All layers are built using Yocto version 5.2.1.  
This corresponds to the \texttt{walnascar} branch.  
As of in the mid of June, this was, besides the \texttt{master} branch, the most recent branch of the Yocto Project, as shown in~\cite{yocto-releases}.  
The latest branch was selected to take advantage of the most up-to-date kernel version included therein.  

The kernel version is crucial for the support of the \texttt{mt7925e} driver, which is only available starting from kernel version 6.8 and is better supported in even newer kernel releases, as described in~\cite{mt76}.  
The \texttt{walnascar} branch was available for all layers except for the \texttt{meta-rust} layer.  
In this case, it was necessary to manually add the \texttt{walnascar} branch to the \texttt{layer.conf} file.  

Due to compatibility issues, the variable \texttt{RUST\_LIBC} in this layer had to be replaced with \texttt{\$\{@d.getVar('RUST\_LIBC').lower()\}}.  
This variable also needed to be defined in the \texttt{local.conf} file using \texttt{RUST\_LIBC = "gnu"}.  
The GNU C Library was chosen because it is the default C library used in full-featured distributions for the Raspberry Pi.

\texttt{local.conf} must also define the target machine to be the Raspberry Pi 5.  
This ensures proper activation of the \texttt{meta-raspberrypi} layer.  
Furthermore, the preferred Linux kernel version must be explicitly set to 6.12, since the default version provided by the \texttt{meta-raspberrypi} layer is 6.1.  

The custom \texttt{meta-masterthesis} layer is assigned a higher priority than the other layers in \texttt{bblayers.conf}.  
This is necessary to ensure that the \texttt{.bbappend} files within this layer are processed before the corresponding \texttt{.bb} files of other layers.  
The \texttt{meta-masterthesis} layer can be divided into four recipe categories, illustrated in purple in Figure~\ref{fig:yocto_own}.  
The individual \texttt{.bb} and \texttt{.bbappend} files are depicted in light green in the same figure.

The Wi-Fi cards used in this work utilize 32-bit DMA addressing.  
The Raspberry Pi 5 does not support this addressing mode by default, as it uses 64-bit DMA addressing.  
Therefore, a device tree overlay must be used to enable 32-bit DMA support.  
A custom recipe was created to install the overlay \texttt{pcie-32bit-dma-pi5.dtbo}.  
This overlay can be obtained from the official Raspberry Pi firmware repository~\cite{overlay}.  
The recipe installs the locally available overlay into the \texttt{/boot/overlays} directory on the target system.  

By setting the variables \texttt{RPI\_USE\_OVERLAYS} and \texttt{RPI\_EXTRA\_CONFIG} in \texttt{local.conf}, the overlay can be included in the \texttt{config.txt} file.  
To fully integrate the overlay into the operating system, the \texttt{meta-raspberrypi} layer must be modified.  
Specifically, the overlay must be added to the \texttt{RPI\_KERNEL\_DEVICETREE\_OVERLAYS} section of the file \texttt{meta-raspberrypi/conf/machine/include/rpi-base.inc}.  
After this adjustment, the overlay was successfully deployed and referenced in the \texttt{config.txt} of the generated image.

To make the operating system real-time capable, the Linux kernel must be extended using the RT patch.  
This is handled within the \texttt{recipes-kernel} section of the \texttt{meta-masterthesis} layer.  
The Linux recipe provided by the \texttt{meta-raspberrypi} layer, which is based on version 6.12.1, is extended via a \texttt{.bbappend} file.  
However, the RT patch is officially only available for kernel version 6.12.28.  
Since this version is not compatible with 6.12.1, an older RT patch developed for version 6.12.8 was tested and found to work reliably.  
This patch was applied by integrating it into the Linux recipe using the \texttt{.bbappend} mechanism.

It is also essential to modify the kernel configuration to select the appropriate preemption model.  
All necessary kernel configuration options can be integrated by placing a \texttt{.cfg} file into the source directory of the Linux recipe.  
This ensures that the final kernel included in the image is real-time capable.

The \texttt{recipes-core} category includes extensions to the \texttt{init-ifupdown} and \texttt{base-files} recipes via \texttt{.bbappend} files.  
The \texttt{init-ifupdown} extension introduces a custom \\
\texttt{interfaces} file to assign static IP addresses to specific network interfaces.  
The \texttt{base-files} extension defines environment variables and configs that are automatically set upon opening a shell session.  
This is accomplished by writing shell commands into \\
\texttt{/etc/profile.d/myenv.sh}.  

The main component of \texttt{recipes-core} is the custom image recipe.  
This extends\\
\texttt{core-image} to include all necessary technologies for the test system.  
It includes self-developed \texttt{.bb} files as well as required tools and programming languages.

Once all technologies are installed on the target system, the final step is to integrate the application code and network configurations.  
This is done in the \texttt{recipes-connectivity} section.  
In the \texttt{network} category, marked in orange in Figure~\ref{fig:yocto_own}, two \texttt{.bbappend} files customize the configurations of \texttt{dnsmasq} and \texttt{dhcpcd}.  

Other \texttt{.bb} and \texttt{.bbappend} files in this section install applications from a custom Git repositorie onto the target system.  
The \texttt{hostapd.bbappend} file installs multiple \ac{AP} configurations into \texttt{/etc/hostapd/}.  
Additionally, it modifies the original recipe to compile \texttt{hostapd} using a custom configuration that supports the Wi-Fi 6E standard.  
By default, \texttt{hostapd} does not support access points operating in the 6~GHz band.  

The \texttt{setup.bb} file installs Python-based test suites from a GitHub repository.  
As these applications are written in Python, no prior compilation is required.

The \texttt{rust-client} and \texttt{rust-server} recipes were generated using the \texttt{cargo-bitbake} tool.  
This tool generates Yocto-compatible recipes for Rust projects, as explained in~\cite{cargo-bitbake}.  
It requires a Git repository reference in the \texttt{Cargo.toml} file and all dependencies to be vendored locally.  
The \texttt{cargo vendor} command, as described in~\cite{vendor}, is used for this purpose.

The generated recipes were extended to install not only the compiled binaries but also the full source code on the target system.  
Additionally, the recipe must include checksums for the vendored files.  

To enable eBPF integration in Rust, the file \texttt{vmlinux.h} is required.  
This file contains auto-generated headers that are used by the BPF program.  
To generate it, the kernel configuration option \texttt{DEBUG\_INFO\_BTF=y} must be enabled.  
The file can then be created using the command:  
\texttt{\$BPFT btf dump file "\$\{VMLINUX\_PATH\}/vmlinux" format c > \$\{S\}/src/bpf/vmlinux.h}.  

With these extensions, the Rust applications—including binaries, source code and a local compilation environment—are fully installed on the target system.

\section{Test system}
In this chapter, the test system is divided into the four components Server and Client, Monitoring, Test Automation and Access Point Configuration. 
Since the implementation of the client and server is closely linked to monitoring, an understanding of the fundamentals of monitoring is required for its description.  
Therefore, the following section first addresses monitoring, followed by the description of the implementation of the client and server.

\subsection{Monitoring} \label{subsec:monitoring}


As already mentioned in Chapter \ref{subsec:used_technologies}, \ac{BPF} is used for monitoring, which is integrated into the Rust code via \texttt{libbpf-rs}.  
The following section explains what \ac{BPF} is, how it works, and how it is used to implement the monitoring of the test system.  
The integration into Rust is described in more detail in Chapter \ref{subsec:impl}.  

\ac{BPF} was originally developed in 1992 by McCanne and Jacobson, as presented at the USENIX Winter Conference 1993 \cite{260309}.  
It was significantly extended in 2013 by Alexei Starovoitov, laying the foundation for \ac{eBPF}, as indicated in this patch thread \cite{ebpf}.  
\ac{eBPF} is the modern standard for \ac{BPF} and is also used in this work.  
However, the term \ac{BPF} will be used throughout this document, as it is common in the literature and sources, as described by Gregg in \cite[Chap.~1]{Gregg_2020}.  
Brendan Gregg has played a significant role in the dissemination and development of \ac{BPF}, as evidenced by his books \cite{Gregg_2020} and \cite{Gregg_2020a}.  

As Gregg explains in \cite{Gregg_2020}, writing \ac{BPF} code directly is very challenging.  
Therefore, various libraries exist to simplify this process.  
The two most prominent are \texttt{bcc} and \texttt{libbpf} for C++ and C, respectively.  
Using the tools \texttt{bcc} and \texttt{bpftrace}, \ac{BPF} can be utilized from the command line.  
These tools also internally rely on \texttt{libbpf} and \texttt{bcc}.  

\begin{figure}[H]
    \centering
     \includegraphics[width=\textwidth]{figures/BPF.drawio.pdf}
    \caption{Presentation of the working principle of Berkley Package Filter}
    \label{fig:bpf:working_principle}
\end{figure}

In this work, only the \texttt{libbpf-rs} library is used, and thus, the functionality and scope of these tools will not be further discussed.  
The \texttt{libbpf-rs} library is based on the \texttt{libbpf} library and serves as its Rust binding.  
Its exact functionality will be described in Section~\ref{subsec:impl}, as it is closely related to the implementation of the server and client.  
The following section provides a more detailed explanation of the functionality of \ac{BPF}.  

In Figure~\ref{fig:bpf:working_principle}, the working principle of \ac{BPF} is illustrated.  
The figure shows the various components of \ac{BPF} and their interactions.  
It also distinguishes where each component resides, either in the kernel or in user space.  
In Figure~\ref{fig:bpf:working_principle}, components that are directly connected to the \ac{BPF} workflow are depicted in grey.  
Configurations or interactions are represented in blue circles, while external Linux components are shown in yellow.  

The \ac{BPF} workflow begins with a \ac{BPF} program.  
As explained by Gbadamosi et~al.\ in \cite[p.~7]{gbadamosi2024ebpfruntimelinuxkernel}, this program is compiled using \texttt{clang}.  
For this compilation, the \texttt{bpf} target must be set.  
This process produces the \ac{BPF} bytecode, which is then loaded into kernel space via a userspace loader, such as one of the available libraries like \texttt{libbpf}, to the verifier.  
As described by Gbadamosi et~al.\ in \cite[p.~4]{gbadamosi2024ebpfruntimelinuxkernel}, the userspace loader employs the \texttt{BPF\_PROG\_LOAD} system call.  
Additionally, the necessary kernel hooks and maps are created and linked to the \ac{BPF} program.  

The verifier checks that the program does not perform any illegal operations and that the integrity and safety of the kernel are not compromised.  
As Gregg explains in \cite[Chap.~2.3.2]{Gregg_2020}, this verification not only detects disallowed instructions but also identifies bugs or other potential issues that could trigger a kernel panic or create security vulnerabilities.  
Unbounded loops are also disallowed, as a \ac{BPF} program must always terminate within a finite amount of time.  
The verifier relies on \ac{BTF} to ensure that the code is functional.  

As described by Gregg in \cite[Chap.~2.3.9]{Gregg_2020}, \ac{BTF} is generated by the Linux kernel and stored in the file \texttt{vmlinux.h}.  
In this work, \ac{BTF} was already generated via Yocto, as described in Section~\ref{subsec:yocto}.  
\ac{BTF} contains metadata and structure definitions for Linux kernel headers and all kernel \texttt{struct} types.  
Normally, this information is included with the Linux headers.  
However, in many cases, the \texttt{struct} definitions in the headers are incomplete or missing.  
As a result, a \ac{BPF} program that, for example, relies on a syscall whose return value is an undefined \texttt{struct}, would be rejected by the verifier.  

Beyond verification, \ac{BTF} also plays an important role in providing debugging information for \ac{BPF} programs.  
It is a compact, binary-encoded representation of type information, designed to be efficiently processed by both the kernel and user space tools.  
With \ac{BTF}, tools such as \texttt{bpftool} can inspect kernel data structures, and debuggers can provide symbolic names instead of raw memory addresses or offsets.  
\ac{BTF} forms the foundation for \ac{CO-RE}.  
In order for \ac{BPF} code to run anywhere after compilation, the used \texttt{struct} definitions must be precisely described in the \ac{BTF}.  
This information must be passed to both the userspace loader and the verifier.  
Since \ac{CO-RE} is not used in this work, it will not be described further here.

If the program is accepted by the verifier, it is either compiled by the \ac{JIT} compiler or executed by the interpreter.  
For the \ac{JIT} compiler to take over, it must be both supported and enabled, which is controlled via the \texttt{bpf\_jit\_enabled} operation.  
As described in \cite{jit}, this option can be enabled by writing the value "1" to the file \texttt{/proc/sys/net/core/bpf\_jit\_enable}.  

Like described by Gbadamosi et~al.\ in \cite[p.~4]{gbadamosi2024ebpfruntimelinuxkernel} the \ac{JIT} compiler translates the \ac{BPF} bytecode into native machine code for the running architecture at load time.  
This eliminates the overhead of interpreting instructions during execution and significantly improves performance, especially for programs that are invoked frequently or handle large volumes of events.  
 
If the \ac{JIT} compiler is not enabled or supported, the \ac{BPF} program is executed using the in-kernel \ac{BPF} interpreter.  
The interpreter processes each \ac{BPF} instruction sequentially, decoding and executing them in a virtualized manner.  
While this approach is slower due to per-instruction overhead, it ensures compatibility across architectures and provides a fallback execution path in environments where \ac{JIT} compilation is unavailable or undesired.  

Van~Geffen describes in \cite{10.1007/978-3-030-53291-8_29} a custom \ac{JIT} compiler that offers greater security than the Linux implementation.  
According to \cite[p.~566]{10.1007/978-3-030-53291-8_29}, this compiler achieves a performance improvement of 5.24$\times$ over the interpreter.  
However, it remains 1.82$\times$ slower than the Linux \ac{JIT} compiler.  
From these results, the performance gain of the Linux \ac{JIT} compiler over the interpreter can be calculated as $5.24 \times 1.82 = 9.53$.  
Since this difference is close to a factor of ten, and the monitoring overhead on the test system should be minimized, this work employs the Linux \ac{JIT} compiler.  

As described by Gregg in \cite[Chap.~2.3]{Gregg_2020}, once the \ac{BPF} code has been verified and translated into native instructions, it is executed within a virtual machine running in kernel space.  
Gregg notes in \cite[Chap.~2.3]{Gregg_2020} that, particularly after \ac{JIT} compilation, this virtual machine exists only as a specification.  
In contrast to the definition of a virtual machine provided by Bugnion in \cite{Bugnion2017}, where a virtual machine represents an abstraction of an entire computer system, the \ac{BPF} virtual machine is purely a specified execution model.  
According to Bugnion, a true virtual machine must virtualize the processor, memory, and I/O components.  
In the context of \ac{BPF}, as Fleming explains in \cite{ebpf_intro}, the term “virtual machine” refers solely to a logical \ac{CPU} specification with a fixed instruction set and ten registers, designed to run platform-independently within the kernel.  
Consequently, as Gregg observes, the \ac{BPF} virtual machine exists only in specification form.  
This is particularly true when the code has already been compiled into machine instructions.  
In such cases, these instructions are executed directly by the \ac{CPU}.  
During the runtime of a \ac{BPF} program, there is no additional abstraction layer between the \ac{CPU} and the executing code.  
A \ac{JIT} compiler and an interpreter exist, but there is no virtual machine in the traditional sense.  

Besides the 10 registers, the virtual machine also offers 512 bytes on the stack, as Gregg describes in \cite[Chap.~2.3]{Gregg_2020}.  

Additionally, more memory is available in so-called maps.  
These maps are created using the command \texttt{BPF\_MAP\_CREATE}, as described in \cite[p.~5]{gbadamosi2024ebpfruntimelinuxkernel}.  

As Gregg discusses in \cite[Chap.~2.2]{Gregg_2020}, \ac{BPF} programs can exchange data among each other threw using maps.  
Furthermore, the maps are synchronized, allowing parallel memory accesses.  
Maps can be accessed from userspace, providing a way to transfer collected data from the virtual machine back to userspace.  
Command-line tools such as \texttt{bpftrace} use these maps to display statistics, for example.  

As Gregg explains in \cite[Chap.~2.2]{Gregg_2020}, this has the advantage that no communication between user- and kernelspace is necessary.  
Since the program runs entirely in kernelspace at runtime, events can be filtered and processed there.  
Events or network packets can also be discarded in kernelspace if they are harmful or would endanger further processing in userspace due to their value ranges.  
Thus, the mechanism of maps and the virtual machine specified therein ensure security and efficiency by preventing unnecessary kernel-to-userspace interactions.  

As shown in Figure~\ref{fig:bpf:working_principle}, the event configuration from userspace interacts with the virtual machine in kernelspace.  
The event configuration particularly refers to the settings of command-line tools.  
Among other things, it can be configured which events should be tracked, for how long they should be tracked, and how they should be processed.  
Since command-line tools are not used in this work, the event configuration will not be discussed further here, but it is mentioned for completeness and illustrated in the figure.  

As shown in Figure~\ref{fig:bpf:working_principle}, the virtual machine provides another method for transferring data from the kernel to userspace.  

This is the ring buffer, which Gregg in \cite[Chap.~2.3]{Gregg_2020} also describes as the perf buffer.  
The buffer is used to continuously transfer data from the kernel to userspace.  
There are also other variants for sharing data between user and kernel space, including relayfs.  

RelayFS was developed by Tom Zanussi and has been integrated into the Linux kernel since 2003, as evident from the patch thread in \cite{relayfs}.  
As explained by Zanussi in \cite{Wisniewski2003relayfsA}, it is also a mechanism to efficiently transfer data from kernelspace to userspace.  
In this approach, a ring-shaped buffer is allocated per \ac{CPU}, which can be read from userspace using \texttt{mmap()}.  
This minimizes copy operations because both the kernel and userspace access the same memory region directly without intermediate data duplication.  
Writing to these buffers is performed sequentially by the kernel, while the userspace continuously reads and only updates the read pointers.  
As described in \cite[p.~498]{Wisniewski2003relayfsA}, it was originally introduced as a standalone filesystem under \texttt{/mnt/relay}.  
It is now integrated into the tracing subsystem and is used, among other things, by the kernel tracing tool LTTng, as described in \cite[p.~89]{Pierre}.  

Although RelayFS is older than perf and ring buffers, it still has use cases, as Fournier describes in \cite{Pierre}.  
Gregg and Calacera describe the functionality and usage of \ac{BPF} in great detail in their books \cite{Gregg_2020} \cite{Calavera_Fontana_Frazelle_2020}.  
However, neither of them mentions any method other than perf buffer and maps for exchanging data between user and kernel space.  
This tendency is reflected not only in theory but also in practice.

Nair et al. developed GAPP in \cite{Nair_2020}, a tool to identify serialization bottlenecks in parallel Linux applications.  
For monitoring, \ac{BPF} is also used, and maps and perf buffers are employed for data exchange between kernel and userspace.  
Another example is Liu et al., who built a protocol-independent network observability system in \cite{9359159}.  
Furthermore, both Kannan et al., presenting a network monitoring agent in \cite{network_obser}, and Gowda et al., proposing kernel-level request tracing for microservice visibility in \cite{V_2022}, use \ac{BPF} along with maps and perf buffers.

All these works utilize \ac{BPF} for monitoring and rely on maps and perf buffers for communication between kernel and userspace.  
These examples confirm, on one hand, that \ac{BPF} is widely used in network observability.  
On the other hand, it is evident that no alternative methods for kernel-user communication are employed in practice.  
This is likely because maps and perf buffers are well integrated with \ac{BPF} and offer excellent performance.  
As a result, the effort to integrate, for example, RelayFS with \ac{BPF} is not justified.  
Therefore, this work also relies on maps and perf buffers.

The modules not yet mentioned from Figure~\ref{fig:bpf:working_principle} are BPF helpers, events, and BPF syscalls.  
All of these are shown as yellow boxes, which, as explained earlier, indicates that they represent components, which do not belong fully to \ac{BPF}, but influence the execution of the \ac{BPF} program.  

As described by Gregg in \cite[Chap.~2.3.6]{Gregg_2020}, a \ac{BPF} program cannot execute arbitrary kernel functions.  
To enable access to information from the operating system context within the program, BPF helper functions are used.  
These are defined in the BPF API in \texttt{include/uapi/linux/bpf.h}, and new helpers are constantly being added.  
The BPF API in this context refers to the set of functions and interfaces that the kernel exposes to \ac{BPF} programs to interact with kernel and user space resources in a controlled manner.  
As illustrated in Figure~\ref{fig:bpf:working_principle}, these helpers can be invoked via the \texttt{bpf\_call} instruction.  

The following paragraphs present selected helper functions to provide an overview of their capabilities.  
Among these restricted kernel calls is \texttt{bpf\_ktime\_get\_ns()}, which returns the time since kernel start in nanoseconds.  
This enables access to a monotonic clock, allowing the measurement of time intervals between specific events at kernel level.  

Other important BPF helpers are \texttt{bpf\_get\_current\_pid\_tgid()} and \\
\texttt{bpf\_get\_current\_comm(buf, buf\_size)}.  
Each of these functions has a return value, which will be referred to as $R_1$ and $R_2$ in the following.  
$R_1$ returns both the TGID and the PID of the current process, where TGID (Thread Group ID) refers to the identifier of the process as a whole, and PID (Process ID) refers to the specific thread within that process.  
The 64-bit value returned by $R_1$ is composed such that the high 32 bits contain the TGID and the low 32 bits contain the PID.  
$R_2$ returns the current task name, also known as the command name (\texttt{comm}) of the process.  
With these two functions, process names and precise IDs can be determined both in user space and kernel space.  
This is important for filtering, and also for diagnostics when it is necessary to determine which process triggered a given event.  

Another essential kernel function accessible via helpers is \texttt{bpf\_trace\_printk}.  
As described in \cite{print}, this function can write print messages to the kernel trace log.  
It thus serves as the \texttt{printf} equivalent for \ac{BPF}.  
In contrast to C, where, as explained in \cite{printf}, messages are printed to the console, \texttt{bpf\_trace\_printk} writes them to \texttt{/sys/kernel/tracing/trace}, because \ac{BPF} applications have no console available.  
The messages can then be read via the \texttt{/sys/kernel/tracing/trace\_pipe} interface.  
This function therefore provides a fast way to add simple debugging output.

As illustrated in Figure~\ref{fig:bpf:working_principle}, beside \ac{BPF} helper funtions, also syscalls can be invoked from the \ac{BPF} virtual machine.  
These syscalls are specific to the \ac{BPF} environment and provide the same functionality as conventional syscalls, but operate differently.  

Syscalls have existed since the early 1980s, as evidenced by the first official Unix Programmer's Manual~\cite{bell}.  
As described by Tanenbaum in~\cite[p.~50--53]{Tanenbaum_2014}, syscalls constitute the programming interface for userspace programs to request services from the kernelspace.  
Thus, syscalls act as a mechanism for the userspace to interact with the kernelspace.  

According to Tanenbaum~\cite[p.~54--55]{Tanenbaum_2014}, syscalls can be divided into the four fundamental categories process management, file management, directory and file system management, and miscellaneous.  
System calls for process management include, among others, the \texttt{fork()} command, which creates a child process.  
The \texttt{open()} and \texttt{close()} system calls are used for file management to open or close a file.  
The \texttt{mkdir()} command creates a new directory and falls into the category of directory and file system management.  
The miscellaneous category contains everything that does not fit into the three categories mentioned above, such as the \texttt{chmod} system call, which modifies a file’s permissions by changing its protection bits.  

As described by Gregg in~\cite[Chap.~2.3.6]{Gregg_2020}, the \ac{BPF} syscall can be invoked via the code shown in listing \ref{lst:bpf_syscall}.

\begin{listing}[H]
\begin{minted}[fontsize=\small]{c}
int bpf(int cmd, union bpf_attr *attr, unsigned int size);
\end{minted}
\caption{BPF syscall interface}
\label{lst:bpf_syscall}
\end{listing}

The \texttt{cmd} parameter specifies the particular \ac{BPF} operation to be performed.  
It is an integer value provided through an enumeration.  
As Gregg describes it in \cite[Chap.~2.3.6]{Gregg_2020}, the \texttt{BPF\_PROG\_LOAD} enum value instructs the verifier to check a \ac{BPF} program and subsequently load it into the kernel.  
Similarly, maps can be accessed or modified from userspace using commands such as \texttt{BPF\_MAP\_CREATE} or \texttt{BPF\_MAP\_LOOKUP\_ELEM}.  

The key difference between conventional syscalls and the \ac{BPF} syscall is that there is only one syscall for the entire \ac{BPF} subsystem.  
Nevertheless, as explained above, this single syscall can provide multiple functionalities.  
In contrast, conventional syscalls are monofunctional, with one syscall per functionality.  
Thus, while traditional syscalls are monofunctional, the \texttt{bpf()} syscall is polyfunctional.  
Compared to traditional syscalls, \texttt{bpf()} does not directly implement a single syscall in the classical sense, but rather acts as a wrapper for the syscalls of the \ac{BPF} subsystem.  
However, the fundamental purpose of syscalls, to provide a communication interface between userspace and kernelspace, remains unchanged in the \ac{BPF} implementation.  

As shown in Figure~\ref{fig:bpf:working_principle}, events also interact with \ac{BPF}.  
As described by Gregg in~\cite[Chap.~1]{Gregg_2020}, the primary functionality of \ac{BPF} is to execute user-defined code in response to events.  
Therefore, the events shown in Figure~\ref{fig:bpf:working_principle} are among the most crucial components of the overall system.  
Like described by Gregg in \cite[Chap. 1]{Gregg_2020}, events can be divided into the two categories static and dynamic events.  
In Figure~\ref{fig:probes}, a software stack is illustrated.  
This illustration indicates, among other aspects, where specific static and dynamic events are located and which monitoring techniques can be used to observe them.

    \centering
    \includegraphics[width=\textwidth]{figures/Probes.drawio.pdf}
    \caption{Presentation of a software stack and selection of static and dynamic probes}
    \label{fig:probes}

In Figure~\ref{fig:probes}, only three monitoring techniques are distinguished: dynamic tracing, static tracing, and sampling.  
In the following the available monitoring techniques are discussed, their differences highlighted and it will be explained what a probe is and how probes can be classified.  

Gregg describes in \cite[Chap.~1.2]{Gregg_2020} that monitoring techniques serve the purpose of observability.  
He defines the term \emph{observability} as the ability to understand a system by means of monitoring tools.  

The term \emph{observability} was originally introduced in 1960 by Kalman in \cite{Klmn1960ContributionsTT}.  
He defines observability as the property that the internal state of a system at any given time can be completely determined from its outputs over a finite period of time.  

\begin{equation} \label{eq:obser}
x_{k+1} = A x_k + B u_k, \quad y_k = C x_k + D u_k,
\end{equation} 

For a given state-space system model like presented in equation \ref{eq:obser} the variable $x_k$ is the state vector of the system at time step $k$.
In equation \ref{eq:obser}, $u_k$ is the input vector at time step $k$,  
$y_k$ is the output vector at time step $k$,  
$A$ is describing the evolution of the internal state over time,  
while $B$ the input matrix describes how inputs affect the states,  
$C$ is the output matrix mapping the state $x_k$ to the measured outputs $y_k$,  
and $D$ is the feedthrough matrix describing any direct influence of the inputs on the outputs.  

According to Kalman \cite{Klmn1960ContributionsTT}, a system is observable if the \emph{observability matrix} shown in equation \ref{eq:matrix} has full rank, in other words \(\mathrm{rank}(\mathcal{O}) = n\), where \(n\) is the dimension of the state vector \(x_k\).  
The variables $A$ and $C$ in equation \ref{eq:matrix} have the same meaning, like in equation \ref{eq:obser}.
The product $C A^i$ describes how the output at time step $k+i$ depends on the initial state $x_k$.
To $i$ applies $i \in [0, n-1]$.
The observability matrix in equation \ref{eq:matrix} has one column for each state variable, in other words $n$ columns if $x_k \in \mathbb{R}^n$.
\begin{equation} \label{eq:matrix}
\mathcal{O} =
\begin{bmatrix}
C \\
C A \\
C A^2 \\
\vdots \\
C A^{n-1}
\end{bmatrix}
\end{equation}  

Full column rank ensures that each state variable can be uniquely determined from the output measurements.
The outputs must be multiplied by $A^i$ in each block $C A^i$ because the effect of the initial state on future outputs evolves over time according to the system dynamics.
This condition ensures that the current state $x_k$ can be fully reconstructed from the output measurements $y_k$.  

Nevertheless, Gregg's definition of observability does not deviate substantially from Kalman's original formulation.  
A system can only be fully understood if its internal state can be determined at all times from its outputs. 
Also Gregg's definition is more practical orientated, where the original definition is more orientatedto the theory.
In order for a system to produce outputs from which its internal state can be inferred, certain analysis techniques are required.  
Gregg categorizes these techniques in \cite[Chap.~1.2]{Gregg_2020} into \emph{tracing}, \emph{snooping}, \emph{sampling}, and \emph{profiling}.  

Tracing, as described by Gregg in \cite[Chap.~1.2]{Gregg_2020}, refers to recording the system state based on events.  
There are various tools in the Linux context that enable tracing, such as \texttt{strace} \cite{strace} or \texttt{top}.  
According to Gregg, \texttt{top} internally also works with events and subsequently outputs a summary of the information extracted from these events to the console.  
From this, it follows that tracers must, on the one hand, be capable of detecting events, and, on the other hand, also be able to read their metadata in order to fully understand their context.  
Furthermore, since events can occur very frequently, the overhead of a tracer must remain low; otherwise, the system would be significantly impaired.  

As Gregg explains in \cite[Chap.~1.2]{Gregg_2020}, snooping is very similar to tracing.  
It also describes the observation of events.  
Snooping was introduced in 1983 by Ravishankar and Goodman in \cite{osti_5139336}.  
They presented a bus snooping technique that monitors a memory block stored across multiple caches and informs other caches when this memory block has been modified.  
This approach avoids cache incoherency.  
Therefore, the difference between snooping and tracing lies less in functionality and more in their objectives.  
Snooping is generally a passive observation with occasional reactions, whereas tracing often aims to thoroughly analyze and record a specific area of the system.
