\chapter{Test Environment} \label{sec:implementation}
In this chapter, the test environment is examined in more detail.
In the following, the terms test environment, test system and \ac{OS} are used. 
The test environment comprises both the test system and the \ac{OS}. 
The test system refers exclusively to the applications that are part of the test environment and run on top of the \ac{OS}. 
Accordingly, the test system does not include the underlying hardware or the \ac{OS} itself.

\section{Requirements}
In this section, the requirements of the test environment are analyzed in greater detail. 
The discussion begins with a description of the system architecture, followed by an outline of general real-time requirements. 
These are then used to define the specific requirements applicable to the test system.

The test environment is illustrated in Figure \ref{fig:pi_wifi_general}. 
It consists of two Raspberry Pi 5 devices, as described in \ref{sec:used_hardware}. 
One Raspberry Pi acts as the server, while the other functions as the client. 
Both devices run the same \ac{OS}.

There are two communication links between the server and the client.
One link which transfers real-time-data and another one for transferring bulk data.
These two links are illustrated in Figure \ref{fig:pi_wifi_general} in blue and red.
These connections are handled by separate processes but operate within the same network. 
The server provides an \ac{AP} to which the client connects.
So an exclusive Wi-Fi network is used in this work.

In summary, the goal of the test environment is to transmit both real-time-data and bulk-data\footnote{The bulk-data does not have any real-time constraints.} over the same wireless network interface. 
While the bulk data throughput should be maximized, the primary focus is to ensure that no real-time violations occur on the real-time connection.

Since the test system is intended to transmit real-time-data among normal data, it must fulfill the requirements of a \ac{rt-system}. 
Therefore, the following section first outlines the general requirements of \acp{rt-system}. 
Subsequently, additional requirements that go beyond standard real-time criteria and are specifically relevant for this system within the given test environment are discussed in more detail.

\subsection{Real Time Requirements}
To enable a system to achieve real-time capability, numerous factors must be considered. 
In this work, only software-related requirements are considered.
Since Wi-Fi is an interface that is not inherently real-time capable, hardware-related requirements would have minimal impact in this context while significantly broadening the scope of the thesis.

As previously mentioned in Chapter \ref{sec:real_time}, the primary objective of a real-time system is predictability. 
According to Buttazzo \cite[p. 10]{Buttazzo_2024}, predictability can only be achieved if the system ensures timeliness, meaning that the value of a process depends not only on its correct output but also on its timely execution—specifically, meeting deadlines.

To fulfill these requirements, the \textbf{software foundation}, particularly the \ac{OS} kernel, must be tailored to real-time needs.
Key aspects include preemptiveness, scheduling, inter-task synchronization, inter-task communication, memory management, interrupt handling and timers.
The necessity for these mechanisms to be implemented differently in real-time capable kernels compared to non-real-time ones is discussed in detail in Chapter \ref{subsec:real_time_kernel} and will therefore not be reiterated here.

However, these mechanisms must not only be real-time capable at the kernel level—they also need to be considered during the \textbf{development of applications} intended to operate in a real-time context. 
As Buttazzo outlines in \cite[p. 13 - 20]{Buttazzo_2024}, particular attention must be paid to the choice of programming language, memory usage and synchronization and communication between processes.
It follows that, as shown in Figure \ref{fig:requirements}, memory management, inter-task communication and inter-task-synchronization are not only requirements for the \ac{OS}, but must also be taken into account in the test system.

In \cite[p. 17, 18]{Buttazzo_2024} Buttazzo emphasizes that the choice of programming language for real-time systems should avoid the use of dynamic data structures and recursion. 
This is because dynamic memory allocation and deallocation introduce unpredictability in execution time, making it impossible to determine the program's timing behavior in advance. 
Therefore, memory must be allocated statically and prior to execution. 
Similarly, recursion poses a challenge, as it is difficult to predict the amount of memory required and the number of recursive calls during runtime.

Furthermore, Buttazzo argues that a programming language suitable for real-time applications should support bounded loops, meaning that the number of iterations is fixed and known at compile time. 
In general, programming languages for real-time systems should offer the capability to explicitly define timing constraints and ensure adherence to the aforementioned principles—ideally enforcing them.
As programming languages, Buttazzo suggests \texttt{Real-Time Concurrent C} and \texttt{Real-Time Euclid}, both of which fulfill all the stated requirements.

By contrast, Michael P. Rooney et al. describe in \cite[p. 1]{10321761} a study involving the development of a \ac{SCADA} real-time application implemented in the four different programming languages C, Rust, Numba Python and Cython.
All of these languages were successfully used to achieve real-time performance. 
Notably, Rust demonstrated a power consumption profile comparable to C, indicating similar efficiency.

While the characteristics outlined by Buttazzo are not mandatory in any of these languages, they can be implemented with appropriate discipline and design. 
Thus, these languages are also suitable for real-time application development, provided that the specific constraints related to memory management, recursion and timing predictability are consciously observed and enforced by the developer, as they are not inherently guaranteed by the language itself.

The chosen programming languages and specific implementation-level requirements for achieving real-time capability and how these are addressed, are discussed in detail in Chapter \ref{subsec:impl}.

Furthermore, the test system must be capable of transmitting both real-time and bulk data concurrently over the same network, with the real-time traffic maintaining a \ac{RTT} as low as possible. 
This timing constraint stems from the fact that this work seeks to characterize Wi‑Fi’s real-time capabilities and the factors that influence them and to assess whether Wi‑Fi can be employed in an industrial real-time environment. 
The lower the achievable real-time capable \ac{RTT}, the wider the range of industrial applications in which Wi-Fi could be employed. 
This is because the requirements in industrial environments can vary substantially, resulting in different levels of real-time constraints.
These belong in one hand, to the duration of \ac{RTT} and in the other, the overall degree of real-time capability that a system must provide.

\subsection{Requirements of the Test Environment} \label{subsec:requirements}
The following section defines the requirements for the test environment which are shown in yellow in Figure \ref{fig:requirements}.
For both the test system and the \ac{OS}, the previously defined criteria for real-time capability are assumed to be fulfilled.

The requirements for the \ac{OS} include providing appropriate \textbf{support for both the hardware and the software components} of the test environment. 
As described in Chapter \ref{sec:used_hardware}, this work utilizes a Raspberry Pi 5, to which a MediaTek 7925B22M and an Atheros \texttt{AR5BXB92} Wi-Fi module can be connected via PCIe.
Accordingly, the \ac{OS} has to support the Raspberry Pi 5 architecture and offer compatibility with the drivers mt76, mt7925e and ath9k.

Furthermore, the mt7925e driver is only available starting from Linux kernel version 6.8 and receives extended feature support with newer versions. 
These enhancements primarily concern functionality related to Wi-Fi 6E and Wi-Fi 7, which is described in \cite{mt76}. 
Since these standards are also within the scope of this work, the \ac{OS} should support the most recent possible version of the mt7925e driver to ensure full access to these capabilities.

In addition to hardware compatibility, the \ac{OS} must also ensure compatibility with the required software components. 
This includes the availability of essential programming languages, user space networking and diagnostic tools which are necessary to run the test-system.

Moreover, the \textbf{\ac{OS} should be as minimal as possible}, containing only the components explicitly required for the test environment. 
This reduces background activity and minimizes potential sources of interference or error, thereby ensuring a more stable and predictable testing environment.

In addition to the \ac{OS}, the test system also has \textbf{non‑real‑time requirements}.
These are highlighted in yellow under “Test System” in Figure \ref{fig:requirements}. 
The application under test must be instrumented so that its real-time performance can be measured accurately, enabling meaningful conclusions to be drawn. 
This requires comprehensive monitoring and debugging facilities to precisely identify and isolate any sources of real-time violations.

For the non‑real‑time traffic, as much data as possible should be transmitted without degrading the real-time application’s performance. 
This means, only throughput and packet‑loss metrics need be considered for this traffic in the monitoring.

Moreover, this study will compare the real-time performance of the algorithms underpinning different Wi‑Fi standards. 
For that, the server must support \acp{AP}  for Wi-Fi 4, 5 and 6 across all relevant frequency bands (2.4 GHz, 5 GHz and 6 GHz). 
The impact of QoS on real-time capability will also be evaluated, so the test system must be able to mark network packets with QoS parameters. 
Given the large number of combinations of Wi‑Fi standards, frequency bands and QoS settings, an automated test framework is required to generate a comprehensive dataset for all test cases, from which reliable insights can be derived.

In this chapter, the requirements for the test environment were defined. 
The following sections will discuss how these requirements are implemented. 
The focus will first be on the selection and configuration of the \ac{OS}, because it forms the foundation of the test environment after the choice of hardware.

\section{Operating System} \label{sec:os}
As discussed in the previous chapter, the selection of an appropriate \ac{OS} must primarily consider its real-time capabilities. 
Such \acp{OS} are referred to as \acp{RTOS}. 
There exists a wide variety of \ac{RTOS}, each differing in architecture, strengths and limitations.
The following section compares the advantages, disadvantages and performance characteristics of selected \acp{RTOS}. 
Furthermore, their suitability for the purpose of this work is evaluated.

\subsection{Selection of Operating System}
The \ac{RTOS} that is used in this work is RT-Linux.
It is one of the \acp{RTOS} that imposes almost no restrictions in terms of performance and compatibility compared to a general-purpose \ac{OS}.
As described by Sampath et al. in \cite{Sampath_2007}, RT-Linux is a Linux-based system enhanced through the PREEMPT\_RT patch, which equips it with real-time capabilities. 
The authors examine the use of RT-Linux on an industrial controller with strict real-time requirements and additional real-time Ethernet demands. 
Their study demonstrates the suitability of RT-Linux for such applications, reporting a maximum jitter of 380 microseconds over a 24-hour endurance test.

Similarly, Arshiabanu \cite{ARSHIABANU_2014} presents a real-time system implemented using RT-Linux. 
The study evaluates the impact of various scheduling policies on real-time performance and is executed on a Raspberry Pi. 
Dewit et al. \cite{ae11aecebd4e4fd6896d0b8bb93fa73a} further investigate the influence of RT-Linux in combination with a Raspberry Pi 5 on scheduling latencies, reporting a maximum scheduling latency of 125 microseconds.
This study is especially relevant for this work, because it uses the same hardware platform.

Despite these studies, there also are more critical perspectives. 
Siro Arthur et al. \cite{Siro_2007} also evaluated real-time capabilities of RT-Linux. 
This study analyzes metrics such as context switch time, memory access latency and TCP latency. 
The study reveals that while the PREEMPT\_RT patch enhances real-time capabilities, it does not reach the same level of determinism as systems natively designed for real-time applications. 
Furthermore, this analysis was performed on single-core CPUs, where reduced shared resources can change the real-time behavior. 

There are also studies with multicore platforms which question the suitability of RT-Linux for hard real-time environments. 
Carvalho et al. \cite{9018464} investigated RT-Linux running on a Raspberry Pi, focusing on latency metrics such as polling, timed loops, hardware interrupts and software interrupts. 
Their results confirm that although RT-Linux offers certain real-time properties, it should only be used in non-critical real-time environments. 
This conclusion is supported by Betz et al. \cite{5347056}, who state that RT-Linux is appropriate for soft real-time applications.

Yang et al. \cite{10870260} compare the real-time performance of NuttX, FreeRTOS, RT-Linux and Xenomai. 
A noteworthy aspect of their study is the inclusion of both real-time capabilities and general-purpose features. 
While RT-Linux can be used as a standalone system, to match these requirements, pure \acp{RTOS} like FreeRTOS and NuttX are executed alongside a general-purpose \ac{OS}. 
Also in this study a Raspberry Pi 4 was used as the hardware platform. 
The results are showing that pure \ac{RTOS}, especially FreeRTOS, nevertheless deliver better real-time performance.

In summary, the optimal \ac{RTOS} depends heavily on the specific application and real-time requirements. 
Based on the referenced studies, FreeRTOS appears to offer the best real-time capabilities. 
However, additional constraints beyond real-time performance must be considered when selecting the \ac{OS}, like stated in the previous section.
This means particularly hardware compatibility of the \ac{OS}. 
The MediaTek 7925B22M Wi-Fi card used in this work lacks drivers outside the Linux ecosystem, thereby excluding FreeRTOS as a viable option.

Considering the experience with RT-Linux on Raspberry Pi systems stated by the studies before and the demonstrated maximum scheduling latency of 125 microseconds along with a maximum jitter of 380 microseconds of the test-system, RT-Linux proves sufficient for the purposes of this work. 
This jitter is considered acceptable, since the expected \ac{RTT} is in the range of several milliseconds. 

As described by Rostedt in \cite{rt_patch}, a  RT-Linux system can be created by extending the kernel with the $PREEMPT\_RT$ patch. 
This results in two primary approaches for building an RT-Linux system. 
One can either use an existing Linux distribution such as Ubuntu and apply the $PREEMPT\_RT$ patch, or build a complete Linux system from scratch using a build system.

As Vasquez outlines in \cite[Chap. 6]{10163343}, building an \ac{OS} using a build system offers the advantage of full customization tailored to specific needs. 
Every component of the \ac{OS} can be configured and assembled individually. 
However, this method is considerably more time-consuming compared to using a pre-built \ac{OS} that is already available for the Raspberry Pi 5, such as a customized Ubuntu version 24.02 or Raspberry Pi OS, which can then be extended with the $PREEMPT\_RT$ patch.

Due to the requirements defined in Chapter \ref{subsec:requirements}, the \ac{OS} must be capable of providing a foundation for both software and hardware. 
For the Wi-Fi card drivers, it is essential, as previously mentioned, that the kernel is as recent as possible. 
The kernel version can only be adapted with a reasonable effort, in the existing \acl{OS} for the Raspberry Pi 5.
A build system has a possibility, to do this more easily.
Moreover, certain kernel configurations must be set to support integration of these drivers. 
These configurations can be managed much more flexibly and conveniently using a build system. 
For this reason, the \ac{OS} used in this work is built using a build system.

Furthermore, an \ac{OS} built using a build system is the preferred choice for embedded systems, as noted by Navik in \cite{8008968}. 
This assertion is supported by Vasquez in \cite[Chap. 6]{10163343}, who argues that the main advantages lie in the minimal footprint and the ability to restrict applications and background processes as needed. 
Given that the requirements for the embedded system in this work also include reproducibility and minimal external interference, this further supports the decision to use a build system for the \ac{OS}.

As Salvador describes in \cite[Chap. 1]{10251255}, the Yocto Project is a widely used and powerful build system. 
It is open-source and comes with excellent documentation, making it a suitable choice for building the \ac{OS} in this work.

The technical details of how the Yocto Project functions were already covered in Chapter \ref{subsec:yocto}. 
Since all technologies used in the test system must be known for proper \ac{OS} configuration, the following chapter will provide a more detailed overview of the test setup.

\section{Structure of Test Environment}
Figure \ref{fig:technologies} illustrates the test environment along with all relevant components and technologies. 
As previously described, it consists of a server and a client. 
First, the structure of the test system is explained in more detail, followed by an analysis of how it satisfies the requirements defined in Section \ref{subsec:requirements}.

The test environment in Figure \ref{fig:technologies} is divided into several elements. 
The \ac{OS} is excluded from the discussion and the focus is placed solely on the components of the test system.

The server part of the test system is controlled via the \textbf{Server Test Suite}, which is responsible for executing \texttt{test runs} and automating the overall testing process. 
For the evaluation of real-time performance, the factors \textbf{Wi-Fi standard, frequency, bandwidth, \ac{QoS}} and \textbf{protocol} are considered in Chapter~\ref{sec:eval}.
Therefore, these factors must be configurable within the test suite.
The Wi-Fi standard, frequency and bandwidth are set through the \ac{AP} configuration, whereas \ac{QoS} and the protocol type are configured within the test suite itself.
The \texttt{Server Test Suite} is essential for the automated execution of these \texttt{test runs}, thereby fulfilling the previously specified requirement for test automation.

\begin{figure}[ht]
    \centering
     \includegraphics[width=\textwidth]{figures/Technologien_Testsystem.drawio.pdf}
    \caption{Visualization of the test environment including used technologies.}
    \label{fig:technologies}
\end{figure}

A \textbf{server-side test run} comprises the three components \texttt{hostapd}, \texttt{Iperf Bulk Server} and \texttt{Rust-RT Server}. 
Each \texttt{test run} contributes to the overall test automation by ensuring that the required steps to establish both a real-time and a non-real-time network link within the same network are executed in the correct order.

The first step in a server-side \texttt{test run} is the creation of the \ac{AP}, which is achieved using the \textbf{Hostapd} software. 
\texttt{Hostapd} allows the configuration of various Wi-Fi standards, frequencies and bandwidths, thereby meeting the requirement to support multiple Wi-Fi standards.

Once the \ac{AP} is established, the server for non-real-time applications is launched using \textbf{Iperf3}. 
This software supports differentiation between UDP and TCP traffic, various packet sizes and data rates. 
It also provides metrics such as packet loss and jitter, thus fulfilling all previously defined requirements for bulk data transmission.

Finally, the \textbf{Rust-RT Server} is started. 
This component is implemented in Rust and makes use of \ac{BPF}. 
This enables both compliance with real-time requirements and integrated monitoring capabilities. 
The rationale behind the choice of programming languages is discussed after the explanation of the test system architecture in Section \ref{subsec:used_technologies}.

The \textbf{client-side test system} is structurally similar to the server-side system. 
As shown in Figure \ref{fig:technologies}, it also consists of a \texttt{Client Test Suite} and a \texttt{test run}. 
The functionality of the client-side test suite and \texttt{test run} mirrors that of the server-side system. 
However, the client-side \texttt{test run} differs slightly in structure.

The client-side \texttt{test run} comprises two phases. 
First, a connection to the server’s \ac{AP} must be established. This is handled using the \textbf{$wpa\_supplicant$} software, which utilizes a configuration file specifying details such as the network password and encryption algorithm. 
For this reason, client and server \texttt{test runs} must be synchronized.
Any mismatch in Wi-Fi standards will prevent the client from connecting to the server’s \ac{AP}.

Once a connection is established, the \textbf{Rust-RT Client} is launched. 
This client establishes a connection to the \texttt{Rust-RT Server}. 
Unlike the server-side \texttt{test run}, the \texttt{Iperf Bulk Client} is not launched directly as part of the \texttt{test run} but is instead initiated from within the \texttt{Rust-RT Client}. 
The reason for this design choice is explained in more detail in Section \ref{subsec:impl}.

After describing the architecture and functionality of the test system and how it satisfies the specified requirements, the following section discusses the selection of technologies and their configuration within the Yocto environment.

\section{Used Technologies} \label{subsec:used_technologies}
To create an \ac{AP} on the server, the software \texttt{hostapd} is used, as previously described.  
As Anderson states in \cite{hostapd}, this is one of the most widely used tools to create an AP that can be configured in detail.  
With this software, the Wi-Fi standard, frequency, bandwidth and encryption can be configured, as shown in \cite{hostapd2}.  
Thus, all previously specified requirements regarding the configurable properties of the Wi-Fi are met by this software.  

To allow the client to connect to the AP, the software \texttt{wpa\_supplicant} is used.  
As shown in \cite{hostapd2} and \cite{wpa}, it can be configured at the same level as \texttt{hostapd}.  
This allows for a fine-grained configuration of the connection to the AP.  
An alternative on Linux would be the \texttt{NetworkManager}.  
However, it includes more background processes and is therefore more heavyweight, which would impact the system more strongly.  
Moreover, it cannot be configured as precisely in coordination with \texttt{hostapd} as \texttt{wpa\_supplicant}.  

To generate network traffic, \texttt{iperf3} is used, as it fulfills the required specifications, as previously described.  
As shown in \cite{iperf}, this tool allows the generation of network traffic and precise configuration regarding TCP/UDP, packet size and throughput.  
Furthermore, no separate monitoring needs to be developed, as the tool already includes it.  
For example, latency and packet loss can be directly observed using \texttt{iperf3}.  

Both the \texttt{Server Test Suite} and the \texttt{Client Test Suite} are implemented in Python.  
This is possible because there are no real-time requirements for these components.  
Only the server responsible for the RT connection must fulfill real-time constraints.  
In this case, Python is a suitable choice because, as described in \cite{10209340}, it is very popular and widely used in embedded programming.  
Moreover, the language offers a high level of abstraction and is script-like in nature.  
Since the test suites only need to coordinate the testing processes, the script-based nature of Python is well-suited for this task.  

In contrast to the test suite, the RT server and client must fulfill real-time characteristics.  
As described by DLR in \cite[p. 86]{dlr212971}, most embedded real-time applications are written in C or C++.  
Nevertheless, Rust was chosen for the RT application in this work.  
This decision is based on the fact that DLR also states in \cite{dlr212971} that Rust is more suitable for RT applications due to its memory and thread safety.  
However, the language is still too young to be fully established for hard real-time systems.  

Rust does not use a garbage collector, as explained in \cite[p. 2]{10.5555/3563572.3563603}.  
Nevertheless, it prevents issues such as use-after-free, null pointer dereferencing and data races.  
This is achieved through Rust's ownership system.  
Ownership in Rust means that each value has exactly one owner, which becomes invalid once the owner goes out of scope.  
An owner can be a variable, function, or data structure that holds the exclusive right to access or modify a value.  
This mechanism also prevents undefined behavior.  

Furthermore, as described in \cite[p. 1]{10.5555/3563572.3563603}, Rust offers better development capabilities due to \texttt{rustc} and zero-cost abstractions.  
\texttt{rustc} allows better debugging and significantly eases troubleshooting.  
Rust provides better error messages than C and benefits from zero-cost abstractions.  
Additionally, as shown in \cite[p. 1]{10321761}, Rust performs similarly to C.  

Rust is also becoming increasingly popular, as noted in \cite[p. 2]{dlr212971}.  
This is also evident in its adoption into the Linux kernel due to its strong memory safety.  
As described by Panter in \cite{10.1145/3674805.3690756}, this integration has already shown promising results.  
Rust has also been integrated into Android for memory safety reasons.  
As described in \cite[p. 1]{seidel2024bringingrustsafetycriticalsystems}, the share of safety vulnerabilities was reduced from 76\% to 35\%.  

Moreover, increasing progress is being made in the field of real-time applications with Rust.  
As shown in \cite{Rust_Foundation}, the Safety-Critical Rust Consortium was founded in 2024 with the goal of using Rust in DO-178C-certified products.  
As described in \cite{do178} and \cite[p. 4]{seidel2024bringingrustsafetycriticalsystems}, this is one of the strictest certifications for airborne systems.  

In summary, Rust is well-suited for real-time applications and offers better development capabilities than C and C++.  
It is also becoming increasingly popular and has almost no performance disadvantages compared to C.  
Accordingly, the RT application in this work is written in Rust.  

To implement monitoring of the real-time application, \ac{BPF} is used.  
It can be seamlessly integrated into Rust code using \texttt{libbpf-rs}.  
\ac{BPF}, is a technology for efficient in-kernel data processing and monitoring, originally designed for packet filtering.  
As described by Gregg in \cite[Chap. 2.10]{Gregg_2020}, it was originally build to observe network packages.
And it offers nearly the same functionality as the widely used profiling tool \texttt{perf}.  
Furthermore, it is also employed in practice for network monitoring.
This is evident in \cite{network_obser} and \cite{9359159}.
However, it integrates better with Rust and is more flexible due to its scriptability and access to a broader range of event sources than \texttt{perf}.  
BPF supports more event sources such as tracepoints, \acp{kprobe}, \acp{uprobe} and performance counters, enabling more detailed and application-specific monitoring.  

In summary, the programming languages Python, Rust and BPF, as well as the tools \texttt{hostapd}, \texttt{iperf3} and \texttt{wpa\_supplicant}, must be provided by the \ac{OS} for the test system.  
The following section describes how this can be realized using the Yocto Project.

The background and functionality of the Yocto Project have already been described in Section~\ref{subsec:yocto}.  
Therefore, this section does not elaborate on them further and proceeds directly with the specific implementation within the context of this thesis.

All layers are built using Yocto version 5.2.1.  
This corresponds to the \texttt{walnascar} branch.  
As of in the mid of June, this was, besides the \texttt{master} branch, the most recent branch of the Yocto Project, as shown in~\cite{yocto-releases}.  
The latest branch was selected to take advantage of the most up-to-date kernel version included therein.  

The kernel version is crucial for the support of the \texttt{mt7925e} driver, which is only available starting from kernel version 6.8 and is better supported in even newer kernel releases, as described in~\cite{mt76}.  
The \texttt{walnascar} branch was available for all layers except for the \texttt{meta-rust} layer.  
In this case, it was necessary to manually add the \texttt{walnascar} branch to the \texttt{layer.conf} file.  

Due to compatibility issues, the variable \texttt{RUST\_LIBC} in this layer had to be replaced with \texttt{\$\{@d.getVar('RUST\_LIBC').lower()\}}.  
This variable also needed to be defined in the \texttt{local.conf} file using \texttt{RUST\_LIBC = "gnu"}.  
The GNU C Library was chosen because it is the default C library used in full-featured distributions for the Raspberry Pi.

\texttt{local.conf} must also define the target machine to be the Raspberry Pi 5.  
This ensures proper activation of the \texttt{meta-raspberrypi} layer.

As can be seen in Figure \ref{fig:yocto_own}, the custom \texttt{meta-masterthesis} layer is assigned a higher priority (10) than the other layers in \texttt{bblayers.conf}.  
This is necessary to ensure that the \texttt{.bbappend} files within this layer are processed before the corresponding \texttt{.bb} files of other layers.  
The \texttt{meta-masterthesis} layer can be divided into four recipe categories, illustrated in purple in Figure~\ref{fig:yocto_own}.  
The individual \texttt{.bb} and \texttt{.bbappend} files are depicted in light green in the same figure.

The Wi-Fi cards used in this work utilize 32-bit DMA addressing.

\texttt{meta-raspberrypi/conf/machine/include/rpi-base.inc}.  
After this adjustment, the overlay was successfully deployed and referenced in the \texttt{config.txt} of the generated image.

To make the \ac{OS} real-time capable, the Linux kernel must be extended using the RT-patch.

It is also essential to modify the kernel configuration to select the appropriate preemption model.

This ensures that the final kernel included in the image is real-time capable.

The main component of \texttt{recipes-core} is the custom image recipe.

\texttt{core-image} to include all necessary technologies for the test system.

Once all technologies are installed on the target system, the final step is to integrate the application code and network configurations.  
This is done in the \texttt{recipes-connectivity} section.  
In the \texttt{network} category, marked in orange in Figure~\ref{fig:yocto_own}, two \texttt{.bbappend} files customize the configurations of \texttt{dnsmasq} and \texttt{dhcpcd}.

\subsection{Berkley Package Filter} \label{subsec:bpf}
\ac{BPF} was originally developed in 1992 by McCanne and Jacobson, as presented at the USENIX Winter Conference 1993 \cite{260309}.  
It was significantly extended in 2013 by Alexei Starovoitov, laying the foundation for \ac{eBPF}, as indicated in this patch thread \cite{ebpf}.  
\ac{eBPF} is the modern standard for \ac{BPF} and is also used in this work.  
However, the term \ac{BPF} will be used throughout this document, as it is common in the literature and sources, as described by Gregg in \cite[Chap.~1]{Gregg_2020}.  
Brendan Gregg has played a significant role in the dissemination and development of \ac{BPF}, as evidenced by his books \cite{Gregg_2020} and \cite{Gregg_2020a}.  

As Gregg explains in \cite{Gregg_2020}, writing \ac{BPF} code directly is very challenging.  
Therefore, various libraries exist to simplify this process.  
The two most prominent are \texttt{bcc} and \texttt{libbpf} for C++ and C, respectively.  
Using the tools \texttt{bcc} and \texttt{bpftrace}, \ac{BPF} can be utilized from the command line.  
These tools also internally rely on \texttt{libbpf} and \texttt{bcc}.  

\begin{figure}[H]
    \centering
     \includegraphics[width=\textwidth]{figures/BPF.drawio.pdf}
    \caption{Illustration of the working principle of Berkley Package Filter}
    \label{fig:bpf:working_principle}
\end{figure}

In this work, only the \texttt{libbpf-rs} library is used, and thus, the functionality and scope of these tools will not be further discussed.  
The \texttt{libbpf-rs} library is based on the \texttt{libbpf} library and serves as its Rust binding.  
Its exact functionality will be described in Section~\ref{subsec:impl}, as it is closely related to the implementation of the server and client.  
The following section provides a more detailed explanation of the functionality of \ac{BPF}.  

In Figure~\ref{fig:bpf:working_principle}, the working principle of \ac{BPF} is illustrated.  
The figure shows the various components of \ac{BPF} and their interactions.  
It also distinguishes where each component resides, either in the kernel or in user space.  
In Figure~\ref{fig:bpf:working_principle}, components that are directly connected to the \ac{BPF} workflow are depicted in grey.  
Configurations or interactions are represented in blue circles, while external Linux components are shown in yellow.  

The \ac{BPF} workflow begins with a \ac{BPF} program.  
As explained by Gbadamosi et~al.\ in \cite[p.~7]{gbadamosi2024ebpfruntimelinuxkernel}, this program is compiled using \texttt{clang}.  
For this compilation, the \texttt{bpf} target must be set.  
This process produces the \ac{BPF} bytecode, which is then loaded into kernel space via a user space loader, such as one of the available libraries like \texttt{libbpf}, to the verifier.  
As described by Gbadamosi et~al.\ in \cite[p.~4]{gbadamosi2024ebpfruntimelinuxkernel}, the user space loader employs the \texttt{BPF\_PROG\_LOAD} system call.  
Additionally, the necessary kernel hooks and maps are created and linked to the \ac{BPF} program.  

The verifier checks that the program does not perform any illegal operations and that the integrity and safety of the kernel are not compromised.  
As Gregg explains in \cite[Chap.~2.3.2]{Gregg_2020}, this verification not only detects disallowed instructions but also identifies bugs or other potential issues that could trigger a kernel panic or create security vulnerabilities.  
Unbounded loops are also disallowed, as a \ac{BPF} program must always terminate within a finite amount of time.  
The verifier relies on \ac{BTF} to ensure that the code is functional.  

As described by Gregg in \cite[Chap.~2.3.9]{Gregg_2020}, \ac{BTF} is generated by the Linux kernel and stored in the file \texttt{vmlinux.h}.  
In this work, \ac{BTF} was already generated via Yocto, as described in Section~\ref{subsec:yocto}.  
\ac{BTF} contains metadata and structure definitions for Linux kernel headers and all kernel \texttt{struct} types.  
Normally, this information is included with the Linux headers.  
However, in many cases, the \texttt{struct} definitions in the headers are incomplete or missing.  
As a result, a \ac{BPF} program that, for example, relies on a syscall whose return value is an undefined \texttt{struct}, would be rejected by the verifier.  

If the program is accepted by the verifier, it is either compiled by the \ac{JIT} compiler or executed by the interpreter.  
For the \ac{JIT} compiler to take over, it must be both supported and enabled, which is controlled via the \texttt{bpf\_jit\_enabled} operation.  
As described in \cite{jit}, this option can be enabled by writing the value \texttt{1} to the file\\
\texttt{/proc/sys/net/core/bpf\_jit\_enable}.  

Like described by Gbadamosi et~al.\ in \cite[p.~4]{gbadamosi2024ebpfruntimelinuxkernel} the \ac{JIT} compiler translates the \ac{BPF} bytecode into native machine code for the running architecture at load time.  
This eliminates the overhead of interpreting instructions during execution and significantly improves performance, especially for programs that are invoked frequently or handle large volumes of events.  
 
If the \ac{JIT} compiler is not enabled or supported, the \ac{BPF} program is executed using the in-kernel \ac{BPF} interpreter.  
The interpreter processes each \ac{BPF} instruction sequentially, decoding and executing them in a virtualized manner.  
While this approach is slower due to per-instruction overhead, it ensures compatibility across architectures and provides a fallback execution path in environments where \ac{JIT} compilation is unavailable or undesired.  

Van~Geffen describes in \cite{10.1007/978-3-030-53291-8_29} a custom \ac{JIT} compiler that offers greater security than the Linux implementation.  
According to \cite[p.~566]{10.1007/978-3-030-53291-8_29}, this compiler achieves a performance improvement of 5.24$\times$ over the interpreter.  
However, it remains 1.82$\times$ slower than the Linux \ac{JIT} compiler.  
From these results, the performance gain of the Linux \ac{JIT} compiler over the interpreter can be calculated as $5.24 \times 1.82 = 9.53$.  
This work employs the \ac{JIT} compiler, since it performs significantly better.

As described by Gregg in \cite[Chap.~2.3]{Gregg_2020}, once the \ac{BPF} code has been verified and translated into native instructions, it is executed within a virtual machine running in kernel space.  
Gregg notes in \cite[Chap.~2.3]{Gregg_2020} that, particularly after \ac{JIT} compilation, this virtual machine exists only as a specification.  
In contrast to the definition of a virtual machine provided by Bugnion in \cite{Bugnion2017}, where a virtual machine represents an abstraction of an entire computer system, the \ac{BPF} virtual machine is purely a specified execution model.  
According to Bugnion, a true virtual machine must virtualize the processor, memory, and I/O components.  
In the context of \ac{BPF}, as Fleming explains in \cite{ebpf_intro}, the term “virtual machine” refers solely to a logical \ac{CPU} specification with a fixed instruction set and ten registers, designed to run platform-independently within the kernel.  
Consequently, as Gregg observes, the \ac{BPF} virtual machine exists only in specification form.  

Besides the 10 registers, the virtual machine also offers 512 bytes on the stack, as Gregg describes in \cite[Chap.~2.3]{Gregg_2020}.  
Additionally, more memory is available in maps.  
These maps are created using the command \texttt{BPF\_MAP\_CREATE}, as described in \cite[p.~5]{gbadamosi2024ebpfruntimelinuxkernel}.  

As Gregg discusses in \cite[Chap.~2.2]{Gregg_2020}, \ac{BPF} programs can exchange data among each other through using maps.  
Furthermore, the maps are synchronized, allowing parallel memory accesses.  
Maps can be accessed from user space, providing a way to transfer collected data from the virtual machine back to user space.  
Command-line tools such as \texttt{bpftrace} use these maps to display statistics, for example.  

As Gregg explains in \cite[Chap.~2.2]{Gregg_2020}, this has the advantage that no communication between user and kernel space is necessary.  
Since the program runs entirely in kernel space at runtime, different event sources can be filtered and processed there.  

Gregg uses in \cite[Chap. 2.6]{Gregg_2020} the event source as an umbrella term for events and probes, so for static and dynamic event sources.
Since this term is inconvenient, in literature often the term static and dynamic events is used.
So to be more precise in the following, the term event is only used for static event sources and the term probes is only used for dynamic event sources.

As shown in Figure~\ref{fig:bpf:working_principle}, the virtual machine provides another method for transferring data from the kernel to user space.  
The ring buffer, which Gregg in \cite[Chap.~2.3]{Gregg_2020} also describes as perf buffer, is used to continuously transfer data from the kernel to user space.  

Nair et al. developed GAPP in \cite{Nair_2020}, a tool to identify serialization bottlenecks in parallel Linux applications.  
For monitoring, \ac{BPF} is also used, and maps and perf buffers are employed for data exchange between kernel and user space.  
Another example are Liu et al., who built a protocol-independent network observability system in \cite{9359159}.  
Furthermore, both Kannan et al., presenting a network monitoring agent in \cite{network_obser}, and Gowda et al., proposing kernel-level request tracing for microservice visibility in \cite{V_2022}, use \ac{BPF} along with maps and perf buffers.

All these works utilize \ac{BPF} for monitoring and rely on maps and perf buffers for communication between kernel and user space.  
These examples confirm, on one hand, that \ac{BPF} is widely used in network observability.    
This is likely because maps and perf buffers are well integrated with \ac{BPF} and offer excellent performance.  
As a result, the effort to integrate, for example, RelayFS with \ac{BPF} is not justified.  
Therefore, this work also relies on maps and perf buffers.

The modules not yet mentioned from Figure~\ref{fig:bpf:working_principle} are BPF helpers, event sources, and BPF syscalls.  
All of these are shown as yellow boxes, which, as explained earlier, indicates that they represent components, which do not belong fully to \ac{BPF}, but influence the execution of the \ac{BPF} program.  

As described by Gregg in \cite[Chap.~2.3.6]{Gregg_2020}, a \ac{BPF} program cannot execute arbitrary kernel functions.  
To enable access to information from the \ac{OS} context within the program, BPF helper functions are used.  
These are defined in the BPF API in \texttt{include/uapi/linux/bpf.h}, and new helpers are constantly being added.  
The BPF API in this context refers to the set of functions and interfaces that the kernel exposes to \ac{BPF} programs to interact with kernel and user space resources in a controlled manner.  
As illustrated in Figure~\ref{fig:bpf:working_principle}, these helpers can be invoked via the \texttt{bpf\_call} instruction.  
 
Among these restricted kernel calls is \texttt{bpf\_ktime\_get\_ns()}, which returns the time since kernel start in nanoseconds.  
This enables access to a monotonic clock, allowing the measurement of time intervals between specific event sources at kernel level.  

Other important BPF helpers, which are used in this work are \\
\texttt{bpf\_get\_current\_pid\_tgid()} and \texttt{bpf\_get\_current\_comm(buf, buf\_size)}.  
With this functions the current process ID and the name of the current process can be retrieved, respectively. 

As illustrated in Figure~\ref{fig:bpf:working_principle}, beside \ac{BPF} helper functions, also syscalls can be invoked from the \ac{BPF} virtual machine.  
These syscalls are specific to the \ac{BPF} environment and provide the same functionality as conventional syscalls, but operate differently.  

Syscalls have existed since the early 1980s, as evidenced by the first official Unix Programmer's Manual~\cite{bell}.  
As described by Tanenbaum in~\cite[p.~50--53]{Tanenbaum_2014}, syscalls constitute the programming interface for user space programs to request services from the kernel space.  
Thus, syscalls act as a mechanism for the user space to interact with the kernel space.  

As described by Gregg in~\cite[Chap.~2.3.6]{Gregg_2020}, the \ac{BPF} syscall can be invoked via the code shown in listing \ref{lst:bpf_syscall}.

\begin{listing}[H]
\begin{minted}[fontsize=\small]{c}
int bpf(int cmd, union bpf_attr *attr, unsigned int size);
\end{minted}
\caption{BPF syscall interface}
\label{lst:bpf_syscall}
\end{listing}

The \texttt{cmd} parameter specifies the particular \ac{BPF} operation to be performed.  
It is an integer value provided through an enum.  
As Gregg describes it in \cite[Chap.~2.3.6]{Gregg_2020}, the \texttt{BPF\_PROG\_LOAD} enum value instructs the verifier to check a \ac{BPF} program and subsequently load it into the kernel.  
Similarly, maps can be accessed or modified from user space using commands such as \texttt{BPF\_MAP\_CREATE} or \texttt{BPF\_MAP\_LOOKUP\_ELEM}.  

The key difference between conventional syscalls and the \ac{BPF} syscall is that there is only one syscall for the entire \ac{BPF} subsystem.  
Nevertheless, as explained above, this single syscall can provide multiple functionalities.  
In contrast, conventional syscalls are monofunctional, with one syscall per functionality.  
Thus, while traditional syscalls are monofunctional, the \texttt{bpf()} syscall is polyfunctional.  
Compared to traditional syscalls, \texttt{bpf()} does not directly implement a single syscall in the classical sense, but rather acts as a wrapper for the syscalls of the \ac{BPF} subsystem.  
However, the fundamental purpose of syscalls, to provide a communication interface between user space and kernel space, remains unchanged in the \ac{BPF} implementation.  

As shown in Figure~\ref{fig:bpf:working_principle}, event sources also interact with \ac{BPF}.  
As described by Gregg in~\cite[Chap.~1]{Gregg_2020}, the primary functionality of \ac{BPF} is to execute user-defined code in response to event sources.  
Therefore, the event sources shown in Figure~\ref{fig:bpf:working_principle} are among the most crucial components of the overall system.   
In Figure~\ref{fig:probes}, a software stack is illustrated.  
This illustration indicates, among other aspects, where specific static and dynamic event sources are located and which monitoring techniques can be used to observe them.

In Figure~\ref{fig:probes}, only three monitoring techniques are distinguished: dynamic tracing, static tracing, and sampling.  
In the following the available monitoring techniques are discussed, their differences highlighted and it will be explained what a probe is and how probes can be classified.  

Gregg describes in \cite[Chap.~1.2]{Gregg_2020} that monitoring techniques serve the purpose of observability.  
He defines the term \emph{observability} as the ability to understand a system by means of monitoring tools.  

The term \emph{observability} was originally introduced in 1960 by Kalman in \cite{Klmn1960ContributionsTT}.  
He defines observability as the property that the internal state of a system at any given time can be completely determined from its outputs over a finite period of time.  

\begin{equation} \label{eq:obser}
x_{k+1} = A x_k + B u_k, \quad y_k = C x_k + D u_k,
\end{equation} 

For a given state-space system model like presented in equation \ref{eq:obser}, the variable $x_k$ is the state vector of the system at time step $k$.
The variable $u_k$ is the input vector at time step $k$,  
$y_k$ is the output vector at time step $k$,  
$A$ is describing the evolution of the internal state over time,  
while the input matrix $B$ describes how inputs affect the states,  
$C$ is the output matrix mapping the state $x_k$ to the measured outputs $y_k$,  
and $D$ is the feedthrough matrix describing any direct influence of the inputs on the outputs.  

According to Kalman \cite{Klmn1960ContributionsTT}, a system is observable if the \emph{observability matrix} shown in equation \ref{eq:matrix} has full rank, in other words \(\mathrm{rank}(\mathcal{O}) = n\), where \(n\) is the dimension of the state vector \(x_k\).  
The variables $A$ and $C$ in equation \ref{eq:matrix} have the same meaning, like in equation \ref{eq:obser}.
The product $C A^i$ describes how the output at time step $k+i$ depends on the initial state $x_k$.
To $i$ applies $i \in [0, n-1]$.
The observability matrix in equation \ref{eq:matrix} has one column for each state variable, in other words $n$ columns if $x_k \in \mathbb{R}^n$.
\begin{equation} \label{eq:matrix}
\mathcal{O} =
\begin{bmatrix}
C \\
C A \\
C A^2 \\
\vdots \\
C A^{n-1}
\end{bmatrix}
\end{equation}  

Full column rank ensures that each state variable can be uniquely determined from the output measurements.
The outputs must be multiplied by $A^i$ in each block $C A^i$ because the effect of the initial state on future outputs evolves over time according to the system dynamics.
This condition ensures that the current state $x_k$ can be fully reconstructed from the output measurements $y_k$.  

Nevertheless, Gregg's definition of observability does not deviate substantially from Kalman's original formulation.  
A system can only be fully understood if its internal state can be determined at all times from its outputs. 
Also, Gregg's definition is more practically oriented, where the original definition is more oriented to the theory.
In order for a system to produce outputs from which its internal state can be inferred, certain analysis techniques are required.  
Gregg categorizes these techniques in \cite[Chap.~1.2]{Gregg_2020} into \texttt{tracing}, \texttt{snooping}, \texttt{sampling} and \texttt{profiling}.  

Tracing, as described by Gregg in \cite[Chap.~1.2]{Gregg_2020}, refers to recording the system state based on event sources.  
The origins of tracing can be traced back to 1951, when Gill in \cite{doi:10.1098/rspa.1951.0087} described a method to rapidly diagnose errors in the code of digital computers.  
This topic is closely related to debugging, yet Gill already employed several techniques in this paper that are also relevant to tracing.  
He also emphasized that his error detection method should have as little impact on the system as possible.  
Furthermore, he employed monitoring and reacting to event sources, as can be seen in \cite[p.~540, 547]{doi:10.1098/rspa.1951.0087}.  
He's not using the term ``tracing`` in his paper yet, but he describes a method that nowadays is considered between debugging and tracing.
Like Gregg describes in \cite[Chap. 1.2]{Gregg_2020} nowadays there are various tools in the Linux context that enable tracing, such as \texttt{strace} \cite{strace} or \texttt{top}.  
According to Gregg, \texttt{top} internally also works with event sources and subsequently outputs a summary of the information extracted from these event sources to the console.  
From this, it follows that tracers must, on the one hand, be capable of detecting event sources, and on the other hand, also be able to read their metadata in order to fully understand their context.  
Furthermore, since event sources can occur very frequently, the overhead of a tracer must remain low.
Otherwise, the system would be significantly impaired.  

In this work, \texttt{tracing} is primarily used, and therefore the other three techniques will not be discussed further at this point.  
After having described tracing, the following section explains what an event source is and which types exist in the Linux context.  
As previously mentioned and as shown in Figure \ref{fig:bpf:working_principle}, they can be classified into static and dynamic event sources.

In Figure \ref{fig:probes}, the diagram is also divided into three sections, again distinguishing static and dynamic tracing.  
Sampling, as described, is normally used when many event sources are triggered, so normally in the context of the \ac{CPU}, like presented in Figure \ref{fig:probes}.  
Furthermore, Figure \ref{fig:probes} illustrates how a system stack is organized and which areas can be instrumented with event sources.  
The kernel space is separated from the user space by the system call interface.  

In the kernel space, event sources can be attached in the three categories memory, shown in blue, networking, shown in green, and the \ac{CPU}, shown in orange.  
In addition, Figure \ref{fig:probes} depicts the I/O controllers and the network controller, which are connected to the device drivers through the I/O bridge.  

In this work, only event sources from the networking subsystem and the network controller are required.  
Therefore, Figure \ref{fig:probes} highlights only selected events and tools from these areas.  
For the network controller, no native traceable events exist.  
However, the tools \texttt{netstat}, \texttt{ip}, and \texttt{ethtool} can be used to configure and monitor it, as described in \cite{ethtool,netstat,ip}.  

Having explained where event sources can be attached, the following section discusses in detail how they operate and in which aspects they differ.  
The description begins with dynamic probes, as these were more readily adopted into the Linux kernel.  

As Gregg describes in \cite[Chap. 1.2]{Gregg_2020}, dynamic probes consist of \acp{kprobe} and \acp{uprobe}.  
As shown in Figure \ref{fig:probes}, a \ac{kprobe} affects the kernel space, while a \ac{uprobe} affects the user space.  
According to Mavinakayanahalli \cite[p. 101]{Mavinakayanahalli_Panchamukhi_Keniston_Keshavamurthy_Hiramatsu_2006}, \acp{kprobe} were developed by the IBM Linux Technology Center and were integrated into the mainline kernel in version 2.6.9 in 2004.  
However, the mailing list \cite{kprobe_early} indicates that \acp{kprobe} were patched into kernel 2.5.48 already in 2002, although they were not yet part of the mainline at that time.  

\subsection{Kprobes}
A \ac{kprobe} allows instrumentation of any kernel instruction or function.  
This is achieved, as described in \cite[p. 101-104]{Mavinakayanahalli_Panchamukhi_Keniston_Keshavamurthy_Hiramatsu_2006}, by replacing an instruction with a software breakpoint and redirecting control to a handler.  
As described in \cite[p. 102]{Mavinakayanahalli_Panchamukhi_Keniston_Keshavamurthy_Hiramatsu_2006}, a \texttt{\ac{kprobe} struct} exists.  
This struct can be used to manage and configure probes.  
BPF tools, such as \texttt{bpftrace}, also utilize this struct in the background to register \acp{kprobe}.  
The relevant fields include \texttt{addr}, \texttt{pre\_handler}, \texttt{post\_handler}, and \texttt{fault\_handler}.  
The \texttt{addr} field specifies the location where the \ac{kprobe} should be registered.  
The handler fields indicate the actions to be executed before, after, or instead of the probed instruction.  

In addition to \ac{kprobe}, there exists the \ac{kretprobe}.  
As described in \cite{Mavinakayanahalli_Panchamukhi_Keniston_Keshavamurthy_Hiramatsu_2006}, it is used to monitor return times or return values of functions.  
A dedicated struct, \texttt{kretprobe}, exists for \acp{kretprobe}, containing, besides the entry address, an additional \texttt{maxactive} field.  
Since \acp{kretprobe}, as described later, are not attached to a fixed instruction address, multiple instances of the tracked function may exist simultaneously.  
This can occur, for example, if the function is recursive.  
The \texttt{maxactive} field specifies the maximum number of concurrent \acp{kretprobe} allowed for a single function.  

The following describes the operation of \acp{kprobe} and \acp{kretprobe}:  

\begin{itemize}
    \item A \textbf{Registration} is needed before use, as stated in the official documentation \cite{kprobe_doc}, for both \ac{kprobe} and \ac{kretprobe}.  
          This is done using \texttt{register\_kprobe()} or \\
          \texttt{register\_kretprobe()}.  
          A \ac{kretprobe} cannot exist without a corresponding \ac{kprobe}.  
          Therefore, registering a \ac{kretprobe} always involves a \ac{kprobe}.  
          During \ac{kprobe} registration, the first instruction of the target function is replaced with a breakpoint instruction, which is implemented as \texttt{int3} on the x86 architecture.  
          The original instruction is also copied to allow later execution.  
    \item A \textbf{Trap} occurs when the CPU reaches the address specified during registration, triggering the \ac{kprobe} dispatcher.  
          The normal function flow is interrupted, and control is transferred to the \ac{kprobe} handler.  
          As described in \cite{kprobe_doc}, all registers are saved and control is passed to the handler via the \texttt{notifier\_call\_chain}.  
    \item During the \textbf{\ac{kprobe}-Handler} the \texttt{pre\_handler} is executed first, followed by emulation of the original instruction, and then the \texttt{post\_handler} is executed.  
          In the \texttt{pre\_handler}, the address of the \texttt{\ac{kprobe} struct}  is passed to the handler.  
          Another function of the \texttt{pre\_handler} is to initialize the \ac{kretprobe}.  
          As can be seen in \cite{linux_kprobes_616}, this is performed by \texttt{pre\_handler\_kretprobe(struct kprobe *p, struct pt\_regs *regs)}, where \texttt{*p} is the \texttt{\ac{kprobe} struct}  and \texttt{*regs} contains registers saved during the trap.  
          This function replaces the return address of the probed function on the stack with the trampoline address and stores the original return in the \texttt{kretprobe\_instance} struct.  
          This has the affect that the trampoline is triggered when the original function returns.  
          Aside from this kretprobe-specific \texttt{pre-handler}, regular \ac{kprobe} can execute user-defined code before the actual function.  
          After the \texttt{pre\_handler}, the copied instruction is executed in a single-step manner, as described in \cite{kprobe_doc}.  
          Copying the instruction is necessary to avoid removing the breakpoint, which would allow other \acp{CPU} to skip the \ac{kprobe}.  
          Execution then proceeds to either the trampoline or the \texttt{post-handler}.  
          In the \texttt{post-handler}, the return value can be further processed, or additional user code executed.  
          For a \ac{kretprobe}, the \texttt{post-handler} is not executed, as it is replaced by the next \ac{kprobe} triggered via the trampoline.  
          If the function terminates in a fault, such as a page fault, the previously mentioned fault handler is invoked.
          This handler prevents the function from crashing immediately and implements a user-defined routine for handling the error condition.
    \item The \textbf{Trampoline} typically consists, as described in \cite{kprobe_doc}, of a NOP instruction.  
          As outlined by Stallings in \cite[p. 545]{Stallings_2018}, the NOP instruction means no operation.
          So this operation only acts as placeholder and makes space in the instruction stream.
          The trampoline handler is executed and transfers control to the return handler.  
          After execution of the return handler, the instruction pointer is restored to the original return address stored in \texttt{kretprobe\_instance}.  
          Essentially, the trampoline acts as a NOP instruction with an additional \ac{kprobe}.  
    \item The \textbf{return handler} corresponds to the second \ac{kprobe} in the \ac{kretprobe} and is used to execute user-specific code at the end of the probed function.  
\end{itemize}

As described in \cite{kprobe_doc}, the \texttt{fault\_handler} is only invoked if the probed function ends in a fault, but not if a handler itself triggers a fault.  
For this reason, a safety check is necessary for \acp{kprobe}.  
This check ensures that the breakpoint instruction, which replaces the original function, lies entirely within a single function.  
Since the breakpoint spans multiple bytes, this is not guaranteed by default.  
Furthermore, it is verified that the function does not contain jumps back to the original code, which has been replaced by the \ac{kprobe} breakpoint instruction.  
Finally, it is ensured that each instruction of the original function can be executed out-of-line.  

As stated in \cite{kprobe_doc}, almost everything in the kernel can be probed using \acp{kprobe}, except the probes themselves.  
There are some exceptions, which are recorded in a blacklist.  
This list includes all functions marked with the macro \texttt{NOKPROBE\_SYMBOL()}.  
The blacklist can also be dynamically viewed in DebugFS under \texttt{/sys/kernel/debug/kprobes/blacklist}.  

The performance of \acp{kprobe} can be optimized, as described by Gregg in \cite[Chap. 2.7]{Gregg_2020}, by replacing the break instruction with a jump instruction.  
This has been possible since kernel version 5.x and is applied automatically if feasible.  
Since a \ac{kprobe} cannot instrument itself, measuring the overhead is challenging.  
Moreover, the required execution time depends heavily on the hardware.  
According to the official documentation \cite{kprobe_doc}, \acp{kprobe} on an Intel Xeon E5410 CPU take between 0.5 and 1 $\mu$s.  
In contrast, \acp{kretprobe} take between 0.75 and 1.75 $\mu$s.  
Optimized \acp{kprobe} achieve significantly better results on the same hardware.  
For \acp{kprobe}, execution times range between 50 and 60 ns, while \acp{kretprobe} require between 300 and 400 ns.  
Babrou presents measurements of \acp{kprobe} on an Apple M1 processor in \cite{k_probe_benchmark}, yielding results between 110 and 350 ns.  

In this work, a Raspberry Pi 5 is used.  
The performance of its quad-core ARM Cortex-A76 processor is closer to that of the Intel Xeon E5410 than to the Apple M1.  
This is due to both the number of cores and the clock frequency.  
It can therefore be assumed that the overhead of an optimized \ac{kprobe} on the Raspberry Pi 5 is approximately 50--100~ns, whereas a \ac{kretprobe} requires around 250--500~ns.

As previously described, the probes consist not only of \acp{kprobe} but also of \acp{uprobe}. 
In the following, the functioning of \acp{uprobe} and how they can be distinguished from \acp{kprobe}, is described.

\subsection{Uprobes}
As Corbet notes in \cite{uprobe}, \acp{uprobe} were added to the mainline kernel in version 3.5 in 2007. 
Thus, they were introduced approximately three years after \acp{kprobe}.

As described by Gregg in \cite[Chap. 2.8]{Gregg_2020}, \acp{uprobe} are very similar to \acp{kprobe} in both functionality and implementation.  
In contrast to \acp{kprobe}, \acp{uprobe} are used to dynamically trace user space programs.  
Similar to \acp{kprobe}, there exist both \acp{uprobe} and the derived \acp{uretprobe}, which probe the return of a function.  

Unlike \acp{kprobe}, \acp{uprobe} are attached to a function in an executable file in user space.  
As described in \cite{uprobe_doc}, this can be achieved by registering \acp{uprobe} in the file \\
\texttt{/sys/kernel/tracing/uprobe\_events}.  
For instance, using the command \\
\texttt{echo 'p /usr/test:0x5329c0' > /sys/kernel/tracing/uprobe\_events} attaches an \ac{uprobe} to the executable \texttt{test} at offset \texttt{0x5329c0}.  
In other words, the function to be probed in \texttt{test} starts at byte \texttt{0x5329c0}.  
This implies that the function and offset must always be provided when registering a \ac{uprobe}.  

This behavior can also be seen in \cite{uprobe_code}, where the function in listing \ref{lst:uprobe} is defined.

In listing \ref{lst:uprobe}, \texttt{inode} specifies the file to be probed, and \texttt{offset} indicates the offset of the function in the file where the breakpoint should be set.  
The argument \texttt{uc} provides information on how the probe should be handled, including callback functions for the handlers.  

The beginning of the function, i.e., the location in the file pointed to by the offset, is replaced by a breakpoint instruction, similar to \acp{kprobe}.  
However, the breakpoint instruction is not set immediately upon registering the \ac{uprobe}, as noted in \cite{uprobe_mail}, but only when the file is loaded by a process.  
This ensures that the file is modified only if necessary.  

As described by Zhen et al. in \cite[p. 2, 3]{zheng2023bpftimeuserspaceebpfruntime}, a context switch from user space to kernel space occurs when the \ac{CPU} reaches the breakpoint instruction.  
Subsequently, as with \acp{kprobe}, the handlers are executed in kernel space in a virtual machine.  
Once the \ac{uprobe} has been fully executed in kernel space, another context switch from kernel to user space occurs, and the program continues normally.  

As described in \cite{uprobe_mail}, the instructions are loaded into a separate area.  
This area is implemented using a page where the instructions are single-stepped.  
Therefore, the instructions are executed per process.  
Dronamraju refers to this area, where instructions are executed per process using single-stepping, as the XOL area.
In this context XOL means execute out of line.  
The main difference in the execution flow of a \ac{uprobe} is that it requires two context switches and is executed per process.  
As described by Zhen et al. in \cite[p. 2]{zheng2023bpftimeuserspaceebpfruntime}, these context switches can increase the runtime of an \ac{uprobe} by a factor of ten.  

Furthermore, at the time of this work, no optimizations exist for \acp{uprobe} that are part of the kernel mainline.  
Optimization of \acp{uprobe} by using a jump instruction, as in the case of \acp{kprobe}, is not possible because, due to per process execution in the XOL area, the jump instruction would otherwise overwrite the original instructions of other processes that are not currently executing the \ac{uprobe}.  
This is because, as described in \cite[p. 3-333]{jmp}, the jump instruction loads the handler, i.e., the XOL area, into the current page.  
As a result, all processes executing the code containing the probed function would execute the \ac{uprobe} handler using single-stepping.  
This behavior contradicts the design principle of \acp{uprobe}, which is that they are executed per process.
Therefore, the breakpoint instruction \texttt{int3} is used, which triggers an exception and causes a context switch into kernel space, where execution is redirected to the XOL area.  
Since there exists one XOL area per process, the per process design can be preserved.  

Because \acp{uprobe} cannot be optimized and additionally involve context switches, they are slower than \acp{kprobe}.  
There is less documentation and fewer studies available on \acp{uprobe} compared to \acp{kprobe}, which is why there are only limited reliable data regarding the overhead of \acp{uprobe}.  
Nevertheless, Zhen et al. measured an overhead of 3.2~$\mu$s in \cite[p. 7]{zheng2023bpftimeuserspaceebpfruntime}.  
Keniston et al. reported similar values in \cite[p. 218]{keniston}, with an overhead of 3.4~$\mu$s.  
For comparison, Keniston et al. also presented results for optimized \acp{kprobe}, where the overhead was reduced to 0.25~$\mu$s.  
This is consistent with the values given in the official documentation \cite{kprobe_doc}.  
Thus, it can be assumed that the overhead of \acp{uprobe} is approximately 10 to 15 times higher than that of \acp{kprobe}.  

The performance of \acp{uretprobe} is unexpectedly good in the results described by Zhen et al., with values close to 4~$\mu$s.  
Given an overhead of 3.2~$\mu$s, this corresponds to only a 25\% increase.  
In contrast, the results for non-optimized \acp{kprobe} in \cite{kprobe_doc} showed an additional overhead of 50\% to 75\%, while the optimized variant reached as high as 500\% to 600\%.  
This can be explained by the fact that \acp{uretprobe} do not introduce an additional context switch, which, as also described in \cite{zheng2023bpftimeuserspaceebpfruntime}, accounts for a major portion of the total execution time.  

There are already initial optimization approaches that specifically target \acp{uprobe}.  
One such approach was presented by Zheng et al. in \cite{zheng2023bpftimeuserspaceebpfruntime}.  
They optimized the behavior of \acp{uprobe} by reducing context switches.  
This is achieved by handling \acp{uprobe} entirely in user space.  
The approach is limited to the use of \acp{uprobe} in the context of \ac{BPF}.  
In the proposed program \texttt{bpftime}, the virtual machine for \ac{BPF} is implemented in user space instead of in the kernel.  
Thus, the entire execution of a \ac{BPF} program, as described before, takes place in user space.  
It would go beyond the scope here to explain the execution flow in detail, but Zheng et al. were able to fully implement \acp{uprobe} in user space.  
The per process principle was preserved in this implementation.  
As a result, all context switches were eliminated, which is also reflected in the performance results.  

The performance of user space \acp{uprobe} and \acp{uretprobe} is approximately 10 times better than that of the original probes.  
In \cite[p. 7]{zheng2023bpftimeuserspaceebpfruntime} values of about 314~ns for \acp{uprobe} and 381~ns for \acp{uretprobe} were achieved.  
These results are already very close to those of optimized \acp{kprobe}.  
In particular, the values of optimized \acp{uretprobe} show no significant difference compared to \texttt{bpftime}.  

However, at the time of this work, \texttt{bpftime} is still a work in progress and suffers from several bugs and an unstable API, as described in \cite{bpftime}.  
Nevertheless, \texttt{bpftime} is mentioned here to illustrate that the performance of \acp{uprobe} could soon approach that of \acp{kprobe}.  

After having explained what a probe is, and how it is implemented in Linux, both in the kernel and in user space, the following section explains what an event is.  
Furthermore, it will be discussed how events are implemented and what differences exist compared to probes.  
 \subsection{Tracepoints}
An event, as Gregg describes in \cite[Chap. 2.9, Chap. 2.10]{Gregg_2020}, serves the purpose of static instrumentation in both user space and kernel space.  
In the kernel space, they are implemented using tracepoints, while in user space they are realized by means of \ac{USDT}.  
The following section will first take a closer look at the implementation of tracepoints.  

Tracepoints were developed in 2008 by Desnoyers.  
They were introduced as the successor to kernel markers, which had also been merged into mainline in 2008 with the release of version 2.6.24, as can be seen in \cite{kernel_markers-changelog}.  
Kernel markers are also static event sources and were developed in the context of the tracing tool \texttt{LTTng}, as described by Desnoyers in \cite{lttng_kernel_markers}.  
As Desnoyers explains in \cite[p. 170]{Desnoyers2009}, the original motivation for kernel markers was to provide an alternative to \acp{kprobe}, since their overhead was too high for the development of \texttt{LTTng}.  
Tracepoints were implemented shortly thereafter as an extension of kernel markers.  
As Desnoyers notes in \cite[p. 171]{Desnoyers2009}, the essential difference is a stable\footnote{Tracepoints are static and therefore normally remain unchanged, but as Gregg describes in \cite[Chap. 2.9]{Gregg_2020}, the API of tracepoints may change, although this happens only rarely.} API.  
This ensures that both the user and the callee side have a well defined agreement about the arguments of a given function.  
This is implemented using the library \texttt{include/trace/events}, in which the corresponding tracepoint function can be inserted into the source code at the desired location.  
For this tracepoint function, both the parameters to be passed and the return values are well defined.  
The structure of the tracepoints can be found under \texttt{/sys/kernel/debug/tracing/events/subsystem/event/format}.

As can be seen in \cite{tracepoints_commit}, the first commits for tracepoints by Desnoyers were made in 2008.  
However, as Gregg notes in \cite[Chap. 2.9]{Gregg_2020}, they were not released until 2009 with kernel version 2.6.32.  

Gregg describes that in the kernel, tracepoints have been placed at more than 100 points of interest for monitoring. 
Tracepoints are continuously added by developers, which causes their number to steadily increase.  
On the \ac{OS} used in this work, nearly 2500 tracepoints are already available.\footnote{This number can be determined with the command \texttt{find /sys/kernel/debug/tracing/events -type d | wc -l}, since all tracepoints are documented in this directory.}  

A tracepoint follows the format \texttt{subsystem:eventname}.  
For example, the tracepoint \texttt{net/net\_dev\_xmit} consists of the subsystem \texttt{net} and the event \texttt{net\_dev\_xmit}.  
As shown in \cite[Line 3831]{linux_xmit}, this event is triggered when a network packet is handed over to the driver for transmission.  

As described by Desnoyers in \cite{tracepoints}, a tracepoint can be in either the \emph{active} or the \emph{inactive} state.  
Gregg explains in \cite[Chap. 2.9.2]{Gregg_2020} that, when compiling the kernel, a 5-byte NOP instruction is inserted at the location where the tracepoint will reside.  
This instruction performs no operation and therefore introduces only a minimal runtime overhead.  
It represents the tracepoint in its inactive state.  

When the tracepoint is activated, the kernel replaces the NOP instruction with a JMP instruction of also 5-bytes that points to a trampoline.  
In addition, a callback routine is registered for the tracepoint.  
The trampoline in this context is a small routine that executes all callback functions registered for this tracepoint and forwards the arguments collected by the tracepoint.  
Multiple callback functions can be registered per tracepoint, typically by tracers such as \texttt{ftrace}, \texttt{perf}, or \texttt{LTTng}.  
As described by Desnoyers in \cite[p.~218]{Ecole23165}, the results of these callback functions are usually delivered to the tracers in user space via a ring buffer.  

In the following, the structure of a tracepoint function is described.  
A tracepoint is structured as shown in Listing~\ref{lst:tracepoint}.  
As illustrated in line~1 and explained by Rostedt in \cite{tracepoints_3}, the definition of every tracepoint always begins with the macro \texttt{TRACE\_EVENT}.  
This macro consists of the following six components:  

\begin{enumerate}
    \item First, a tracepoint always requires a \textbf{name}.  
          This name corresponds to the name of the event, as described earlier.  
          In the previous example, this would be \texttt{net\_dev\_xmit}.  
          The function invoked to place the tracepoint also contains this name.  
          It follows the naming convention \texttt{trace\_event-name}.  

    \item Next, the \textbf{prototype} of the tracepoint function is defined.  
          As shown in line~3 of Listing~\ref{lst:tracepoint} and explained by Desnoyers in \cite{tracepoints}, this prototype contains all arguments passed when the tracepoint is invoked.  

    \item The \textbf{arguments} used in the prototype must also be explicitly declared as parameters.  
          While this appears contradictory and redundant, it is necessary, as described by Rostedt in \cite{tracepoints_3}, because the tracepoint function executes callback functions to which these arguments must be forwarded.  
          Therefore, the arguments need to be provided again as separate parameters using \texttt{TP\_ARGS}, as illustrated in line~7 of Listing~\ref{lst:tracepoint}.  

    \item Furthermore, the \textbf{structure} of the data passed to the ring buffer must be specified.  
          This structure can include additional macros such as \texttt{\_\_field(type1, field1)} or \texttt{\_\_array(char, arr, LEN)}, as shown in lines~9--14 of Listing~\ref{lst:tracepoint}.  
          Here, \texttt{type1} could, for example, be an \texttt{int}, and \texttt{field1} is the name of the variable.  
          For arrays, the same applies, with the additional parameter \texttt{LEN} which is specifying the number of elements.  

    \item In addition, the \textbf{assignment} must define how the data is stored in the ring buffer.  
          As explained by Rostedt in \cite{tracepoints_3}, this step specifies how the previously defined structure is populated with the arguments introduced in step~2.  
          This is implemented using the parameter \texttt{TP\_fast\_assign}, as shown in line~16 of Listing~\ref{lst:tracepoint}.  

    \item Finally, the \textbf{output} is defined using \texttt{TP\_printk}.  
          As Rostedt explains in \cite{tracepoints_3}, this represents a format specification for the output of the fields contained in \texttt{TP\_STRUCT\_\_entry}.  
\end{enumerate}

Also for tracepoints, there are only very few reliable data regarding their overhead time.  
A distinction must be made between inactive and active tracepoints.  

As Edge describes in \cite{min_imp}, inactive tracepoints incur an overhead of approximately 2-4 cycles.  
At a clock frequency of 2.4\,GHz, as provided by the Raspberry Pi 5, this would correspond to a permanent overhead of about 1–1.5\,ns.  
In the active state, both Zheng et al.\ in \cite[p.~7]{zheng2023bpftimeuserspaceebpfruntime} and Gebai in \cite[p.~26:19]{tracepoint_comp} measure an overhead of 100–150\,ns.  
However, this exceeds the overhead of the optimized \ac{kprobe}, which incurs only around 60\,ns.  

In contrast Gregg, in \cite[Chap.~2.9.5]{Gregg_2020}, reports different figures.  
He compares the overhead of \acp{kprobe} with tracepoints and raw tracepoints.  
Raw tracepoints were introduced in Linux 4.17 in 2018 and do not provide a stable API, but only a stable tracepoint name.  
This reduces the overhead slightly.  
According to his results, raw tracepoints exhibited a maximum overhead of 9\%, regular tracepoints up to 14\%, and \acp{kprobe} up to 30\%.  
However, he does not provide any information on whether the \acp{kprobe} used in the measurements were optimized or not.  
These results contradict the previously mentioned findings.
For optimized \acp{kprobe} they appear too poor, while for unoptimized ones they appear too good.  

Desnoyers reports in \cite[p.~94]{Desnoyers2009} that \acp{kprobe} require 1.49\,$\mu$s.  
This also explains why tracepoints were developed as an evolution of \acp{kprobe}.  
Optimized \acp{kprobe} were only added to the kernel at the end of 2009, as indicated in \cite{kprobe_opt}.  
Therefore, at the time of the development of tracepoints, they were not yet available.  

There are no reliable data indicating whether optimized \acp{kprobe} or tracepoints exhibit lower overhead.  
However, in both cases, the overhead is very small.  

Besides the tracepoints for the kernel space, there also exist \acp{USDT} for the user space.  
In the following section the user space equivalent of tracepoints will be explained,

\subsection{User-level statically defined tracing}
As Gregg describes in \cite[Chap.~2.10]{Gregg_2020}, they work in a very similar way to kernel tracepoints.  
\acp{USDT} were developed to enable static tracing in user space.  
The functionality was first implemented in 2004 as part of \texttt{DTrace} \cite{USDT,269899}, but was only added to Linux later.  
From 2016 onwards, an integration with \ac{BPF} was available through \texttt{BCC}.  

Technically, at the designated location in the program, a \ac{USDT} is placed, which initially exists as a NOP.  
When the probe is enabled by a tracer, the kernel tracing subsystem replaces the instruction with a software breakpoint.  
Through this breakpoint, execution switches to the kernel, where the corresponding eBPF program or perf event is triggered.  

The processing of data does not take place via explicit callback functions in user space, but rather through the perf\_event infrastructure, as described by Gregg in \cite[Chap.~2.13]{Gregg_2020}.  
A file descriptor is opened via \texttt{perf\_event\_open()}, through which data is written into the perf ring buffer, as shown in \cite{perf_event}.  

In contrast to \acp{uprobe}, no currently running instruction needs to be replaced or emulated when patching, which makes \acp{USDT} more efficient.  
However, even with \acp{USDT}, a transition into the kernel is always necessary when the tracepoint is triggered, and thus a context switch occurs.  

As described in \cite{USDT}, \acp{USDT} can be defined in user code via the library \\
\texttt{\#include <sys/sdt.h>}.  
A tracer must then be attached to activate them.  

There are only very few data sources available regarding the overhead of \acp{USDT}.  
According to \cite[p.~26:28]{tracepoint_comp}, the overhead varies between 80~ns and 450~ns depending on the tracer.  
This is the only source that provides overhead measurements for \ac{USDT}.  
The values are considered reliable, as the same source already provides reference values for kernel tracepoints.  
However, no specific data for eBPF was given.  
Nevertheless, it can be seen that the overhead is significantly lower than that of a \ac{uprobe}.  
The order of magnitude lies between a factor of 10 and 40.  

The overhead of a non-activated \ac{USDT} remains the same as that of a kernel tracepoint and is therefore between 1~ns and 1.5~ns.  

After various event sources\footnote{Not all event sources were described, but only a selection of the most common ones and those relevant for this work. Gregg additionally describes dynamic \acp{USDT} and performance monitoring counters in \cite[Chap.~2.11, Chap.~2.12]{Gregg_2020}.}, both static and dynamic, have been explained, the question arises, which is more suitable for monitoring? 
This will be presented in the following section.

\subsection{Comparison of various event sources}
In Table \ref{tab:event}, the most important characteristics of the described event sources are summarized.  
The four event sources are compared in terms of type, overhead in active and inactive states, as well as maintainability, stability and flexibility.  

As shown in Table \ref{tab:event}, the static variants offer less flexibility.  
This means that fewer probe points are available, both in the kernel and in user space, where they can be attached.  
In addition, even when inactive, a small amount of overhead remains.  
Furthermore, maintenance effort is required to ensure that they remain available in all future versions of the program or the kernel.  

Despite these disadvantages, the static event sources also provide several important advantages.  
First, a stable API exists that defines exactly which information is made available by a tracepoint.  
Moreover, tracepoints are preserved in future kernel versions.  
A performance improvement over dynamic event sources\footnote{For the overhead of dynamic event sources, the minimum values correspond to the minimal reported latency of a simple probe, i.e. a \ac{kprobe} or \ac{uprobe}, and the maximum values correspond to the maximum reported latency of the respective return probes.} can also be observed.  

On the kernel side, tracepoints are similar fast as optimized \acp{kprobe}.  
Since \acp{kprobe}, however, cannot always be optimized, the overall performance of tracepoints is generally better.  
On the user-level side, the performance of \acp{USDT} is significantly better than that of \acp{uprobe} and only slightly worse than that of tracepoints.
Therefore their performance is, depending on the tracer, between 10 and 40 times faster than a \ac{uprobe}.

From this data, it follows that static event sources require more effort to maintain and to implement.  
However, this effort is compensated by better performance and higher stability.  

This observation is also supported in the literature.  
Gregg \cite[Chap.~2.9]{Gregg_2020} explains that tracepoints should always be used first whenever possible.  
Kprobes should only be employed as a fallback when no tracepoints exist for a specific use case.  
Gregg's opinion is further supported by Calavera et al. \cite[Chap.~4]{Calavera_Fontana_Frazelle_2020}.  

For monitoring in user space, \acp{uprobe} are also considered insufficient, as argued by Zheng et al. \cite[p.~3]{zheng2023bpftimeuserspaceebpfruntime}.  
They explain that, due to the relatively high overhead of \acp{uprobe} and the additional required context switches, these are not suitable for time-critical or real-time monitoring tasks.  

In summary, considering the advantages and disadvantages of the respective event sources, it is considered best practice to prefer static ones.  
If this is not possible due to lack of support or disproportionately high effort, then, as also mentioned by Calavera et al. \cite[Chap.~4]{Calavera_Fontana_Frazelle_2020}, dynamic event sources can and should be used.

\subsection{Test Application} \label{subsec:appl}

First, the requirements that the test application must fulfill are discussed.  
Afterwards, the test application itself is explained and how it meets these requirements.  

For the test application, the following three aspects are relevant:  

\begin{enumerate}
    \item \textbf{Real-time capability and execution time}:  
    The focus of this work is to evaluate influencing factors on the real-time capability of Wi-Fi.  
    Therefore, influencing factors that are not related to Wi-Fi should be minimized.  
    If the execution time of the application is too long or if it requires many shared system resources such as the \ac{CPU}, cache, memory, or graphics card, then the application becomes vulnerable to real-time issues.  
    That resource contention is a common problem for real-time systems, as stated among others by Aceituno et al. in \cite[p. 1]{ACEITUNO2021102223}.
    Especially in a multi-core environment it is not possible to avoid resource contention completely, but to restrict it as far as possible.
    It is mandatory that the application achieves real-time capability, since real-time violations would otherwise directly affect the test results.  
    
    \item \textbf{Amount of data}:  
    It is also required that the application continuously generates data that can be transmitted.  
    This ensures that a sufficiently large number of data transmissions take place, which in turn are the foundation for reliable test results.  
    In other words, if the application only generates two data sets, only two transmissions occur.  
    From such a small number of transmissions, no reliable conclusions regarding the influencing factors on Wi-Fi performance can be drawn.  

    \item \textbf{Visualization}:  
    This point is rather a benefit than a strict requirement.  
    If real-time violations within the application can be visualized, the results become more intuitive and easier to interpret.  
    While this is not strictly necessary, it can enhance the comprehensibility of the results.  
\end{enumerate}

In Figure \ref{fig:application}, the concept of the test application is presented.  
It is divided into the three sections Application Concept, Calculation and Visualization.  
The discussion first addresses the Concept.

The concept consists of two main components, namely the \texttt{network model} and the job.  
The \texttt{network model} specifies which jobs are executed and at what time.  
It is inspired by the theory of scheduling workload models, as described by Baruah et al.\ in \cite[p.~14--20]{Baruah2015}.  
Although this work does not investigate the real-time capability of scheduling itself, the models can nevertheless be applied in an adapted form to the network.  

In scheduling theory, jobs are also used to represent workload models.  
There a job represents an application that is executed by a thread.  
Each job is characterized by three properties:  

\begin{itemize}
    \item The \textbf{arrival time}, which specifies when the job begins.  
          It corresponds to the point in time when the event \texttt{schedule switch} is triggered, where the parameter \texttt{nextpid} contains the identifier of the thread.  
    \item The \textbf{deadline}, which is the latest point in time by which the job must be completed.  
          The interval between arrival time and deadline is referred to as the scheduling window and represents the time available for execution.  
    \item The \textbf{\ac{WCET}}, which denotes the maximum execution time required by the job.  
          It corresponds to the execution time in the worst case, i.e., when the job is executed under the most unfavorable conditions.  
          Such conditions may arise due to external influences such as interrupts or blocked resources.  
          In the networking context especially the time in the network stack can be considered as a part of these conditions.
          The \ac{WCET} must be smaller than the scheduling window to guarantee that the job finishes before its deadline, thereby ensuring that the application represented by the job is real-time capable.  
\end{itemize}

These properties can also be transferred to the application in this work.  
Although scheduling itself is not the subject of observation, the underlying theory remains the same.  
By assigning a given period, the job can be repeated multiple times, allowing conclusions to be drawn about the behavior of the network.  

As illustrated in Figure \ref{fig:application}, the periodic model of Liu et al.\ has been applied, originally published in 1973 in \cite{10.1145/321738.321743}.  
This model has been used for more than fifty years to evaluate the real-time properties of applications.  
The model assumes an implicit deadline, which is defined by the length of the period.  

A job $J_i$ starts at its arrival time $S_i$ and should complete by its deadline $D_i$.  
In the case of an implicit deadline, the deadline $D_i$ is equivalent to the arrival time of the subsequent job, i.e., $S_{i+1}$.  
These time points are always separated by the period $p_i$.  
The period usually remains constant, such that $\forall i,j \in [0, k]$, $k \in \mathbb{N}\setminus \{0\}: p_i = p_j$.  
The period therefore also defines the length of the scheduling window.  

Besides the original workload model proposed by Liu et al., there exist other models, such as the three-parameter \texttt{sporadic task model}, which is introduced by Baruah et al. in \cite[p.~15, 16]{Baruah2015}.  
This model is structured similarly to the periodic model but differs in two essential aspects.  

First, it includes an explicit parameter for the deadline, which allows the deadline to occur either before or after the release of the next job.  
In other words, the constraint $D_i = S_{i+1}$, which always holds in the model of Liu et al., does not apply here.  

The second major difference is that the period length $p_i$ is no longer fixed.  
Since the sporadic model is not fully periodic, a stochastic component is introduced.  
As a result, the model only guarantees a minimum interarrival time $p_{\min}$ between two tasks.  
However, it is not ensured that $S_{i+1}$ occurs exactly or shortly after $p_{\min}$ time units following $S_i$.  
Consequently, the model exhibits both periodic and sporadic characteristics.  

For evaluating the real-time capability of an application, the periodic factor is highly relevant, since otherwise the data set might be too small to enable result-based conclusions.  

In the context of network communication, there also exist two models, as described by Khojasteh et al. in \cite{khojasteh2017timetriggeringversuseventtriggeringcontrol}.  
These are categorized into the time-triggered and the event-triggered models.  
They define the conditions under which network data is transmitted in an application.  

In the time-triggered variant, data is sent at fixed time intervals, analogous to the \texttt{periodic task model}.  
In contrast, the event-triggered variant transmits data only when a specific event occurs, which resembles the \texttt{sporadic task model}.  
According to Khojasteh et al. \cite[p.~6]{khojasteh2017timetriggeringversuseventtriggeringcontrol}, the event-triggered approach requires less bandwidth and, for the same stability requirements, achieves a lower transmission frequency compared to the time-triggered approach.  
Thus, the event-triggered model is described as the more efficient option.  

However, this view is contrasted by the study of Meister et al. in \cite{meister2023sharednetworkeffectstime}, where the two models are also compared.  
Their results demonstrate that in practice, especially under network effects, the time-triggered model can outperform the event-triggered one.  
Since the studies of Khojasteh et al. where only theoretically and the network load was not considered, the results of Meister et al. can be considered as meaningfull.

Since this work also considers network effects, and because the periodic model provides lower complexity, improved observability, and enhanced predictability, a periodic model is adopted in this thesis.  
The periodic model has a lower complexity, because it has no separate parameter for a deadline or a minimum period and therefore less parameters in general.
It can also be monitored more easily, because it is more predictable.  
It can be determined exactly when the next job will occur and when all jobs will be completed.  

In Figure \ref{fig:application}, the jobs are shown in a model that is very similar to the one of Liu et al.  
A distinction is made between real-time jobs, which are shown in blue, and non-real-time jobs, which are shown in green.  
It can be observed that only the real-time jobs possess a period duration and an arrival time.  
The non-real-time job extends across the entire timeline.  
This is because there is no specific regulation for it.  
The requirement was to transmit as much bulk data as possible alongside the real-time data, which results in this data being sent continuously.  
Only the real-time jobs are subject to timing constraints.  
For $J_{i+2}$, the model also visualizes how a real-time violation occurs.  
$J_{i+2}$ finishes at the time $E_{i+2}$, which is the interval $rt_{v-i+2}$ after its deadline $D_{i+2}$.  
This interval is shown in red.  
Thus, the diagram does not represent the load on the \ac{CPU}, but instead the load on the network, at least partially.  

The execution of a job is depicted on the right side in the Application Concept.  
A job is one iteration in which a step of the application is executed.  
The application visualizes a unit circle.  
In the following, it is described how this circle is constructed.  
The entire coordination is performed by the server, while the client has no information other than what the server provides.  
The execution of the job is labeled with numbers, starting with \circnum{1} which represents $S_i$.
The server is managing this, by starting a timer.
In the first step, also the angle $\alpha$ is calculated, which determines the point on the circle.  
It is computed using $2\pi \div k \times i$ and is shown at the bottom left of the circle.  
Here, $2\pi \div k$ denotes the step size and $i$ the step number.  
The previously described variable $k$ defines the number of points on the circle and thus also the number of jobs.  

In step \circnum{2}, the server computes the x-coordinate of the point by evaluating $cos(\alpha)$.  
This process is illustrated in the Calculation box.  
In step \circnum{3}, the server sends a message to the client.  
This message contains the angle $\alpha$ and the radius of the circle.  
In step \circnum{4}, after receiving the network packet with $\alpha$, the client computes the y-coordinate of the point.  
This is again shown in the Calculation box and is obtained using the function $sin(\alpha)$.  
Then, in step \circnum{5}, the client sends a packet back to the server containing the y-coordinate.  
In step \circnum{6}, the job, as shown in the workload diagram, ends.  
As soon as the server receives the client’s message, it stops the timer and checks whether the deadline $D_i$ was met.  
If the deadline is met, the penalty value $y_p$ is set to 0.  
If the deadline is missed, a penalty is applied.  
As described in Section \ref{sec:real_time}, the value of a real-time application does not only depend on the result but also on the timing constraints.  
Therefore, $y_p$ was introduced.  
Even if $D_i$ was missed, the result would still be correct.  
However, in order to visualize the real-time violation, the result is deliberately distorted by $y_p$, since according to the definition of a real-time application it must be considered incorrect.  

In step \circnum{7}, the angle $\alpha$, the calculated coordinates $(x_i, y_i)$, and the penalty $y_{pi}$, which is 0 if the real-time constraints are satisfied, are stored in a pre-allocated array.  
This is shown in the middle of Figure \ref{fig:application}.  
In step \circnum{8}, after all jobs are completed, the results are visualized.  
This ensures that the real-time capability of the application is not restricted.  
The effect of $y_p$ on the visualization can be seen in the lower left of Figure \ref{fig:application}, where a red square marks the new point that no longer lies on the circle.  
The Visualization box shows the unit circle and how it is composed of the sine and cosine functions.  

After describing the job execution, it becomes clear that in this modified model, unlike in the original scheduling workload model of Liu et al., a job is not an executed application, but rather one iteration in a sequence of instructions within an application.  
This sequence of instructions also includes two network communications, one from the server to the client and one back.  

After describing how the application is structured and how it functions, the following section will discuss how it is technically implemented.  

\subsection{Server and Client Implementation} \label{subsec:impl}

As described before, the entire logic is implemented on the server side, and the client only reacts to the messages of the server.  

The application, as illustrated in Figure~\ref{fig:application}, constitutes only a small part of the overall server.  

The logic of the server can be represented as a state machine, as shown in Figure~\ref{fig:state_machine}.  
The state machine is deterministic, since, as described by Rabin et al.\ in \cite[p.~120]{5392601}, a deterministic state machine requires that for a given state and a given operation the target state must be uniquely defined.  
This property holds for the state machine in Figure~\ref{fig:state_machine}.  

Furthermore, the state machine has finitely many states, which according to \cite[p.~114]{5392601} is the defining property of a finite state machine.  
Consequently, the state machine in Figure~\ref{fig:state_machine} is a \ac{DFSM}.

    \centering
     \includegraphics[width=\textwidth]{figures/Zustandsautomat.drawio.pdf}
    \caption[Presentation of the server state machine]{Representation of the server state machine. Green states have no real-time requirements. Red states are subject to real-time constraints.}
    \label{fig:state_machine}

It can be observed that the server consists of nine states.  

The application, as described in Section~\ref{subsec:appl}, occupies only two of these states.  
Steps~\circnum{1} to \circnum{7} of Figure~\ref{fig:application} are executed in the state \texttt{Calculation}, and Step~\circnum{8} is executed in the state \texttt{Save}.  

The states in Figure~\ref{fig:state_machine} can be classified into four categories.  
First, there are the start and end nodes, as is common for finite state machines.  
Second, the regular states in Figure~\ref{fig:state_machine} are distinguished into states without real-time requirements, shown in green, and states with real-time requirements, shown in red.  
It can be seen that the automaton starts in the state \texttt{Setup} and can terminate in the two states \texttt{Error} and \texttt{End}.  
Furthermore, only the state \texttt{Calculation} has real-time requirements.  

The following describes the function of each state and how it is implemented.  

The state \texttt{Setup} is the initial state.  
It sets the priority to real-time priority, loads and initializes the \ac{BPF} program, and starts the server.  
As shown in Listing~\ref{lst:setup}, line~3, the real-time priority is set to 99, which, as described in Section~\ref{subsec:real_time_kernel}, corresponds to a priority of 139.  
For monitoring, \ac{BPF} is used, which is integrated into Rust through \texttt{libbpf\_rs}.  
As described in \cite{libbpf-rs}, the Rust code resides in the \texttt{/src} directory, while the \ac{BPF} code, written in C, resides in \texttt{/src/bpf}.  
The \ac{BPF} file must have the extension \texttt{.bpf.c}.
In order to integrate the \ac{BPF} program into the Rust code, a skeleton must be generated.  
A skeleton is an automatically created binding layer that provides a type-safe interface to the maps and programs defined in the compiled \ac{BPF} object file.  
It abstracts away low-level details of loading, attaching, and accessing kernel objects, and thus enables the interaction from rust with the \ac{BPF} subsystem in a safe and idiomatic manner.  

As shown in Listing~\ref{lst:setup}, line~1, this skeleton is subsequently included in the Rust code.  

In order to generate the skeleton, a build script must be written, which, as described in \cite{build_script}, has to be placed in the file \texttt{build.rs}.  
This integration ensures that the creation of the skeleton becomes part of the Rust compilation process.  

The build script is presented in Listing~\ref{lst:build_script}.  
In this script, the path to the kernel headers must first be determined, since the \ac{BPF} program has to be compiled against them in order to make use of kernel structures, such as tracepoints.  
To identify the kernel headers, the script attempts to read the path from an environment variable, as shown in lines~5 and~6.  
If this attempt fails, the default path \texttt{/usr/src/kernel} is assumed.  

Subsequently, the skeleton can be generated by means of the \texttt{SkeletonBuilder}.  
As indicated in \cite{skeleton}, the builder requires three arguments.  
First, it requires the \ac{BPF} source file, which in this case is \texttt{monitor.bpf.c}, as illustrated in line~8 of Listing~\ref{lst:build_script}.  
Second, it requires the output file, that is, the file name in which the skeleton will be stored after generation.  
This is shown in line~15.  
Finally, the builder requires compile flags for \texttt{clang}.  
These include, among others, the kernel UAPI headers, as depicted in lines~9--14.

Using the skeleton, as illustrated in Listing~\ref{lst:setup} line 5, an \texttt{ObjectBuilder} is initially created through \texttt{MonitorSkelBuilder::default()}.  
This builder can subsequently be opened using the \texttt{.open()} method.  

During this step, the compiled \ac{BPF} object file is "opened," resulting in the creation of an \texttt{OpenObject}.  
In other words, the \ac{BPF} program is preloaded, thereby enabling modifications to the \ac{BPF} program as described in~\cite{libbpf-rs}.  
However, such modifications are not required in this context.  
Consequently, the \texttt{OpenObject} can be loaded directly via the \texttt{.load()} method, as demonstrated in line 6.  

At this point, the compiled \ac{BPF} program is loaded into the kernel and passes through all mandatory verification processes, including the verifier.  
This procedure is further elaborated in Chapter~\ref{subsec:bpf}.  

Once successfully loaded, the resulting \texttt{Object} enables interaction with the \ac{BPF} script residing in kernel space.  
Accordingly, as shown in lines 7 and 9, all programs specified in the \ac{BPF} file are attached to their designated locations within the kernel.  
In other words, the defined programs are bound to the corresponding event sources.  
Additionally, the maps defined in the \ac{BPF} file are retrieved to enable access to the data generated by the \ac{BPF} programs.  

Once the \ac{BPF} file is operational in kernel space, a ring buffer is created in lines 11--14, to which a callback function is attached.  
Although Gregg \cite[Chap. 2.1]{Gregg_2020} describes communication with the user space via a perf buffer, this work employs a ring buffer.  

As described in \cite{ring-buffer}, the ring buffer is the successor of the perf buffer and was introduced in Linux kernel version 5.8 in 2020.  
Liu et al. \cite[p. 6]{10.1145/3672197.3673430} report that it provides up to 25\% lower access latency.  
At the time of publication of \cite{Gregg_2020}, the ring buffer was not yet mainline, which explains why Gregg uses the perf buffer.  

In lines 16--20, a polling thread is launched, which continuously checks for the presence of new events.  
As detailed in \cite{rb}, polling continues until a new entry is available in the ring buffer or a timeout of 3 ms elapses.  
This timeout is chosen to ensure that, in the absence of new events, the overall process is not blocked, as the application operates on a periodic workload model with a 3 ms interval, as described in Chapter \ref{sec:eval}.  

In lines 22--36, a \ac{TCP} server is initialized, and the \texttt{SetupContext} is configured.  
The \texttt{SetupContext} is a structure encompassing all data required in subsequent states.  
After its initialization, in line 31, the main program flow, managed by the \texttt{run\_state\_machine()} function, is started.  
The setup is identical for both server and client, with the exception that the client initializes a client object to connect to the server, whereas the server sets up a \ac{TCP} server.  

In the \texttt{Start} state, which is illustrated in Figure~\ref{fig:state_machine} and represents the next state after \texttt{Setup}, the server waits until the client has established a connection and transmitted the start message.  

For the communication, different message types are employed.  
These are shown in Listing~\ref{lst:msg_types}.  

The attribute \texttt{\#[repr(u8)]} specifies that the enumeration \texttt{MessageType} is represented internally as an unsigned 8-bit integer as described in \cite{repr}.  
The attribute \texttt{\#[derive(Serialize, Deserialize, Debug, PartialEq)]}, like state in \cite{derive}, instructs the Rust compiler to automatically generate implementations for the traits \texttt{Serialize}, \texttt{Deserialize}, \texttt{Debug}, and \texttt{PartialEq}.  
This allows instances of the enumeration to be easily serialized and deserialized for communication purposes.
For this the crate \texttt{bytemuck} is used, which is described in \cite{bytemuck}.
This is necessary to reduce memory allocations and to ensure the correct layout of the message structures.

In the \texttt{Start} state, the server waits until it receives a message of type \texttt{Start}.  
Subsequently, it transitions into the next derive phase of the protocol.  

After the state \texttt{Start}, the three states \texttt{\ac{NTP}}, \texttt{\ac{PTP}}, and \texttt{Check} follow.  
All three states serve the purpose of time synchronization.  
Contrary to what their names suggest, \ac{NTP} and \ac{PTP} are not directly applied.  
Instead, the names merely describe the functionality of the corresponding synchronization protocols.  
Accordingly, in the \ac{NTP} phase a coarse synchronization between client and server is performed.  
In contrast, in the \ac{PTP} phase a finer synchronization is carried out.  

To understand why synchronization is necessary, the exact implementation of the monitoring process is first considered.  
The objective of the monitoring is to represent, as precisely as possible, the duration required by the program in specific parts of the data transmission process.  
These include the program execution itself, the network stack, and the transmission time within the medium.  
The schematic representation of the monitoring process is shown in Figure~\ref{fig:tx}.  

The figure illustrates both the server and the client.  
Furthermore, the application is depicted as a simplified part of the network stack within the kernel space as well as on the hardware level.  
The execution flow of the application, which was described in Section~\ref{subsec:appl}, is also included in the figure.

A distinction is made between eight intervals, denoted as $t_1$ through $t_8$.

It is assumed that the application starts on the server.  
The intervals are additionally marked with arrows in the corresponding colors in Figure~\ref{fig:tx}.

    \item \textbf{Interval $t_1$}\label{itm:t1} measures the time the application requires to compute the X-coordinate and to transfer the packet from user space to kernel space.  
          Therfore it starts in the application on the server, i.e., at position \circnum{1} in Figure~\ref{fig:application}.  
          It ends at the tracepoint \texttt{net\_dev\_queue}, which marks the entry into the \ac{Qdisc} and thus the TX API.  
          The TX API is described in detail in Section~\ref{subsec:linux_stack}.  
          As shown in Figure~\ref{fig:tx}, the packet already traverses the transport and network layers and ends at the entry into the link layer.  
          This point is of particular interest, since packets can accumulate in the \ac{Qdisc} and an unfavorable scheduler may delay real-time packets.  
          Therefore, this point is also relevant to enable the measurement of the \ac{Qdisc}.  
          Moreover, it includes a context switch which, as described in Section~\ref{subsec:monitoring}, introduces a non-negligible latency.  

    \item \textbf{Interval $t_2$}\label{itm:t2} measures the time the packet spends inside the \ac{Qdisc}.  
          This is particularly relevant to detect potential congestion in the \ac{Qdisc}. 
          It begins at the end of $t_1$, at the tracepoint \texttt{net\_dev\_queue} and ends at the tracepoint \texttt{net\_dev\_xmit}, which marks the exit from the \ac{Qdisc} and thus the entry into the TX ring buffer of the driver.  
          This tracepoint represents the last measurement point on the server side before a network packet leaves the server.  
          Furthermore, it allows the offset introduced by specific queuing strategies to be determined.  
          As reported by Corbet in \cite{qdisc}, the locking mechanisms of the \ac{Qdisc} alone introduce a delay of 48 ns.  
          He further states that the average delay caused by the \ac{Qdisc} is in the range of 58--68 ns.  

    \item \textbf{Interval $t_3$}\label{itm:t3} includes the time required for a packet to be transferred from the TX ring buffer of the server via \ac{DMA} to the server's \ac{NIC}, to be processed there, transmitted over the medium, and received by the client.
          On the client side, the packet must be received by the \ac{NIC}, transferred again via \ac{DMA} into the RX ring buffer, and then passed into kernel space.  
          As soon as a new packet is available in the RX ring buffer, an interrupt is triggered, as illustrated in Figure~\ref{fig:tx}. 
          The interval starts at the end of $t_2$, i.e., at the tracepoint \texttt{net\_dev\_xmit}, and ends at the tracepoint \texttt{consume\_skb} on the client.    
          This interrupt activates the client's poll queue via the soft IRQ \texttt{net\_rc\_action}.  
          A device in this queue triggers the tracepoint \texttt{consume\_skb} to read the packet from the buffer. 
          This is the first tracepoint which is triggered when a network packet arrives at a device. 
          Thus, interval $t_3$ covers the time from the server's link layer through the physical layer, across the medium, into the client's physical and link layers, more precisely into NAPI.  
          The terms NAPI, RX ring, and soft IRQ are explained in Sections~\ref{subsec:linux_stack} and \ref{subsec:real_time_kernel}.  
          This interval involves multiple layer transitions of the \ac{OSI-model}, as well as critical points such as the RX and TX ring buffers of the drivers and the processing in both \acp{NIC}.  
          However, no further tracepoints exist in these areas to allow finer-grained monitoring.  

    \item \textbf{Interval $t_4$}\label{itm:t4} covers the time from the client's link layer, through the network and transport layers, into the application.
          Thus it starts at the client's \texttt{consume\_skb} tracepoint and ends when the packet reaches the application in the client.    
          In this phase, a context switch from kernel space to user space and a system call are required.  
          Both the context switch and the system call may vary in duration depending on system load.  

    \item With this interval, half of the application flow is completed, and the intervals repeat, but this time from client to server.  
          \textbf{Interval $t_5$} corresponds to interval $t_1$ and begins in the client application as soon as computation starts.  
          This interval ends at the client's tracepoint \texttt{net\_dev\_queue}.  
          \textbf{Interval $t_6$} also takes place entirely on the client side, ranging from \texttt{net\_dev\_queue} to \texttt{net\_dev\_xmit}, thus measuring the client's \ac{Qdisc} delay.  
          \textbf{Interval $t_7$} starts at \texttt{net\_dev\_xmit} on the client and ends at \texttt{consume\_skb} on the server.  
          Hence, it measures the time required to transfer the packet from the client's link layer to the server's link layer.  
          \textbf{Interval $t_8$} closes the cycle by measuring the time from \texttt{consume\_skb} to the application on the server, thereby reflecting the time from the link layer to the application.  
          From this point, the measurement cycle restarts with interval $t_1$.  
\end{itemize}

Given the large number of layer transitions and the transmission time over the medium, it can generally be expected that intervals $t_3$ and $t_7$ will constitute the largest share of the total time.  
For the intervals $t_3$ and $t_7$, time synchronization between client and server is required, so that at time $\tau_1$, corresponding to the tracepoint \texttt{net\_dev\_xmit} on the server and at time $\tau_2$, corresponding to the tracepoint \texttt{consume\_skb} on the client, a common time base is available.  
Otherwise, these values could not be compared with each other.  

It is furthermore necessary to synchronize time measurement between kernel space and user space on both devices.  
This is required for the intervals $t_1$, $t_4$, $t_5$ and $t_8$, since in these intervals measurements are taken on both the client and the server, from the application to the tracepoint \texttt{net\_dev\_queue} and from the tracepoint \texttt{consume\_skb} back to the application.  
Thus, for all four intervals, a time measurement in the kernel at the tracepoint and a time measurement in user space within the application are required.  

How this synchronization is implemented is described in the following.

\subsection{Synchronization of the Testenvironment} \label{subsec:impl_uprobe}
The synchronization between user space and kernel space is addressed first, since it is relevant for the subsequent synchronization between client and server.  
In \ac{BPF}, that is, in the code of the application executed within the kernel, time can only be measured using the function \texttt{bpf\_ktime\_get\_ns()}.  
This function returns the time in nanoseconds since system start, as described in \cite{bpf_ktime_get_ns}.  

In Rust, that is, on the user space side, time can be measured using several functions, as described in \cite{rust_time}.  
The function \texttt{std::time::SystemTime::now()} also returns the time since system start.  
However, this value does not match the time obtained from \ac{BPF}.  
Even though both clocks are monotonic, \ac{BPF} refers to the uptime of the kernel, whereas Rust refers to the uptime of the user space.  
Furthermore, \texttt{std::time::SystemTime::now()} is not reliable, as discussed in \cite{systemtime}, since the monotonic clock may refer to different reference points in time.  
Rust does not rely on a single system start time, but on several closely related reference points.  
Although these points are very close to each other, they may still cause measurable drift when using \texttt{std::time::SystemTime::now()}, like stated in \cite{systemtime}.  

The exact composition of the difference between the two time measurements will be described later in this chapter.  
The implementation of the user space and kernel space synchronization is shown in Figure~\ref{fig:uprobe}.  
For synchronization, a uretprobe is used.  
The goal is to establish a common time base simultaneously in user space and kernel space by means of the \ac{uretprobe}.  
This common base then allows the times measured in user and kernel space to be related to each other.  

As described in Section~\ref{subsec:monitoring}, a \ac{USDT} is more suitable than a \ac{uprobe} for performance reasons.  
Zheng et al.\ also state in \cite{zheng2023bpftimeuserspaceebpfruntime} that a \ac{uprobe} is not real-time capable and that its overhead is particularly large under high invocation frequencies.  
Since the implementation of a \ac{USDT} via \texttt{libbpf-rs} was not successful, a \ac{uprobe} must be used.  
However, as the synchronization is performed only once and the overhead plays only a minor role, this choice is acceptable.

The following section discusses the technical implementation of the synchronization.  
This process is illustrated in Figure~\ref{fig:uprobe}.  
As can be seen, a \ac{uretprobe} is used for time synchronization.  
Two timelines are depicted, one for user space and one for kernel space.  
The user space timeline starts at time $tu_0$, while the kernel space timeline begins at time $t_{k0}$.  
As previously mentioned, the problem is that $t_{u0} \neq t_{k0}$.  
Therefore, it is desirable to establish a common reference point on both timelines from which times can be measured relative to each other.  
This is achieved by the \ac{uretprobe}.  

As discussed in Section~\ref{subsec:monitoring}, the implementation of a \ac{uretprobe} requires a \ac{uprobe}.  
The \ac{uprobe} is attached to a user space function and is triggered upon entering this function.  
In Figure~\ref{fig:uprobe}, the function is entered at $t_{u1}$ in user space, and via the \texttt{int3} breakpoint, control is passed to the \ac{uprobe} in kernel space, which receives control at $t_{k1}$.  
It holds that $t_{k1} > t_{u1}$\footnote{Like stated before, these timers can not be compared, because at this point no shared time basis is available. But if they were comparable, the described statement would apply}, since the context switch to the \ac{uprobe} requires time.  
This interval is highlighted in blue in Figure~\ref{fig:uprobe} and corresponds to $t_{k1} - t_{u1}$, which can not be determined.  
As described in Section~\ref{subsec:monitoring}, the \ac{uprobe} only manipulates the return address in order to prepare the trampoline for the \ac{uretprobe}.  
Thus, the \ac{uprobe} terminates at $t_{k2}$ and returns control to the user space function.  
The duration of the \ac{uprobe} is marked in yellow in Figure~\ref{fig:uprobe} and has the value $t_{k2} - t_{k1}$.  

At $t_{u2}$, the function in user space regains control.  
It then sets a timer using the system call \texttt{clock\_gettime()}.  
This syscall again requires a transition into kernel space.  
The duration of this transition is shown in green in Figure~\ref{fig:uprobe}.  
The syscall executes in kernel space starting at $t_{k3}$ and completes at $t_{k4}$.  
At $t_{u3}$, the user space function regains control, and the timer is set.  
This point is marked by a orange dot in the figure and represents the relative moment from which measurements can be taken.  
Since the function returns at this point, the \ac{uretprobe} is triggered.  

The \ac{uretprobe} again switches to kernel space.  
This transition is slightly longer than the syscall transition and is indicated in blue, analogous to the \ac{uprobe}.  
At $t_{k5}$, the \ac{uretprobe} receives control and, using the function \texttt{bpf\_ktime\_get\_ns()}, measures the system time in nanoseconds.  
Thus, at $t_{k6}$, the relative program start time in kernel space is set.  
At $t_{k7}$, the \ac{uretprobe} terminates and returns control to the user space function, which resumes execution at $t_{u4}$.  

At this point, reference values have been established in both kernel and user space that can be used for future measurements.  
When a tracepoint such as \texttt{consume\_skb} is triggered, a timestamp can be obtained in kernel space that can be correlated with the corresponding user space timestamp.  
As shown in Figure~\ref{fig:uprobe}, at $t_{k8}$ the tracepoint is triggered and at $t_{k9}$ the time is measured using \texttt{bpf\_ktime\_get\_ns()}.  
The tracepoint is exited at $t_{k10}$, and control flows through the network layers back to the application in user space, as illustrated in Figure~\ref{fig:tx}.  
The application regains control at $t_{u6}$ and measures the time at $t_{u7}$ using \texttt{Instant::now()}.  
The time difference $d_u$ between the program start at $t_{u3}$ and the measurement at $t_{u7}$ can thus be related to the time difference $d_k$, which is defined as the difference between the kernel space program start $t_{k6}$ and the tracepoint entry $t_{k9}$.  
Consequently, the time needed by $t_4$ and $t_8$ in Figure~\ref{fig:tx} can be determined as $d_u - d_k$.  

It is difficult to determine the delay between the user space time $t_{u3}$ and the kernel space time $t_{k6}$.  
This delay reflects the accuracy of the synchronization between user space and kernel space.  
Zheng et al.\ report in \cite{zheng2023bpftimeuserspaceebpfruntime} that the \ac{uretprobe} introduces an overall overhead of approximately $4\,\mu$s.  
However, since the delay does not account for the entire duration of the \ac{uretprobe}, it is expected to be significantly smaller.  

To estimate this delay, measurements can be performed in user space using \texttt{Instant::now()}.  
From this, Equation~\ref{eq:uretprobe} is derived for the delay $d_{ku}$ between user space and kernel space.  
Accordingly, the duration $t_{uretprobe}$ of the \ac{uretprobe} can be measured as $t_{u4} - t_{u1}$.  
By replacing the \ac{uretprobe} with a \ac{uprobe}, the execution time of the \ac{uprobe} can be determined.  
This corresponds to the duration $t_{uprobe} = t_{u3} - t_{u1}$.  
It must be noted that the \ac{uprobe} returns immediately and does not, unlike the \ac{uretprobe} shown in Figure~\ref{fig:uprobe}, include the timing and ring buffer logic, as this would distort the measurement results. 
This logic is shown later in this chapter. 

\begin{equation} \label{eq:uretprobe}
d_{ku} = \frac{1}{2} [(t_{u4} - t_{u1}) - (t_{u3} - t_{u1})]
\end{equation} 

In this way, the measurement results presented in Table~\ref{tab:timer_comparison} were obtained.  
For each case, 100 measurements were performed in order to determine the maximum and average values of latency and jitter.  
The table reports both the maximum and average values for $d_{ku}$ as well as for jitter, in addition to the average durations of $t_{uretprobe}$ and $t_{uprobe}$.  

Furthermore, these values are provided for two different timers in Rust.  
Specifically, the measurements were conducted using the timer \texttt{SystemTime::now()}, which, as explained earlier, is said to be unsuitable and and the timer \texttt{Instant::now()}.  
In addition, the experiments were carried out once with real-time priority enabled and once without real-time priority.

The results reveal two clear tendencies.  
First, the function \texttt{Instant::now()} is faster than \texttt{SystemTime::now()} both on average and in the worst case and it also exhibits lower jitter.  
Second, the measurements with real-time priority consistently outperform those without real-time priority.  
Both tendencies were expected, since it was already shown in \cite{systemtime} that \texttt{SystemTime::now()} is less accurate than \texttt{Instant::now()}.  
Real-time priority, as described in Section~\ref{subsec:real_time_kernel}, allows the scheduler to prioritize execution, which generally results in lower latency and jitter.  
Since both timers, \texttt{SystemTime::now()} and \texttt{Instant::now()}, require a transition into kernel space, it was to be expected that prioritization by the scheduler would accelerate this process.  

Another interesting observation concerns the duration of the \ac{uretprobe} and the \ac{uprobe}.  
Zheng et al.\ report in \cite[p.~7]{zheng2023bpftimeuserspaceebpfruntime} that the \ac{uretprobe} introduces an overhead of about $4\,\mu$s, while the \ac{uprobe} introduces an overhead of about $3\,\mu$s.  
In the measurement results shown in Table~\ref{tab:timer_comparison}, the times for both probes are higher.  
This can be explained by the fact that this work uses a Raspberry Pi~5, which presumably has lower computational power compared to the \ac{CPU} used by Zheng et al.  
Although \cite{zheng2023bpftimeuserspaceebpfruntime} does not specify the exact \ac{CPU}, it is reasonable to assume that a more powerful processor was employed, as the paper was published in 2023 and the \ac{CPU} of the Raspberry Pi~5 cannot match the performance of a desktop \ac{CPU} from this time.  
Furthermore, additional overhead may be introduced by performing the measurements with Rust user space functions.  
Nevertheless, the results do not deviate substantially from the values reported in \cite{zheng2023bpftimeuserspaceebpfruntime}, which supports the conclusion that the values obtained for $d_{ku}$ are reliable.  

As a final conclusion, the measurements demonstrate that synchronization between user space and kernel space can be achieved with the \ac{uretprobe} at an accuracy of approximately $1$--$1.5\,\mu$s.  
Moreover, the results confirm the observation from \cite{systemtime} that \texttt{Instant::now()} provides more accurate timing than \texttt{SystemTime::now()}.  
Finally, it can be concluded that synchronization should be performed after assigning real-time priority in order to maximize accuracy.

Having explained how user space and kernel space synchronization is achieved, the following section describes how client-server synchronization is implemented.  
This synchronization is carried out in three states, namely \texttt{\ac{NTP}}, \texttt{\ac{PTP}} and \texttt{Check}.  
As previously mentioned, these phases are named after time-synchronization protocols.
However, only their functionality is implemented, not the full protocol specification.  

\ac{NTP} was developed in 1991 by Mills, like he wrote in \cite{103043}.  
At the time of this work, it has been in operation for more than 30 years.  
As described by Chefrour in \cite[p.~31]{CHEFROUR202226}, \ac{NTP} achieves an accuracy ranging from tens of microseconds to several hundred milliseconds, depending on the network conditions.  
As a successor, and particularly with a focus on improved performance, \ac{PTP} was developed in 2002, as reported in \cite{1048550}.  
This protocol, however, was primarily designed for \ac{LAN} environments.  
According to Chefrour \cite[p.~31]{CHEFROUR202226}, \ac{PTP} can achieve accuracies between $10$ and $100\,\text{ns}$, but only when implemented in hardware, which requires specialized network chips.  

Both \ac{NTP} and \ac{PTP} are, as highlighted in \cite[p.~29]{CHEFROUR202226}, significant milestones and key protocols in network synchronization.  
For this reason, these names are used here to denote the phases of coarse- and fine-synchronization, respectively.  
Both protocols rely on the assumption of a symmetric network.  
In other words, it is assumed that the transmission time from $x$ to $y$ equals the transmission time from $y$ to $x$.  
The synchronization approach used in this work is based on the same principle.  

The principle of synchronization is illustrated in Figure~\ref{fig:flow_chart}.  
This figure shows both a flow chart of the three states and their respective iterations as a sequence diagram.  

\begin{figure}[ht]
    \centering
    \includegraphics[width=\textwidth]{figures/time_sync.drawio.pdf}
    \caption{Presentation of a Flow Chart of the synchronization between Client and Server}
    \label{fig:flow_chart}
\end{figure}

The time synchronization begins with the \ac{NTP} phase, which is represented by the \texttt{\ac{NTP}} state in Figure~\ref{fig:state_machine}.  
A predefined number of repetitions is executed until the \ac{RTT} falls below the specified requirement $RTT_{Req}$.  
An \ac{NTP} repetition is illustrated in Figure~\ref{fig:flow_chart}.  
In this process, the server first synchronizes its user space with kernel space, as described earlier.  
It then sends a message of type \ac{NTP} to the client, as shown in Listing~\ref{lst:msg_types}.  
Once the client receives the \ac{NTP} message, it also synchronizes its user space and kernel space and responds with a message of type \ac{NTP}.  
The server waits for the client's response and can thus determine $\ac{RTT}_{NTP}$.  
This ensures that the server and client are roughly synchronized, with an error bounded by $\frac{\ac{RTT}_{NTP}}{2}$.  
This assumption holds only under symmetric network conditions, which Wi-Fi does not reliably provide.  
Nevertheless, it guarantees that the time deviation between client and server is less than $RTT_{NTP}$.  
Therefore, it is advantageous to minimize the \ac{RTT}, which is why the \ac{NTP} phase enforces the requirement $\ac{RTT}_{NTP} < RTT_{Req}$.  
If this condition is not satisfied, the \ac{NTP} repetition is repeated, otherwise, the state changes to \texttt{\ac{PTP}}.  

The resulting $\ac{RTT}_{NTP}$ serves as the basis for fine synchronization.  
The procedure of the \ac{PTP} phase is illustrated as \ac{PTP} repetition in Figure~\ref{fig:flow_chart}.  
In this phase, the server again sends a message to the client, this time of type \ac{PTP}.  
Unlike in the \ac{NTP} phase, the server does not synchronize its user and kernel space before sending the message, but rather after a delay.  
Specifically, it waits for $\frac{\ac{RTT}_{NTP}}{2}$ after sending the message, before performing synchronization.  
The client behaves identically to the \ac{NTP} phase, except that it returns a packet of type \ac{PTP} to the server.  
The server measures $\ac{RTT}_{PTP}$ and checks whether $|\ac{RTT}_{NTP} - \ac{RTT}_{PTP}| < \ac{PTP}_{Req}$ holds.  
If the condition is satisfied, the process transitions to the \texttt{Check} state, otherwise, the repetition is executed again.  
This approach ensures that the server can predict the client's reception time of the packet, thereby improving synchronization accuracy.  
In the case of a symmetric network, the maximum synchronization error is $PTP_{Req}$.  
However, $\ac{RTT}_{NTP}$ may not always be reproducible, since it could have been obtained under exceptionally favorable conditions that cannot be recreated.  
For this reason, the \ac{PTP} phase is limited to a maximum number of repetitions.  
If this limit is exceeded, $\ac{RTT}_{NTP}$ must be redetermined, and the system transitions back to the \texttt{\ac{NTP}} state.  

The final phase of the time-synchronization process is the Check state.  
This step is necessary because Wi-Fi is not always symmetric.  
In this phase, the server sends a message of type Check to the client while recording a timestamp $t_{ss}$.  
The client records the two timestamps $t_{cr}$ upon receiving the message and $t_{cs}$ upon sending the response.  
It then returns these values to the server in a message of type Check.  
Upon reception, the server records another timestamp $t_{sr}$.  
From these values, the one-way delay from server to client is computed as $t_{s-c} = t_{cr} - t_{ss}$, and the delay from client to server as $t_{c-s} = t_{sr} - t_{cs}$.  
If the Wi-Fi connection is symmetric and the synchronization is correct, then $t_d = t_{s-c} - t_{c-s} = 0$.  
In the \texttt{Check} phase, this procedure is repeated several thousand times, after which the median $M_{Check}$ of the $t_d$ values is calculated.  
If $M_{Check} < Latency_{Req}$, real-time computation is initiated, otherwise, the system returns to the \texttt{\ac{PTP}} state.  
Although Wi-Fi tends to be symmetric on average over longer periods, this is not guaranteed for individual packets.  
Therefore, the median\footnote{In this case, the median is used because it is less sensitive to outliers and thus provides more stable results.} is used to determine whether synchronization is sufficiently accurate.  
While deviations still occur, under the assumption of long-term Wi-Fi symmetry, the maximum synchronization error between client and server is bounded by $Latency_{Req}$.  
In this work, a threshold of $10\,\mu$s is applied.  

Following the \texttt{Check} state is the \texttt{Calc} state.  
As shown in Figure~\ref{fig:state_machine}, this is the only state with a real-time requirement.  
The implementation of this state has already been explained in Figures~\ref{fig:application} and \ref{fig:tx}.  
The number of repetitions depends, as illustrated in Figure~\ref{fig:application}, on the number of measurement points.  
The following section discusses how data can be collected using \ac{BPF} and how it is processed in Rust.  

The code used to read a tracepoint is nearly identical for all tracepoints.  
As an example, the procedure for the tracepoint \texttt{net\_dev\_xmit} is explained.  
The code of the function executed when the tracepoint triggers is shown in Listing~\ref{lst:bpf_tracepoint}.  
Similar to the \ac{uprobe}, the function is attached to the tracepoint using \texttt{SEC("tracepoint/net/net\_dev\_xmit")}.  
As shown in lines 3–5, the \ac{PID} must first be determined using the function \texttt{bpf\_get\_current\_pid\_tgid()}, and the process name must be retrieved using \texttt{bpf\_get\_current\_comm()}.  
Subsequently, the process name (\texttt{comm}) is verified to ensure that the message originates from the correct process.  

In lines 8–13, the addresses of \texttt{head} and \texttt{mac\_header} are extracted.  
These addresses are obtained from the \texttt{sk\_buff} struct, which, as described in \cite{sk_buff}, represents a network message.  
To extract these fields, the function shown in Listing~\ref{lst:member_read} is used.  
This function determines the address of a struct member using the \texttt{offsetof()} function.

Using \texttt{head} and \texttt{mac\_header}, the location of the MAC header can be determined.  
For precise identification of the network packet, the IP header is also required.  
This header follows directly after the MAC header and can therefore be computed as shown in line 14 of Listing~\ref{lst:bpf_tracepoint}.  
Subsequently, it is checked whether the packet is a \ac{TCP} packet or not.
If not, the function is aborted.  
Additionally, lines 22–28 of Listing~\ref{lst:bpf_tracepoint} extract the last octet of the source and destination IP addresses, i.e., the \texttt{yz} part from \texttt{192.168.wx.yz}.  
It is then verified whether the server IP ends with 1 and the client IP ends with 43.  
If this condition is not met, the function is aborted, as the packet is either destined for the wrong recipient or sent by the wrong sender.  

The \ac{TCP} header is also required to access the payload.  
The TCP header follows immediately after the IP header, and its length must be known.  
This length is computed in line 29.  
For this purpose, the IP header length (\texttt{ihl}) is used and multiplied by 4.  
This is necessary because \texttt{ihl} specifies the header length in 32-bit words, as described in the standard \cite[p.~11]{rfc791}.  
In other words, if \texttt{ihl} returns 5, the IP header consists of $5 \times 32$ bits, i.e., $5 \times 4$ bytes.  

In line 36, the offset for the payload is determined.  
For this calculation, the TCP header length is required.  
This length can be computed using the data offset, which again provides the size in words, as described in the standard \cite[p.~16]{rfc793}.  

Finally, the message specified in Rust is loaded.  
A check is performed again to ensure that the message type is not out of bounds.  
If the check passes, the event is assembled and submitted to the ring buffer.  
This procedure has already been illustrated in Listing~\ref{lst:bpf_uprobe}.  

The data sent via the ring buffer is received in user space by Rust and stored as events in separate queues.  
In other words, a dedicated queue is provided for each tracepoint event.  
As shown in Listing~\ref{lst:bpf_uprobe}, the event also contains the \ac{PID}.  
This identifier is used to verify whether the event in the ring buffer originates from \ac{BPF}.  
Since the ring buffer is not exclusively assigned to \ac{BPF} but represents a system-wide resource, this verification is necessary.  
Subsequently, the \texttt{net\_dev\_xmit} event is written into the send queue in user space.  
The same procedure applies to the other events.  

Listing~\ref{lst:calc} illustrates the flow of the \texttt{calculation} function on the server as pseudo-Rust code.  
As previously mentioned, the start time is first recorded and the $x$-coordinate is computed, before the angle for which the $y$-coordinate is to be calculated is sent to the client.  
This process is shown in lines 2--7.  
Subsequently, the tracepoint events for \texttt{net\_dev\_xmit} and \texttt{net\_dev\_queue} are awaited.  
This is realized through the function \texttt{wait\_for\_event()}, which takes the queue as a parameter in which the corresponding event is collected.  
The function returns the event, from which the timestamp of its occurrence can be extracted via the \texttt{timestamp} attribute.

Afterwards, the response from the client is awaited, and upon its arrival the end time is recorded.  
The message contains the $y$-value and the client's timing data.  
These, combined with the server's timing data, are used as shown in lines 22--26 to calculate the monitoring times described in Figure~\ref{fig:tx}.  
Finally, the server checks whether the interval between start and end time exceeds the specified time limit, thereby violating the real-time requirement.  
If this is the case, the previously mentioned penalty is applied to $y$.

After this state, only two states remain, as shown in Figure~\ref{fig:state_machine}.  
The first is the \texttt{Error} state, which is also a terminal state.  
It can be reached from any synchronization state as well as from the \texttt{Calc} state.  
This state is entered under one of the following conditions:  
\begin{itemize}  
    \item \textbf{Client timeout:} If the client terminates the \ac{TCP} connection or does not respond in the case of \ac{UDP}.  
    \item \textbf{Incomplete dataset:} If the data collected by the server\footnote{The dataset consists of monitoring data and circle data, i.e., the $x$ and $y$ values.} is incomplete.  
          In other words, if not all points contain measurements or if certain data for specific points are missing.  
\end{itemize}  

The \texttt{Error} state terminates both the server and the client and informs the test automation system that the test must be repeated.  

The second state, which has not yet been described, is the \texttt{Save} state.  
In this state, the data collected during \texttt{Calculation} are written to a file, where they can later be retrieved and visualized.  
This state concludes in the \texttt{End} state, which marks the successful completion of the \texttt{test run}.

\subsection{Test Automatization}

The organization and automation of the test executions are implemented by means of a test suite.  
As described in Chapter~\ref{subsec:used_technologies}, this suite is implemented in Python.  
There is one test suite for the client and one for the server.  
However, these are largely similar in their structure and functionality.  

Figure~\ref{fig:test-suite} illustrates the workflow of the \texttt{Server Test Suite}.  
Based on this figure, the workflow of the test suite will be explained in the following.  
The workflow of the \texttt{Client Test Suite} is also explained on this basis.
In the figure the test suite for the server is shown, it will be explained, when the \texttt{Client Test Suite} differs from it.  

\begin{figure}[ht]
    \centering
    \includegraphics[width=0.7\linewidth]{figures/Test-Suite.drawio.pdf}
    \caption{Sequence diagram illustrating the interaction and execution flow between the Server and Client Test Suites.}
    \label{fig:test-suite}
\end{figure}

The test suite begins by compiling the Rust code in order to ensure that the latest version is used.  
Subsequently, in the \texttt{Server Test Suite}, the \texttt{Iperf-Bulk Server} is started in a separate thread.  
This step does not exist in the \texttt{Client Test Suite}.  
On the client side, the \texttt{Iperf-Bulk Client} is not launched by the test suite itself, but rather by the application once the \texttt{Check} state has been successfully finished.  

In both test suites, the next step is the selection of the \texttt{test run}.  
For this purpose, the status file is first checked, which contains a digit specifying which \texttt{test run} should be executed next.  
Afterwards, the test specific configuration file is opened.
Each configuration corresponds to one line in this file, specifying the Wi-Fi standard, frequency, bandwidth, \ac{QoS} status, protocol and \ac{AP} configuration name.  
For instance, the line \texttt{4 2.4 20 0 udp wifi4} specifies that the Wi-Fi connection should use standard 4, a frequency of 2.4 GHz and a bandwidth of 20 MHz.  
Moreover, no \ac{QoS} parameters should be applied, the application should use \ac{UDP} and the corresponding \texttt{hostapd} configuration for the Wi-Fi parameters is included in the config file \texttt{wifi4}.  
The last parameter is not relevant for the \texttt{Client Test Suite} since it does not have to start an \ac{AP} with \texttt{hostapd}.  

The next step on the server side is to start the \ac{AP} with the respective \texttt{hostapd} configuration.  
Instead of launching \texttt{hostapd}, the client establishes a connection to the server using wpa-supplicant.  
The \texttt{hostapd} configurations are explained in more detail in Chapter~\ref{subsec:hostapd}.  

In the subsequent step, both test suites set or reset the \ac{QoS} parameters.
Afterwards the application, either the server or the client, is started in a thread.    
On the server side, only the application priority is checked to ensure that it is set to 139, i.e., real-time priority, while the \texttt{iperf} process runs at a lower priority.  
This is achieved by executing the shell command \texttt{ps -eLo comm,pri | grep server/iperf} in Python and verifying that the server process runs at priority 139, whereas the \texttt{iperf} process does not.  
As described in~\cite{ps}, this command lists all processes including threads and outputs only the name and the priority.  
The client side checkes the priorities analogously.  
Additionally, it is verified that Wi-Fi version, bandwidth and frequency match the values specified in the configuration.  
In other words, the \texttt{Client Test Suite} checks that the server's \ac{AP} configuration is correct and actually usable\footnote{The fact that an \ac{AP} provides certain features, such as Wi-Fi standard 6, does not automatically imply that these features are active in the client connection.  
For example, if the client connects to the \ac{AP} with an incompatible \ac{WPA} configuration, the Wi-Fi standard may be downgraded.  
Therefore, it is necessary to perform the verification on the client side to guarantee that all configurations are applied correctly.}.  

The bandwidth can be determined using the command \texttt{iw dev IFACE info}.  
The value is found after the parameter \texttt{width:} and can be extracted with the \ac{RegEx} $re.search(r'width:\backslash s*(\backslash d+)\backslash s*(?=MHz)', output)$.  
The frequency and Wi-Fi standard can be determined with the command \texttt{iw dev IFACE link}, as described in~\cite{iw}.  
The frequency is found after the argument \texttt{freq} and can be extracted using the \ac{RegEx} $re.search(r'freq:\backslash s*(\backslash d+\backslash .\backslash d+)', output)$.  
For determining the Wi-Fi standard, the full output is analyzed for the flags \ac{HT}, \ac{VHT} and \ac{HE}.  
\ac{HT} is mandatory for Wi-Fi~4, \ac{VHT} for Wi-Fi~5 and \ac{HE} for Wi-Fi~6.  
If none of these flags is present in the output, the standard is older than Wi-Fi~4.  

Even if the tests fail, the application is executed to completion, but the test results are logged, allowing one to identify which properties were not fulfilled.  
The tests are implemented using \texttt{py-unittest}.  
This ensures that the desired configurations are validated and enforced.  

After the application finishes, the status file is updated.  
If the application terminates successfully in the state \texttt{End}, the digit in the status file is incremented by one.  
If, however, the application terminates in the state \texttt{Error}, the digit remains unchanged.  
In this way, the current \texttt{test run} will be repeated.  
The next step is to clean up the entire configuration.  
This means that \ac{QoS} parameters are reset if necessary, and the \ac{AP} is terminated.  
On the client side, the \ac{WPA} configuration is reset.  

Finally, the \texttt{Iperf-Bulk Server} thread is terminated.  
Figure~\ref{fig:test-suite} illustrates a \texttt{test run}.  
This represents the section that is repeated at least once for each configuration entry in the configuration file.  
Consequently, the Rust project is compiled only once for both client and server.  
On the server side, the \texttt{Iperf-Bulk Server} is also started only once, since it remains persistent.  
By contrast, the \texttt{Iperf-Bulk Client} reconnects for each \texttt{test run}, since it may require a different configuration.  

Having now described the organization of the \texttt{test runs}, the following section addresses the implementation of the \acp{AP} using \texttt{hostapd}.  

\subsection{Access point configuration} \label{subsec:hostapd}
As described in Chapter~\ref{subsec:impl}, the \acp{AP} must support the three configurable properties Wi-Fi standard, frequency, and bandwidth.  
These properties can be configured using \texttt{hostapd} in a configuration file.  
The following section explains which parameters must be set to achieve the desired network configuration.  
Furthermore, it also addresses how the client’s \texttt{wpa\_supplicant} must be configured to connect to the network.  

The configuration can be divided into several parts:  
\begin{itemize}
    \item \textbf{Core elements:} Core elements include parameters that are relevant in every configuration and do not change between configurations.  
          These include the \texttt{interface}, which specifies the network interface to use and the \texttt{driver}, which specifies the network driver.
          In this work, the \texttt{nl80211} driver is always used.  
          Additionally, \texttt{ssid}, i.e. the network name and \texttt{wpa\_passphrase}, a password, must be specified.  
          Certain security aspects are also relevant, such as \texttt{wpa\_key\_mgmt}, where Simultaneous Authentication of Equals (SAE) is used.  
          Furthermore, \texttt{rsn\_pairwise=CCMP} must be set.  
          The \texttt{rsn\_pairwise} parameter specifies the cipher suite used for the Robust Security Network (RSN) and CCMP is the encryption algorithm applied for data confidentiality and integrity.
          
    \item \textbf{Wi-Fi standard:} The Wi-Fi standard can be set using the \texttt{ieee80211} parameters.  
          For standard 4, \texttt{ieee80211n=1} must be set, while for standard 5, \texttt{ieee80211ac=1} and for standard 6, \texttt{ieee80211ax=1} is necessary.  
          Additionally, for standard 6, \texttt{ieee80211w=2} must be set, which indicates that management frame protection is required.  
          Without this, it is not possible to create a Wi-Fi standard 6 \ac{AP}, as explained in~\cite{hostapd-config}.  
          The parameters \texttt{ieee80211w=2} and \texttt{key\_mgmt=SAE} must also be included in the client’s \texttt{wpa\_supplicant} configuration.  
          This is the only configuration on the client side that must be adjusted when Wi-Fi property, like the standard, change.

    \item \textbf{Frequency:} To configure the frequency, the \texttt{hostapd} parameters \texttt{hw\_mode}, \texttt{channel}, and \texttt{op\_class} must be set.  
          Frequencies of 2.4\,GHz, 5\,GHz and 6\,GHz can be selected.  
          For 2.4\,GHz, \texttt{hw\_mode=g} must be set.  
          For 5\,GHz and 6\,GHz, \texttt{hw\_mode=a} must be set.  
          The channel must be within the respective frequency band.  
          As described in Chapter~\ref{subsec:stand}, channels 1–14 are available for 2.4\,GHz, 36–156 for 5\,GHz, and 1–233 for 6\,GHz.  
          Since \texttt{hw\_mode} and \texttt{channel} alone cannot clearly distinguish between 5\,GHz and 6\,GHz, the \texttt{op\_class} parameter is used.  
          According to~\cite[p.~2]{operating-class}, all values of 131 or higher correspond only to 6\,GHz.

    \item \textbf{Bandwidth:} To configure the bandwidth in \texttt{hostapd}, the parameters \texttt{channel}, \\
          \texttt{centr\_freq\_idx}, \texttt{oper\_chwidth} and \texttt{op\_class} are relevant.  
          Each channel has a center frequency $f_c$, which can be calculated, like stated in \cite[p.~2829]{9363693}, as $f_c = f_{start} + 5 \times n$, where $f_{start}$ is the start frequency of the respective band and $n$ is the channel number.  
          For 2.4\,GHz, bandwidths of 20\,MHz and 40\,MHz are available, whereas for 5\,GHz and 6\,GHz, 20\,MHz, 40\,MHz, 80\,MHz and 160\,MHz are possible.  
          By default, if only the channel is specified, a channel bandwidth of 20\,MHz is used.  
          For other bandwidths, \texttt{centr\_freq\_idx} and \texttt{oper\_chwidth} must be set.  
          For \texttt{oper\_chwidth}, the value $0 \rightarrow 40\,\text{MHz}$, $1 \rightarrow 80\,\text{MHz}$ and $2 \rightarrow 160\,\text{MHz}$ applies.  
          For \texttt{centr\_freq\_idx}, the center frequency $f_{center} = \frac{f_{c-start} + f_{c-end}}{2}$ must be calculated, and the channel containing this frequency must be selected.  
          For example, in the 5\,GHz band with a bandwidth of 80\,MHz and a starting channel of 36, the end channel is 48 due to the 20\,MHz channel width\footnote{Like described in Chapter \ref{subsec:stand}, the distance between two channels is 5\,MHz. So to achieve a bandwidth of 80\,MHz it is necessary to add four 20\,MHz channels. In this case these are the channel 36, 40, 44 and 48.}.  
          Thus, $f_{center} = \frac{(5000\,\text{MHz} + 5 \times 36) + (5000\,\text{MHz} + 5 \times 48)}{2} = 5210\,\text{MHz}$.  
          This corresponds to channel 42, which is assigned to \texttt{centr\_freq\_idx}.  
          In the 6\,GHz band, \texttt{op\_class} must also be considered.  
          Opclass values correspond to bandwidths as follows: 131 $\rightarrow$ 20\,MHz, 132 $\rightarrow$ 40\,MHz, 133 $\rightarrow$ 80\,MHz and 134 $\rightarrow$ 160\,MHz.

\end{itemize}

Having now explained how the desired settings can be applied in \texttt{hostapd}, the following section examines further measures regarding network characteristics, prioritization and their influence on the real-time performance of the Wi-Fi connection.
