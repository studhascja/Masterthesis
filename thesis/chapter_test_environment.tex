\chapter{Test Environment}
In this chapter, the test environment is examined in more detail.
In the following, the terms test environment, test system, and operating system are used. 
The test environment comprises both the test system and the operating system. 
The test system refers exclusively to the applications that are part of the test environment and run on top of the operating system. 
Accordingly, the test system does not include the underlying hardware or the operating system itself.

This chapter is divided into the three parts requirements, test system and the operating system. 
A detailed analysis of the requirements is provided at the outset, as they serve as the basis for both the development of the operating system and the test concept. 
Thus, the requirements constitute the foundation for the overall design of the test environment.
Afterwards the operating system, as it forms the foundation on which the test system will later be implemented, will be described.
Finally, the test system itself will be discussed in more detail.

\section{Requirements}
In this section, the requirements of the test environment are analyzed in greater detail. 
The discussion begins with a description of the system architecture, followed by an outline of general \ac{rt} requirements. 
These are then used to define the specific requirements applicable to the test system.

The test environment is illustrated in Figure \ref{fig:pi_wifi_general}. 
It consists of two Raspberry Pi 5 devices, whose exact composition is described in detail in Chapter \ref{sec:used_hardware}. 
One Raspberry Pi acts as the server, while the other functions as the client. 
Both devices run the same operating system.

There are two communication links between the server and the client.
One link which transfers \ac{rt-data} and another one for transferring \ac{non-rt-data}.
These two links are illustrated in Figure \ref{fig:pi_wifi_general} in blue and red.
These connections are handled by separate programs but operate within the same network. 
The server provides an access point to which the client connects, thereby establishing a peer-to-peer connection.

In summary, the goal of the test environment is to transmit both \ac{rt-data} and \ac{non-rt-data} data over the same wireless network interface. 
While the bulk data throughput should be maximized, the primary focus is to ensure that no \ac{rt} violations occur on the \ac{rt} connection.

Since the test system is intended to transmit, among normal data, \ac{rt-data}, it must fulfill the requirements of a \ac{rt-system}. 
Therefore, the following section first outlines the general requirements of \acp{rt-system}. 
Subsequently, additional requirements that go beyond standard \ac{rt} criteria and are specifically relevant for this system within the given test environment are discussed in more detail.

\subsection{Requirements Real Time}
To enable a system to achieve \ac{rt} capability, numerous factors must be considered. 
Since this work aims to evaluate the \ac{rt} capabilities of Wi-Fi, an interface that is not inherently \ac{rt} capable—and given that hardware-based requirements would have little impact in this context while significantly broadening the scope of this thesis, only software-related requirements will be addressed.

As previously mentioned in Chapter \ref{sec:real_time}, the primary objective of a \ac{rt} system is predictability. 
According to Buttazzo \cite[p. 10]{Buttazzo_2024}, predictability can only be achieved if the system ensures timeliness, meaning that the value of a process depends not only on its correct output but also on its timely execution—specifically, meeting deadlines.

To fulfill these requirements, the software foundation, particularly the operating system kernel, must be tailored to \ac{rt} needs.
Key aspects include preemptiveness, scheduling, inter-task synchronization, inter-task communication, memory management, interrupt handling, and timers.
The necessity for these mechanisms to be implemented differently in \ac{rt} capable kernels compared to non-real-time ones is discussed in detail in Chapter \ref{subsec:real_time_kernel} and will therefore not be reiterated here.

However, these mechanisms must not only be \ac{rt} capable at the kernel level—they also need to be considered during the development of applications intended to operate in a \ac{rt} context. 
As Buttazzo outlines in \cite[p. 13 - 20]{Buttazzo_2024}, particular attention must be paid to the choice of programming language, memory usage, and synchronization and communication between processes.
It follows that, as shown in Figure \ref{fig:requirements} memory management, inter-task communication and inter-task-synchronsiation are not only requirements for the \ac{OS}, but must also be taken into account in the test system.

In \cite[p. 17, 18]{Buttazzo_2024} Buttazzo emphasizes that the choice of programming language for \ac{rt} systems should avoid the use of dynamic data structures and recursion. 
This is because dynamic memory allocation and deallocation introduce unpredictability in execution time, making it impossible to determine the program's timing behavior in advance. 
Therefore, memory must be allocated statically and prior to execution. 
Similarly, recursion poses a challenge, as it is difficult to predict the amount of memory required and the number of recursive calls during runtime.

Furthermore, Buttazzo argues that a programming language suitable for \ac{rt} applications should support bounded loops, meaning that the number of iterations is fixed and known at compile time. 
In general, programming languages for \ac{rt} systems should offer the capability to explicitly define timing constraints and ensure adherence to the aforementioned principles—ideally enforcing them.
As programming languages, Buttazzo suggests \texttt{Real-Time Concurrent C} and \texttt{Real-Time Euclid}, both of which fulfill all the stated requirements.

By contrast, Michael P. Rooney et al. describe in \cite[p. 1]{10321761} a study involving the development of a \ac{SCADA} \ac{rt} application implemented in the four different programming languages C, Rust, Numba Python and Cython.
All of these languages were successfully used to achieve \ac{rt} performance. 
Notably, Rust demonstrated a power consumption profile comparable to C, indicating similar efficiency.

While the characteristics outlined by Buttazzo are not mandatory in any of these languages, they can be implemented with appropriate discipline and design. 
Thus, these languages are also suitable for \ac{rt} application development, provided that the specific constraints related to memory management, recursion, and timing predictability are consciously observed and enforced by the developer, as they are not inherently guaranteed by the language itself.

The chosen programming languages and specific implementation-level requirements for achieving \ac{rt} capability and how these are addressed are discussed in detail in Chapter \ref{subsec:impl}.

\subsection{Requirements Test Environment}
The following section defines the requirements for the test environment which are shown in yellow in Figure \ref{fig:requirements}.
These are divided into the requirements for the operating system and the requirements for the test system itself.
For both the test system and the operating system, the previously defined criteria for \ac{rt} capability are assumed to be fulfilled.

The requirements for the operating system include providing appropriate support for both the hardware and the software components of the test evnironment. 
As described in Chapter \ref{sec:used_hardware}, this work utilizes a Raspberry Pi 5, to which a MediaTek 7925B22M and an Atheros AR5BXB92 Wi-Fi module can be connected via PCIe.
Accordingly, the operating system have to support the Raspberry Pi 5 architecture and offer compatibility with the drivers mt76, mt7925e, and ath9k.

Furthermore, the mt7925e driver is only available starting from Linux kernel version 6.8 and receives extended feature support with newer versions. 
These enhancements primarily concern functionality related to Wi-Fi 6E and Wi-Fi 7. 
Since these standards are also within the scope of this work, the operating system should support the most recent possible version of the mt7925e driver to ensure full access to these capabilities.

In addition to hardware compatibility, the operating system must also ensure compatibility with the required software components. 
This includes the availability of essential programming languages and user-space networking and diagnostic tools which are necessary to run the test-system.

Moreover, the operating system should be as minimal as possible, containing only the components explicitly required for the test environment. 
This reduces background activity and minimizes potential sources of interference or error, thereby ensuring a more stable and predictable testing environment.

In addition to the operating system, the test system also has non‑real‑time requirements.
These are highlighted in yellow under “Test System” in Figure \ref{fig:requirements}. 
The test system must be capable of transmitting both \ac{rt} and non-real-time data concurrently over the same network, with the \ac{rt} traffic maintaining a maximum round-trip delay of 3 ms. 
This timing constraint stems from the fact that this work seeks to characterize Wi‑Fi’s \ac{rt} capabilities and the factors that influence them, and to assess whether Wi‑Fi can be employed in an industrial \ac{rt} environment. 
As discussed in Chapter \ref{sec:real_time}, such environments commonly impose a 3 ms deadline.

Furthermore, the application under test must be instrumented so that its \ac{rt} performance can be measured accurately, enabling meaningful conclusions to be drawn. 
This requires comprehensive monitoring and debugging facilities to precisely identify and isolate any sources of \ac{rt} violations.

For the non‑real‑time traffic, as much data as possible should be transmitted without degrading the \ac{rt} application’s performance. 
This measn, only throughput and packet‑loss metrics need be considered for this traffic in the monitoring.

Moreover, this study will compare the \ac{rt} performance of the algorithms underpinning different Wi‑Fi standards. 
To that end, the server must support access points for Wi-Fi 4, 5, and 6 across all relevant frequency bands (2.4 GHz, 5 GHz, and 6 GHz). 
The impact of QoS on \ac{rt} capability will also be evaluated, so the test system must be able to mark network packets with QoS parameters. 
Given the large number of combinations of Wi‑Fi standards, frequency bands, and QoS settings, an automated test framework is required to generate a comprehensive dataset for all test cases, from which reliable insights can be derived.

In this chapter, the requirements for the test environment were defined. 
The following sections will discuss how these requirements are implemented. 
The focus will first be on the selection and configuration of the used technologies, because they are needed for the creation of the \ac{OS}.

\section{Operating System}
As discussed in the previous chapter, the selection of an appropriate operating system must primarily consider its \ac{rt} capabilities. 
Such operating systems are referred to as Real-Time Operating Systems (RTOS). 
There exists a wide variety of RTOS, each differing in architecture, strengths, and limitations.

One RTOS that imposes almost no restrictions in terms of performance and compatibility compared to a general-purpose operating system is RT-Linux. 
As described by Sampath et al. in \cite{Sampath_2007}, RT-Linux is a Linux-based system enhanced through the PREEMPT\_RT patch, which equips it with real-time capabilities. 
The authors examine the use of RT-Linux on an industrial controller with strict \ac{rt} requirements and additional \ac{rt} Ethernet demands. 
Their study demonstrates the suitability of RT-Linux for such applications, reporting a maximum jitter of 380 microseconds over a 24-hour endurance test.

Similarly, Arshiabanu \cite{ARSHIABANU_2014} presents a \ac{rt} system implemented using RT-Linux. 
The study evaluates the impact of various scheduling policies on \ac{rt} performance and is executed on a Raspberry Pi. 
Dewit et al. \cite{ae11aecebd4e4fd6896d0b8bb93fa73a} further investigate the influence of RT-Linux in combination with a Raspberry Pi 5 on scheduling latencies, reporting a maximum scheduling latency of 125 microseconds.
This study is especially relevant for this work, because it uses the same hardware platform.

Despite these studies, there also are more critical perspectives. 
Siro Arthur et al. \cite{Siro_2007} also evaluated \ac{rt} capabilities of RT-Linux. 
This study analyzes metrics such as context switch time, memory access latency and TCP latency. 
It compares not only various Linux preemption models but also contrasts RT-Linux against RTOS specifically designed for \ac{rt} use, such as RTAI and LXRT. 
The study reveals that while the PREEMPT\_RT patch enhances \ac{rt} capabilities, it does not reach the same level of determinism as systems natively designed for \ac{rt} applications. 
Furthermore, this analysis was performed on single-core CPUs, where reduced shared resources can change the \ac{rt} behavior. 

There are also studies with multicore platforms which questions the suitability of RT-Linux for hard \ac{rt} environments. 
Carvalho et al. \cite{9018464} investigated RT-Linux running on a Raspberry Pi, focusing on latency metrics such as polling, timed loops, hardware interrupts, and software interrupts. 
Their results confirm that although RT-Linux offers certain \ac{rt}  properties, it should only be used in non-critical real-time environments. 
This conclusion is supported by Betz et al. \cite{5347056}, who state that RT-Linux is appropriate for soft \ac{rt} applications.

Yang et al. \cite{10870260} compare the \ac{rt} performance of NuttX, FreeRTOS, RT-Linux, and Xenomai. 
A noteworthy aspect of their study is the inclusion of both \ac{rt} capabilities and general-purpose features. 
While RT-Linux can be used as a standalone system, to match these requirements, pure RTOS like FreeRTOS and NuttX are executed alongside a general-purpose operating system. 
Also in this study a Raspberry Pi 4 was used as the hardware platform. 
The results are showin that pure RTOS, especially FreeRTOS, netherless deliver better \ac{rt} performance.

Mariesk et al. \cite{6140739} distinguish between the two fundamental RTOS types kernel-based RTOS and embedded RTOS. 
In their study, they evaluate systems based on interrupt latency, task switching time, and preemption time. 
RT-Linux and Xenomai are considered kernel-based RTOS, while eCos represents the embedded type. 
The results show that kernel-based RTOS are more suitable for multi-task applications due to their lower task-switching overhead. 
Since this work requires the execution of multiple concurrent tasks, frequent scheduling switches are expected, making a kernel-based RTOS the preferable choice.

In summary, the optimal RTOS depends heavily on the specific application and \ac{rt} requirements. 
Based on the referenced studies, FreeRTOS appears to offer the best \ac{rt} capabilities. 
However, additional constraints beyond \ac{rt} performance must be considered when selecting the operating system, like stated in the previous section.
This means particularly hardware compatibility of the \ac{OS}. 
The MediaTek 7925B22M Wi-Fi card used in this work lacks drivers outside the Linux ecosystem, thereby excluding FreeRTOS as a viable option.

Considering the experience with RT-Linux on Raspberry Pi systems stated by the studies before and the demonstrated maximum scheduling latency of 125 microseconds along with a maximum jitter of 380 microseconds of the test-system, RT-Linux proves sufficient for the purposes of this work. 
Given a round-trip time (RTT) requirement of 3 milliseconds, this jitter is acceptable. 
Furthermore, since Wi-Fi is inherently not \ac{rt} capable, and as discussed in Chapter \ref{sec:used_hardware}, the employed hardware which has, among other shared resources, a split L3 cache, is not optimized for \ac{rt} processing.
So the minor limitations of RT-Linux do not significantly impact this test-environment.
